# 工作日记保存与决定更新

## 触发与内容

只有用户明确要求记录今天、保存指定会话或维护用户级记忆时进入本流程。自动召回、开发完成和同意方案都不触发保存。只提取当前实际可见或成功读取的指定材料，不扩大到其他会话分支。

日记回答“我做了什么”，候选可包含：

- 工作内容与实际结果，区分讨论、尝试、完成、失败和未完成。
- 当时作出的决定及理由、重要约束、仍需处理的问题。
- 有后续价值的排查经历与结论；根因未确认就注明未知，不用一般原则补猜根因。

不要求每条内容具有跨项目通用性。避免复制完整代码、日志、配置清单和凭据；记录关键事件即可，必要时指向项目文档或本地经验主题。用户只要求一件事时，不扩成整天总结；无有效新增时结束。

日记和项目知识是两个用途。日记可以说“处理了某问题，经验见项目主题”，项目正文记录具体条件和处置；只有明确要求项目知识维护时才进入 `project-write.md`，不顺带双写。画像仅在用户明确要求提炼或维护时按 `profile.md` 另行预览确认。

## 拟定候选

1. 从 `status` 的项目表将实际项目名/别名映射到稳定 ID。项目工作使用对应 ID；`general` 用于非项目事项或明确要求的通用经验，不是所有记录的默认桶。没有匹配时先提出登记候选，不能从文件夹名擅自创建近似项目。
2. 按日期和项目组织指定材料，每个项目单独生成保存计划。脚本使用库时区的当前保存日期；补记过去工作时在正文说明实际发生时间，不能伪造保存日期或假设存在日期参数。
3. 一条记录只表达一个事项。进度、问题、事实分别用 `progress`、`issue`、`fact`；决定和约束用 `decision`、`constraint`，提供稳定 `rule_key`。个人偏好的日记依据可用 `preference_evidence`，但这不等于已更新画像。
4. 查重：同一事实和状态没有变化就不重复保存；新一天确有新工作才记录新进展。不要把内容相似的不同事件误当重复。已有相同 `session_id` 会拒绝，不能改 ID 绕过重复限制，也不承诺会话增量自动合并。
5. 对决定和约束，先用 `rules --project <真实ID>` 查看当前规则，必要时分页。相同键的新版本自动列出被替代旧记录；不同键发生明确替代时用 `supersede_record_ids` 和 `supersession_reason` 指明同项目当前有效旧规则。适用平台或条件不同的记录可共存，未决冲突不擅自裁决。
6. 来源关联用 `source_record_ids` 指向已经存在的真实日记 ID，适用于有来源的经验提炼或后续事件。不编造来源，不把项目文件路径塞进 ID 数组；项目知识链接可写入正文。来源不必仍是当前规则，历史版本也可作为依据。

## 预览与提交

- 用标准输入调用 `plan save --input -`，不在工作项目散落临时 JSON。计划缓存写入用户级库的技术目录，不是权威日记，也不是完全不落盘。
- 展示项目、保存日期、提取范围、完整新增正文、来源 ID，以及 `superseded_records` 中每条旧正文、日期、理由和后继 ID。明确说明：旧条目仅退出当前规则，正文、日期和 ID 仍保留。
- `withdrawn_months` 列出被撤回摘要；新记录进入已经整理过的当月时该月摘要需重建。仅替代旧月份决定不会抹去旧月份历史摘要，不宣称已自动重建。
- 用户确认该份具体计划后，才 `commit --plan-id <id> --approved`。候选变化、计划过期、协议旧版或库内容变化时停止并重新预览。
- 不提前生成随后会被前一次提交指纹变更作废的多个计划。多项目或多用途按当前状态依次生成并确认；一份确认不覆盖未展示内容。

## 历史、纠错与忘记

新决定取代旧决定不是删除：脚本保留旧正文，只写替代状态与关联，当前规则查询只返回有效版本。月度来源和历史查询仍保留当时的决定，不能把它误当今天的约束。

用户明确要求纠正错误记录或忘记某条信息时，按 `integrity.md` 展示具体物理删除及引用影响；必要时再提出正确内容的保存计划。不能借正常更新、画像维护或总结自动删除过去日记。
