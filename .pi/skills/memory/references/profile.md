# 个人画像

## 什么时候更新

画像保存具有跨会话价值的稳定偏好或长期背景，不是每日工作记录。只有用户明确要求提炼、整理、修改或删除画像/长期偏好时才生成写入候选：

- 用户明确表达长期偏好并要求记住其长期作用，例如以后学习新概念先看实例。
- 用户明确纠正旧偏好，或要求清理过期、重复画像。
- 用户要求从指定日记或会话提炼画像，反复出现的行为可作为推测候选，但必须展示依据并让用户确认。

“保存今天的工作”“总结这个月”、一次选择、临时要求或项目技术决定都不触发画像更新；不因为出现疑似偏好就顺带提取或在收尾反复询问。用户说“今天只看结论”不等于长期喜欢简短，“本项目选用某数据库”也不是全局偏好。

## 读取与适用范围

普通任务开始时主动判断哪些偏好会影响当前回答或操作，不需要用户手动查询，也不依赖当轮出现“偏好”等关键词。固定领域为 `communication`（交流表达）、`coding`（编程）、`learning`（学习）和 `workflow`（协作流程）；按实际任务选择相关领域，不因进入项目就读取全部画像。

已加载的适用偏好及其条件仍在当前上下文、没有变化迹象时直接复用，不每轮重新查询。确有缺口时用 `profiles --domain <相关领域>` 取得必要内容；新任务、恢复会话、目标或环境变化、用户提示偏好更新时，只刷新受影响部分。只有文件路径或未成功读取的结果不能当作已经取得偏好。

作用域为 `global`、`domain:<id>`、`project:<project_id>`。工具按领域返回，Agent 再筛选当前适用作用域，不编造作用域过滤参数；项目作用域使用真实项目 ID，未确认归属的条目不能当作当前项目偏好。项目临时约束不能提升为全局偏好。用户当前明确要求优先于历史画像，实质冲突先核实，不静默改写。

取得足以支持当前任务的适用偏好后停止，不追读无关领域或日记来源；需要核实某条依据时才回溯来源。不常驻全部条目、不另建“核心画像”副本，也不从日记临时推断新画像来补齐读取结果。读取及采用偏好不授权画像更新，写入仍按下述候选与确认流程处理。

## 候选与确认

1. 先查询相关领域，检查重复、相反描述和适用条件。原画像已正确表达时不重复新增。
2. `basis:explicit` 表示用户明确表达；`basis:inferred_confirmed` 表示从材料推测且用户已确认。不能把未经确认的推测作为事实提交，也不因出现次数多就认定是永久偏好。
3. 有日记依据时填写真实 `source_record_ids`，只依赖当前可见或实际读取材料，不编造来源。来源可以是历史日记，不要求仍是当前规则。
4. 更新旧偏好时，用 `replace_profile_ids` 指定同领域旧条目，预览完整旧正文、新正文、依据及作用范围。仅确认日记或技术方案不构成本次画像确认。
5. 通过 `plan profile --input -` 生成候选，再取得对该份具体计划的确认，最后提交。候选或库变化则重新预览。

## 生命周期与隐私

画像更新只改变画像条目，不删除历史日记或旧偏好证据，也不因此撤回历史月度回顾。旧画像可以被替换，过去日记仍如实保留“当时表达了什么”。

用户明确要求删除日记来源时，脚本会预览并清理画像中的悬空来源 ID，但不自动删除仍经用户确认的画像正文；是否忘记偏好由用户明确要求决定。

不主动存账号口令、令牌、认证信息或无必要的敏感个人属性。不把模型的泛化标签、性格猜测、一次错误或短期情绪写成长期身份。
