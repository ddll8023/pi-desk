# 月度工作回顾

## 触发与范围

只在用户明确要求月度总结或重建摘要时执行，不在月末后台自动运行，不因普通历史查询缺少摘要就顺带生成。

正式月度摘要要求月份已经结束；本月最后一天只有用户明确确认当天记录结束才允许。此时读取 `month-source` 使用 `--closed-today-confirmed`，生成计划使用 `closed_today_confirmed:true`。其余未完结情况不得冒充完整月度回顾。

默认范围是该月日记里的所有项目与非项目事项，不只读取 `general`。用户明确限定项目时按其真实 ID 分批读取；不扫描项目本地知识或其他会话来补造工作史。

## 来源收集

1. 调用 `month-source YYYY-MM --offset 0 --limit 50`。如需限定项目再传 `--project <id>`。
2. 返回 `has_more=true` 时，按 `next_offset` 继续，直到覆盖指定范围。不能只凭第一页或近期30天窗口总结整月。
3. 来源包含当月旧决定及其后续被替代状态。回顾应描述当时发生的决定及当月变化，不因今天的新决定把过去工作改写为没有发生，也不把历史版本当作今天的约束。
4. 只有已有摘要没有原文时，明确资料覆盖边界；不能宣称已读取完整日记。无来源时不生成虚构总结。

## 归纳内容

按项目 → 工作主题组织，优先回答：做了哪些事、得到什么结果、作出了什么决定、哪些问题反复出现、哪些事项未完成。讨论、尝试和实际完成分开；不把“计划做”写成“已完成”，不捏造工时、提交数、测试通过或量化收益。

不是把每天逐条拼接成流水，也不是只提炼几条通用原则。可迁移方法可以作为有证据的附加认识，但不是月度总结的全部，也不自动成为新规则或画像。

每个主题引用当月同项目的真实 `source_record_ids`。项目知识可以作为明确指出的解释线索，但不能替代当月日记来源；不在总结时顺带维护项目文件。

## 预览与确认

- Agent 根据来源组装 `groups`，调用 `plan month --input -` 生成完整预览，不让用户手工填写 JSON。
- 展示全文、范围、来源覆盖及必要的不确定性。引擎的 `source_total`、`source_used`、`source_uncovered_ids` 按整月记录计算；仅总结一个项目时解释范围外 ID，低价值细节可不引用，但不能隐藏重大遗漏。
- 已有摘要须明确 `rebuild_existing:true`，展示覆盖内容并重新确认。
- 只在用户确认该份具体计划后提交；来源变化或计划过期则重新预览，不盲目重试。

## 与原文及画像的关系

摘要是可重建的回顾，不替代或清理日记。后来的新决定仅改变旧记录有效性，旧月份原始正文和历史摘要继续保留；真正删除日记来源会撤回关联月份摘要，新增日记进入已整理月份也需重新整理，脚本会在计划中列明。

记录日记和生成月度总结都不更新个人画像。用户另外要求提炼或维护画像时，按 `profile.md` 生成独立候选，展示依据并确认后保存。通用经验保存和项目知识维护也分别遵守自身范围，不能借总结确认自动写入。
