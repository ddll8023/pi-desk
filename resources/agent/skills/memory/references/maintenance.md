# 过时记忆的维护审查

用户要求审查过时记忆、清理流水式记录，或维护中发现记录与当前事实冲突时使用。单条保存与状态规则以 [日记保存](save.md) 为准，数据边界与删除见 [数据边界](integrity.md)。

## 触发

- 用户明确要求审查、清理或整理过时记忆、流水式记录。
- 维护中发现某条记录与当前代码、文档或已确认决定冲突。
- 保存前核对现行规则时，发现同键旧版本已失效但尚未替代。

时间久、读取次数少、库体积大都不是审查理由，不自动触发。

## 候选来源

维护只处理下列来源，范围由用户确认：

1. 用户点名的记录 ID、主题、项目或时间范围。
2. `memory_rules` 返回的生效规则清单，可按族或项目收窄。
3. 已有 `memory_search` 命中的记录；需要远期细节时改用 `records` 并 `memory_read` 取全文。

工具不提供按 `type` 或 `status` 枚举全库的入口，无法列出全部 `active` 的 `progress` / `issue`。不要声称已做全库审查；需要更大覆盖时说明缺口，请用户给定范围或主题。

## 判定与证据

每条记录给出一个结论：

| 结论 | 判据 | 处置 |
| --- | --- | --- |
| 仍有效 | 与当前代码、文档或已确认决定一致，且仍会改变后续判断 | 保留 `active` |
| 已过时 | 有证据表明功能已移除、方案已被替代、问题已解决或事实已变化 | 关闭或替代 |
| 无法判定 | 读到的材料不足以确认现状 | 保留 `active`，列出缺少的证据 |

证据只能来自实际读取的代码、文档、测试、后续记录 ID 或用户确认。不根据标题、日期或推测判定；日期只用于排序候选。

## 处置

| 记录情况 | 处置 |
| --- | --- |
| 未决状态已完成或已失效 | `status_updates`：`progress` → `archived`，`issue` → `resolved` 或 `archived` |
| 流水式且没有可复用结论 | 直接 `archived`，不提炼 |
| 流水式但含可复用结论 | 按 [日记保存](save.md) 的文风提炼新记录：结论 → 理由或证据 → 适用条件 → 下一步 |
| 规则类已失效 | 用新记录承载替代结论并给 `supersede_record_ids` 与理由；没有可提炼结论时说明缺口，不用状态更新冒充关闭 |

改写要求：

- 原记录仍按原状态归档，新记录只承载提炼后的结论；不把流水原文改写成 `decision`。
- 新记录用 `source_record_ids` 指向原记录。
- 提炼为 `decision` / `constraint` 时给正确的 `rule_key`，并核对是否会被引擎按同键自动替代同项目旧规则；不为省事复用不相关的键。
- 一次提交可同时包含 `records` 与 `status_updates`，执行顺序由引擎处理。

## 提交与汇报

- 先逐条列出原状态、建议状态、判定结论与证据，集中确认后生成计划；不逐条弹确认，也不批量自动执行。
- 按回执逐条报告记录 ID、原状态 → 新状态与理由；新建记录给出新 ID，以及被关闭或被替代的原记录。
- 引擎只写 `status`，不保存 `reason`，关闭后无法从库内回溯理由；关闭时须在同批保存承载结论的记录，并在汇报里保留理由。
- 计划失败或库忙时停止，不重试，不拆成多批盲目提交。

## 边界

- 不删除记录；纠错与忘记按 [数据边界](integrity.md) 单独提交删除计划。
- 不按时间、条数或读取次数批量关闭，不把“很久没读到”当作过时。
- 不扫描其他 Agent 会话或其他项目目录补造工作史；候选必须能在库内找到真实 ID。
- 不改写历史正文，不改项目归属，不越过用户确认执行。
