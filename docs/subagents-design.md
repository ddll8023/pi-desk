# pi-desk 子代理模块初步设计

本文用于明确需求、范围、调研结论、架构职责、关键取舍与开发阶段方向，不是实现规格或开发授权。具体文件改动、协议字段、依赖选型与实现常数，在对应开发阶段结合项目事实讨论。

## 1. 目标与需求来源

### 1.1 用户明确提出的需求

- 面对调查、修改文档、审查等任务时，可以采用子代理，不要求所有这类任务都必须委派。
- 主代理实际调用子代理后，页面能够动态显示子代理的存在。
- 用户能够直观看到各个子代理的具体工作内容，而不只是最终结果或一个没有说明的运行指示。
- 文档先行：先形成设计文档，不直接进入业务实现。

### 1.2 推荐设计，不等同于用户逐项确认的需求

- 采用主代理委派、子代理独立执行、主代理汇总的协作方式，不交接主对话控制权。
- 基于项目现有 Pi SDK，提供内置委派工具、主进程子任务管理、独立 SDK 子宿主、结构化活动投影和专用 Vue 展示。
- 首版支持单任务与一批并行任务；主代理等待该批结果后继续工作，页面在等待期间持续展示真实活动。
- 调查、审查默认只读；文档修改仅在用户已授权范围内，通过受限编辑能力执行。
- 使用主对话内的子任务卡与可展开详情，不为每个子代理自动创建普通聊天标签。
- 完成记录可回看，但不把查看历史等同于恢复执行。

### 1.3 目标

- 让用户知道主代理委派了什么、交给了谁、目前在做什么以及任务是否真正结束。
- 将独立调查与审查的过程留在子任务上下文中，避免主对话被大量搜索结果和工具输出占满。
- 让子任务的归属、授权、取消、异常和用量有明确所有者，不出现界面已经结束但执行仍在继续的假象。
- 在现有桌面架构中形成边界明确的内置能力，而不是引入另一套通用代理平台。

## 2. 当前项目事实

以下事实来自当前源码或项目记忆，描述现状，不代表必须原样保留的产品需求。

- 项目采用 Electron、Vue 3、TypeScript 和 Pinia，依据 `package.json`。
- 会话执行由 SDK 宿主承担；内置扩展工厂、会话创建、订阅和失效处理集中在 `src/sdk-host/session-runtime.ts`。
- 主进程在 `src/main/sessions/sdk-host-manager.ts` 监督 SDK 宿主，运行身份、绑定代际和会话占用由 `src/main/sessions/session-run-registry.ts` 统一登记。
- 现有宿主与页面契约围绕会话运行实例建立，`src/sdk-host/protocol.ts` 和 `src/shared/runtime-api.ts` 尚未提供完整的父子任务归属与子任务展示契约。
- `src/sdk-host/projection/tool-projection.ts` 将工具事件转换为有界展示条目；普通工具更新主要保留文本，不保留任意结构化结果详情。生成式 UI 载荷有单独识别逻辑，不能据此认为子代理详情已经能够透传。
- `src/renderer/src/sessions/components/ChatMessageItem.vue` 逐项渲染思考块和工具调用；相邻普通工具归入执行记录面板，面板内每条仍是独立工具卡，生成式 UI 使用专用渲染分支。
- `src/sdk-host/extension-ui-bridge.ts` 已有可取消的选择、确认、输入与编辑交互桥，但现有交互不自动具备子任务来源语义。
- `src/main/trust/trust-manager.ts` 明确只管理项目资源信任，不提供 OS 沙箱或工具权限限制。
- `src/shared-process/runtime.ts` 支持加载受管 SDK 运行时，因此实际 SDK 可能不同于编译期依赖；不能只根据依赖声明推断运行能力。
- 项目记忆 `.agents/memory/topics/conventions/multi-session-scope.md` 明确：独立宿主只隔离进程与运行身份，同项目会话仍访问共享工作目录，不提供文件隔离、自动冲突解决或自动恢复全部运行任务。
- 项目记忆 `.agents/memory/topics/conventions/projection-limits.md` 与当前 `ChatMessageItem.vue` 一致：Thinking 与工具调用逐项展示、各自开合，只有相邻工具调用归组。

## 3. 调研结论与方案取舍

### 3.1 Pi 官方子代理示例

来源：[官方示例目录](https://github.com/earendil-works/pi/tree/main/packages/coding-agent/examples/extensions/subagent)。调研同时读取了本地随包示例的说明与源码。

示例提供单任务、并行任务与串行任务链，通过独立 Pi CLI 子进程执行任务，将消息、用量和结果详情回传给父工具，再由终端渲染器展示。

可采纳的思路：

- 子任务使用独立上下文。
- 主代理通过工具委派，结果返回主代理，而不是替换主对话代理。
- 多个子任务分别维护活动和结果。

不直接照搬的部分：

- 示例的终端渲染器不能直接变成 Vue 页面。
- 启动逻辑依赖 CLI 运行环境，不能将桌面 SDK 宿主当成 CLI 原样再次启动。
- 所读源码主要在消息结束时推送展示更新，不能把其“流式展示”描述等同于逐字展示全部执行过程。
- 示例把较多子任务内容放在工具详情里；当前桌面投影不会自动保留这些结构，也不宜反复整量传输不断增长的记录。

Pi 官方将子代理作为可扩展能力提供示例，不是桌面端可以直接调用的完整内核模块。

### 3.2 社区 pi-subagents

来源：[项目说明与源码](https://github.com/agrigoryan/pi-subagents)。调研读取了说明与扩展入口源码。

可借鉴有界任务、并发调度、活动更新节流、独立记录与用量归集。其后台作业机制也说明：任务返回句柄之后，结果收集、取消与用量记账会形成新的生命周期，不能视为普通等待的简单替换。

其说明将 SDK 后端标为实验性，并明确该路径不保留扩展安全钩子。因此不能假设复用模型能力就等于继承父代理的授权和安全约束。

本项目仅参考机制，不直接引入该扩展作为依赖，也不将其默认任务数量、预算或资源策略作为产品要求。

### 3.3 持久化 pi-subagent

来源：[项目说明](https://github.com/badlogic/pi-subagent)。

该方案通过 tmux 承载独立持久子会话，提供状态查看、追加消息、等待、停止和直接接管。

可借鉴稳定任务身份与独立可观察记录，但 tmux 与终端接管不适合作为当前桌面内置模块的默认底座。持久复用代理和持续追加工作也超出本次首版范围。

### 3.4 Claude Code、Codex 与 OpenAI Agents SDK

来源：

- [Claude Code 子代理](https://code.claude.com/docs/en/sub-agents)。
- [Claude Code 桌面交互](https://code.claude.com/docs/en/desktop)。
- [Codex 子代理](https://developers.openai.com/codex/subagents/)。
- [OpenAI Agents SDK 的 Agents as tools](https://openai.github.io/openai-agents-python/tools/#agents-as-tools)。
- [Anthropic 多代理研究系统工程经验](https://www.anthropic.com/engineering/multi-agent-research-system)。

这些资料共同支持以下方向：

- 主代理保持需求、决策和最终交付职责，将独立工作委派给子代理。
- 独立上下文承载过程噪声，主代理接收结论和必要证据。
- 主对话中的活动入口与单个子任务详情分开，用户能够追踪子任务而不被全部日志淹没。
- 子代理流式事件必须保留代理与调用关联，不能假设父代理事件流会自动包含全部子代理活动。
- 明确任务目标、信息范围、产出和不做项，减少重复调查与遗漏。
- 读多写少、可独立拆分的任务更适合并行；并行写入增加协调成本。

这些是方案依据，不是当前项目的性能或成本测量结果。不能据外部案例承诺一定更快、更便宜或质量更高，也不因此引入其他代理 SDK。

### 3.5 推荐技术路线

推荐：产品内置委派工具，由主进程统一管理子任务，每个子代理在独立 SDK 子宿主中执行，页面通过结构化活动投影展示。

理由：

- 延续现有宿主监督与运行身份架构，避免建立一套脱离桌面的进程管理方式。
- 子任务拥有独立故障域，便于分别处理取消与异常。
- 执行事实、页面展示和历史记录可以分开管理，不依赖终端组件或模型生成界面。

代价：增加子进程开销，并需要补齐父子归属、事件转发、资源释放和记录管理。

同一宿主内创建多个 SDK 会话可减少进程开销，但共享故障域，面对不配合取消的代码也难以单独强制收敛，因此保留为简化候选，不作为默认方向。

直接安装现成子代理扩展虽然更快获得 CLI 委派能力，但仍然需要重做桌面展示和生命周期接入，不能作为完整替代。

## 4. 首版范围与不做项

### 4.1 纳入首版

- 单个子任务与一批并行子任务。
- 调查、审查，以及用户已授权范围内的文档修改。
- 主对话中的动态子任务入口、状态、最近活动、可展开详情与最终结果。
- 分任务取消、父任务取消及父会话关闭时的子任务收敛。
- 已完成或中断任务的记录关联与历史回看。
- 子任务用量展示和整体用量的单次归集。

调查、文档、审查先作为任务模式，而不是一套必须由用户配置的人设或团队。

### 4.2 不纳入首版

- 子代理递归创建子代理。
- 代理互聊、团队消息总线、通用工作流平台。
- 委派工具返回后仍脱离当前父任务运行的独立后台作业。
- 持久子代理的反复追加工作、接管为普通聊天会话或自动续跑。
- worktree 隔离、OS 沙箱与自动文件冲突解决。
- 代理市场、角色配置中心、资源监控面板或专门的进程池。
- 为展示当前工作而额外调用模型生成进度描述。

“主代理等待结果”不等于子代理只能串行执行：一批子任务可以并行，页面也可以实时更新，只是主代理在该批委派返回之后再继续汇总。

## 5. 架构与职责

### 5.1 主代理与委派工具

主代理判断任务是否值得拆分，提供明确目标、必要背景、允许范围、产出和不做项，并负责评估与整合结果。

委派工具是主代理访问子任务能力的入口，不是另一套最终交付通道。它不能根据模型自己填写的任务文本扩大权限。

每次委派应提供自足的任务说明与必要引用。默认不复制整个主对话，也不能假设子代理已经读过主代理读过的文件。

### 5.2 主进程子任务管理

主进程是运行身份和父子归属的权威来源，负责：

- 将子任务固定关联到发起它的父会话、父任务与归属项目。
- 管理派发、排队、取消、宿主退出和异常收敛。
- 防止切换前台项目或会话后，旧任务的事件与操作命中新对象。
- 将在途子任务纳入父会话关闭、资源释放和空闲判断。

子任务不是普通前台会话，不应因为复用宿主能力就自动进入会话侧栏、切换前台或新开聊天标签。现有运行身份规则应继续成立，具体接入方式在开发阶段确定。

### 5.3 独立 SDK 子宿主

子宿主创建独立任务上下文，执行允许的能力，报告真实活动、结果与用量，不直接控制页面，也不替主代理向用户作最终交付。

默认沿用派发时父代理选定的模型；父代理之后切换模型，不追改已运行的子任务。是否开放单独模型配置留待对应开发阶段讨论，不预设廉价模型适合所有调查或审查工作。

任务所需的供应商能力、安全扩展和资源必须明确装配。不能把“禁用全部扩展”当成安全收窄，因为它也可能移除必要的安全钩子或供应商能力。

### 5.4 活动投影与同步

活动投影负责将真实执行事件转换为可校验、可关联的页面状态与详情。

- 状态和活动摘要依据真实事件，不从模型的一段文字推断完成状态。
- 需要重同步时能够提供当前快照，而不是要求页面完整收到过去所有增量。
- 活动摘要有界，长输出和历史记录按需读取，不反复整量回传。
- 子任务活动与主代理消息保持各自身份，不将子代理事件直接混入父会话投影。
- 子代理结构化活动使用专用契约，不借用生成式 UI 载荷管理执行状态。

Pi 的嵌套工具调用与独立子代理不是同一个概念；能够执行嵌套工具，不代表已经拥有独立模型上下文、父子会话管理或子代理事件转发。

### 5.5 Vue 子任务视图

页面负责动态卡片、任务组、单任务详情、结果入口和停止操作。既有 Markdown 与工具展示能力可以复用，但页面不决定工具权限，也不以组件卸载判断任务结束。

界面风格沿用当前产品，不引入第二套视觉规范或由模型自由生成的执行面板。

### 5.6 记录管理

主会话保存关联、摘要和结果入口，子任务的必要详情独立保存。运行身份与持久记录身份需要区分，不能用仅在进程内有效的身份充当历史定位依据。

记录管理负责访问边界、主会话分支关联、缺失记录的降级和删除语义，不默认永久保留全部输出。

## 6. 工作过程与展示

### 6.1 一次委派

- 主代理提供任务说明与必要背景。
- 主进程登记父子归属，页面立即显示任务卡；排队任务不能提前显示为运行中。
- 子宿主开始工作，页面分别显示各子任务的实际活动与可展示输出。
- 每个子任务独立收敛，完成一个就更新一个，不等待整批完成才展示结果。
- 一批任务收敛后，主代理接收结论、证据、失败和未决事项，再形成最终答复。

单个失败或被取消不应伪装成整批成功，也不要求丢弃其他已完成任务的结果。

### 6.2 主对话中的轻量入口

在发生委派的位置出现任务组；单任务可以采用相同结构的简化展示。

默认能够看出任务职责、当前状态、最近真实活动和整组完成情况。卡片始终能够识别具体任务，不能只显示无法区分的“Agent 1”“Agent 2”而没有工作说明。

不显示缺乏依据的进度百分比；状态变化也不应反复抢占用户正在阅读的位置。

### 6.3 单任务详情

展开后展示：

- 主代理交给它的任务、边界与必要背景。
- 按执行顺序排列的实际工具操作及其相关文件或来源。
- 适合展示的参数、输出、变更信息和明确的错误。
- 最终结论、证据与未解决事项。

“工作可见”依靠真实执行记录和可展示输出，不要求暴露模型内部思考。长输出发生截断时必须说明省略范围；敏感信息不应因为可观察性需求而被无差别传播。

### 6.4 状态表达

界面需要区分等待派发、执行中、等待必要用户交互、已请求停止以及真实终态。终态应区分完成、失败和中断，不能将所有结束都写成成功。

这些是用户可见语义方向，不在本文锁定协议枚举或内部状态机。

## 7. 授权与安全边界

### 7.1 用户授权不能由委派文本替代

主代理只能委派用户已允许的工作。子代理不能自己扩大范围、增加工具或修改授权策略；主代理也不能用一次自然语言回复静默代替用户批准新增操作。

需要新增写入或其他未授权动作时，应暂停并说明来源任务、目标与影响。必要交互可以复用现有桌面确认能力，但必须关联原子任务；交互不可用或回应身份不匹配时不能继续执行。

### 7.2 只读任务的能力约束

调查和审查默认只读。只读不是一段提示词，也不是给工具打一个名称标签：

- 不默认提供任意 bash、可写 MCP 或其他能够旁路修改文件的能力。
- 必要检索能力及其资源范围需要明确选择。
- 未知能力不能仅凭“调查任务”这一名称被认定安全。

具体能力集合与约束入口留到开发阶段讨论，不能假设新建 SDK 会话后会自动继承父代理全部安全行为。

### 7.3 文档修改

文档修改是首版需求的一部分，不应通过永久只读化把它排除。

- 仅使用用户已授权的目标范围，不能让模型自行填写任意路径即获得写入能力。
- 实际编辑能力承担路径边界约束，不能只在提示词里要求“只改文档”。
- 同一文件的修改串行，避免并行读改写覆盖。
- 写入失败、中断或结果未知时如实报告，不自动重试可能已经生效的操作。

### 7.4 不承诺的安全能力

Project Trust 是项目资源加载的信任决定，不是逐任务写入授权。

独立宿主是进程与故障域隔离，不是文件隔离或 OS 沙箱。工具边界用于约束受信任 SDK 和扩展环境中的模型调用，不能防御恶意扩展代码或承诺阻止所有外部进程副作用。

## 8. 生命周期与异常

- 切换标签或项目不停止子任务，也不改变归属；切回时通过快照补齐当前状态。
- 单独停止一个子任务，不直接中止其他子任务或整个父会话。
- 停止整轮或关闭父会话时，收敛对应范围内的在途子任务和必要用户等待，不遗留脱离所有者的执行。
- 停止请求与停止确认分开。宿主退出未确认时保留登记，不提前宣称任务已经结束。
- 子宿主异常退出时保留真实失败或中断信息及已有结果，不把子任务异常自动等同于父宿主失效。
- 正常完成应依据 SDK 的真实收敛边界，不能把一次低层 agent 结束事件或暂时没有新输出当成全部工作结束。
- 不默认自动重试写入任务，不在应用重启后自动恢复执行。
- 结束任务的资源需要释放，历史查看不依赖保持子宿主常驻，也不为此引入进程池。

## 9. 上下文、记录与用量

### 9.1 上下文

主代理提供必要背景与引用，子代理独立收集执行所需信息。主代理只接收结论、必要证据和可追溯记录入口，不默认重新消费完整子日志。

任务拆分应避免重复劳动，也不适合把强依赖同一上下文、需要频繁来回讨论的工作强行分给多个子代理。

### 9.2 历史与分支

- 主会话保存的子任务关联应尊重当前对话分支，不能把其他分支的任务显示成当前分支新发生的工作。
- 完整记录独立于主会话模型上下文；页面摘要收缩不等同于删除原始记录。
- 回退对话不撤销已经发生的文件修改，也不自动重放历史子任务。
- 应用重启后，历史记录不能被当成仍在执行；对于没有完整终态的记录应如实表达中断或未知情况。
- 记录缺失或已清理时，保留可用摘要并明确提示，不伪造完整详情。
- 记录可能含敏感文件内容和工具输出。存储访问边界、保留策略及与主会话删除的联动，需要在记录管理开发阶段明确。

### 9.3 用量与资源

- 子任务分别展示已知用量，整体总量只归集一次，不能既计入父工具又再次重复相加。
- 中断、异常退出或供应商信息缺失时保留不完整状态，不以零值表示确定没有消耗。
- 并发与任务投入应受控，但本文不预设固定代理数、超时或预算。
- 额外模型请求、独立上下文和子进程都会增加成本；并行可能减少等待，但不保证总消耗下降。

## 10. 统一问题清单

以下是调研与静态分析发现的设计缺口和资料冲突，不代表这些问题已修复。每项仅给出一个推荐处置方向，具体实现归对应开发阶段。

### 10.1 子任务结构无法直接进入现有展示链路

- **位置**：`src/sdk-host/projection/tool-projection.ts`、`src/shared/runtime-api.ts`。
- **证据**：工具更新主要提取文本，普通结构化详情不会作为子任务数据保留，生成式 UI 只有专用识别逻辑。
- **影响**：直接安装现成子代理扩展不能自动出现任务组与分任务工作详情。
- **推荐处置**：增加受校验的子任务展示契约，分开实时活动、摘要与历史详情，不借用生成式 UI 管理执行状态。

### 10.2 现有身份与生命周期缺少父子关系

- **位置**：`src/main/sessions/session-run-registry.ts`、`src/main/sessions/sdk-host-manager.ts`、`src/sdk-host/protocol.ts`。
- **证据**：现有机制统一管理普通会话的运行身份、绑定和宿主，没有完整的子任务归属与父级取消关系。
- **影响**：子任务自行启动会绕过桌面所有权，可能造成旧事件串线、父会话释放后仍执行或空闲判断失真。
- **推荐处置**：沿用主进程身份权威，补齐父子登记、在途状态、取消、过期事件隔离和退出未确认状态的收敛。

### 10.3 项目信任不能替代子任务授权

- **位置**：`src/main/trust/trust-manager.ts`、`src/sdk-host/session-runtime.ts`、`src/sdk-host/extension-ui-bridge.ts`。
- **证据**：Project Trust 明确不做工具权限限制；新子会话也不会自动获得父会话的完整安全装配和交互来源关联。
- **影响**：可能将“信任项目”错误解释为允许子任务任意写入，或在必要安全钩子缺失时执行。
- **推荐处置**：显式装配允许能力与必要安全资源，关联用户交互到原任务，未获授权或交互不可用时停止推进。

### 10.4 共享目录存在并行写入竞争

- **位置**：同项目共享工作目录；`.agents/memory/topics/conventions/multi-session-scope.md`。
- **证据**：独立宿主不提供文件隔离或自动冲突解决，多个会话仍操作同一份文件。
- **影响**：同文件并行修改可能覆盖结果；任意 bash 也能绕过只读提示。
- **推荐处置**：只读工作并行，文档写入使用范围受限的编辑能力，同文件读改写串行，不承诺文件隔离。

### 10.5 SDK 能力与子任务用量需要统一口径

- **位置**：`src/shared-process/runtime.ts`、`src/sdk-host/session-runtime.ts` 以及 Pi SDK 的工具用量契约。
- **证据**：实际加载的 SDK 可不同于编译期依赖；独立模型调用需要主动归集用量。
- **影响**：仅根据类型声明设计可能与运行能力不符，用量也可能漏计或重复计入。
- **推荐处置**：开发阶段按实际加载能力确定接入，并建立子任务用量单次归集与未知数据表达规则。

### 10.6 记录持久化带来体积与敏感信息问题

- **位置**：Pi 会话存储及拟新增的子任务记录职责。
- **证据**：完整子任务记录可能持续增长并包含文件正文和工具输出；反复放入父工具详情会放大传输和上下文负担。
- **影响**：增加磁盘占用、敏感信息保留和页面内存开销。
- **推荐处置**：独立记录、有界投影、按需读取，并在记录管理开发阶段明确访问边界和保留、删除语义。

## 11. 开发阶段方向

阶段描述仅确定目标与依赖，不是文件级执行清单，也不自动授权代码修改。

### 阶段一：只读单任务可观察闭环

- **目标**：形成委派、独立执行、真实活动展示、结果回传和记录关联的完整方向。
- **重点职责**：委派入口、子任务管理、SDK 子宿主、活动投影、单任务视图和基础记录。
- **开发时详细讨论**：实际 SDK 接入、身份边界、只读能力装配、事件同步、记录关联与资源释放。
- **交付方向**：单个调查或审查子任务可以被识别、追踪、结束并回看；不是将首版永久限定为只读。

### 阶段二：并行与生命周期

- **目标**：支持任务组和并行子任务，保持分任务状态、取消和归属一致。
- **依赖**：阶段一的执行、活动和记录边界。
- **开发时详细讨论**：共享并发约束、排队、部分失败、分任务取消、父会话关闭及在途子任务对资源回收的影响。
- **交付方向**：用户能够区分多个子任务的工作与结果，不因切换会话或部分失败丢失归属。

### 阶段三：受限文档修改

- **目标**：在已建立的执行与生命周期管理之上，支持授权范围内的文档编辑。
- **依赖**：前述任务管理、取消与结果表达；授权和记录边界在前两个阶段即需预留，不能事后仅补提示词。
- **开发时详细讨论**：授权目标的表达、路径约束、编辑能力、安全扩展装配、同文件串行与变更展示。
- **交付方向**：完整首版包含文档修改能力，不把它默认为范围外，也不扩展成任意代码修改平台。

## 12. 留待对应阶段确定的事项

- 允许能力、必要供应商与安全扩展的具体装配方式，以及无法安全表达时的拒绝行为。
- 主进程子任务管理与现有注册表、宿主监督之间的具体接入点。
- 活动投影与历史详情的协议结构、同步策略和展示上限。
- 子任务详情采用就地展开还是复用既有详情容器的具体布局；不改变主对话入口与分任务可见性。
- 持久记录的存储归属、保留策略、访问方式和主会话删除联动。
- 是否提供功能开关、单独模型配置或用户自定义任务模式；这些不是当前默认纳入的需求。
- 并发、时限、预算和资源释放的具体策略，不在初步设计中固定常数。

在这些事项完成对应阶段讨论并获得明确执行清单批准之前，本文只作为设计依据，不启动业务实现。
