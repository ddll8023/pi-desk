# 专家配置设计

本文是 pi-desk「专家」能力的初步设计：需求、配置存放方案、加载与校验、会话内生效方式、关键取舍、风险与阶段。本文不描述具体实现细节，不含字段级定义、文件清单、验证方案与推进条件；模块现状以 `docs/modules/` 为准，两者不一致时以模块文档为准。

## 1. 背景与问题

pi-desk 目前有两种可复用指令载体：随包与用户级的**技能**，以及四类**子代理**。技能回答「怎么做某件事」，子代理负责「把一段工作挪到隔离进程里做」，但缺少中间一层：**以固定身份、固定方法论、固定输出规范完成单点任务**。

缺这一层的结果是，每个会话都从通用助手的状态重新开始，专业方法只能靠用户每次粘贴提示词，或靠 `AGENTS.md` 承担本不属于它的角色描述。

本期要解决这一层：引入**专家**——人工配置、可内置也可自定义、在会话里召唤即在系统提示中加入一段角色指令并使用其引用的技能。

## 2. 名词约定

全文只用以下名称，不混用近义词。

| 术语 | 含义 | 代码/配置对应 |
| --- | --- | --- |
| 专家 | 一份人工编写的角色定义：身份、方法论、输出规范，外加对技能的引用 | 定义由 `src/shared-process/expert-definitions.ts` 解析，角色段由 `src/sdk-host/expert-role.ts` 装配 |
| 专家定义 | 专家在磁盘上的一份 Markdown 文件（声明段 + 正文） | `expert.md`，声明段取名称、简介、技能范围与 MCP 范围 |
| 专家目录 | 存放专家定义的目录，一个专家一个子目录，目录名即 id | 内置 `resources/agent/experts/`，自定义 `<agentDir>/experts/` |
| 内置专家 | 随产品构建分发、只读的专家 | `resources/agent/experts/<id>/expert.md`，经 `bundle.json` 的 `experts` 段声明 |
| 自定义专家 | 用户在产品 agent 目录下创建或编辑的专家，设置页内可新建、编辑、派生与删除 | `<agentDir>/experts/<id>/expert.md`，可增删改 |
| 新建 | 在设置页从空白开始创建一份自定义专家，与派生同为自定义专家的两条起点 | `<agentDir>/experts/<id>/expert.md`，不写 `derivedFrom` |
| 派生 | 从内置专家复制出一份自定义专家，之后两份独立演进 | `<agentDir>/experts/<id>-copy/expert.md`，定义里写入 `derivedFrom` |
| 召唤 | 在会话中选用某个专家，使其角色定义进入本次会话的系统提示 | 新建会话时选择，绑定随会话持久保存，首轮后锁定 |
| 角色段 | 注入系统提示的专家正文分段 | 与系统提示的分段机制同层（现有 `skill_guard` 段采用同一机制） |
| 能力范围 | 召唤该专家的会话里可用的技能与 MCP 服务器集合 | 由专家定义与默认能力基线合成，装配期生效（`src/sdk-host/expert-capability.ts`） |
| 默认能力基线 | 所有继承型专家共享的默认范围，设置页一处可改 | `<agentDir>/capability-defaults.json`，两个维度都用 `null` 表示不限制 |
| 技能可见集 | 某次会话里模型可用的技能清单 | 现有技能装配结果（`additionalSkillPaths` 与用户技能合并） |
| 子代理 | 由 `delegate_subagent` 派出的独立子进程 | `src/sdk-host/sub-agent/` |
| 专家团 | 多位专家分工协作完成一个任务 | 本期不做 |

## 3. 需求

### 3.1 已确认需求

1. **人工配置**：专家由人编写或编辑，设置页只提供字段与正文的文本编辑，不代写、不提供 AI 自动生成、不从历史会话自动沉淀。
2. **双来源**：除内置专家外支持自定义专家，两者在同一界面上并列可选。
3. **可派生**：允许从内置专家复制一份自定义专家再修改；内置专家本身保持只读。
4. **单点任务定位**：专家在单个会话内以固定身份执行任务，不扩展为多角色协作。
5. **专家不产生子代理调用**：专家与子代理是并列的两条执行路径，不组合、不嵌套。
6. **可在设置页创建与编辑**：除派生内置副本外，能从空白新建自定义专家，并在设置页内修改其身份、能力范围与正文；编辑范围不外扩到调用方式。
7. **能力范围可配置**：专家能收窄本会话可用的技能与 MCP 服务器；先在默认能力基线上继承，再按专家做增减，不必每次从零勾选。范围只减不增，不引入会话原本没有的技能、服务器或工具。

### 3.2 不做项及原因

| 不做 | 原因 |
| --- | --- |
| AI 自动生成专家、从会话记录自动提炼专家 | 与「人工配置」的明确要求冲突 |
| 自定义覆盖内置（同名覆写） | 用户无法判断当前生效的是哪一份，诊断与升级路径都会变复杂 |
| 并入 `desktop-config.json` | 方法论正文会退化为 JSON 字符串，手改、diff、审阅全部劣化 |
| 单独的 `experts.json` 集中清单 | 一份文件装所有正文，无法按专家单独分享与移动 |
| 项目级专家目录 | 项目级已由 `AGENTS.md` 与项目技能承担，再加一层优先级收益低、冲突面大 |
| 按专家收窄主会话工具集 | 工具集带权限面与失败代价，本期不做；本期只收窄技能与 MCP 服务器 |
| 专家内部嵌套子代理 | 团 → 成员 → 子代理会形成三层调度，取消、预算、归属都要跨层穿透 |
| 一次会话并存多个专家 | 多段角色指令互相稀释，主提示失焦 |
| 专家市场、版本、导入外部专家包 | 需要来源标记与信任边界，与本期「本地预设」定位不同 |
| 对话式 AI 生成或改写专家正文 | 与「人工配置」冲突；且要把模型调用嵌进设置页，成本与质量都不可控 |
| 专家分享链接与专家市场 | 分享需要云端账号、托管与新的信任面；本期跨机复用靠搬运数据目录 |
| 专家头像与其他附加素材 | 列表用名称、简介与来源标签已够识别；引入图片要新增格式校验与体积上限 |
| 本期实现专家团 | 团队的定义与执行语义需单独设计，见 §11 阶段五 |

## 4. 项目事实与依据

| 事实 | 出处 | 对设计的作用 |
| --- | --- | --- |
| 产品有自有的 agent 目录（便携态在 `data/` 下），共享目录只读且产品不写入 | `src/main/shared/pi-paths.ts` | 自定义专家有唯一可写落点，且随便携数据目录同步 |
| 随包资源由清单声明（扩展、技能、`subAgentOnly` 标记、必需工具），构建期打包只读 | `resources/agent/bundle.json` | 内置专家沿用同一分发形态，不需要新机制 |
| 技能装配为「随包非 `subAgentOnly` 技能 + 共享目录技能」，与用户技能同名时保留随包、剔除用户 | `src/sdk-host/product-resources.ts` | 专家同名冲突的处理方式可与之对齐，避免两套冲突语义 |
| 配置中心是单个带版本号的 JSON，可选字段缺省回退、临时文件加改名原子写入 | `src/main/config/desktop-config-store.ts` | 该范式适合开关与列表，不适合承载长文本正文 |
| 子代理只认固定任务类型，边界由进程参数强制，不递归、不注入父会话历史 | `docs/modules/sub-agent.md` | 专家不能借用子代理的隔离能力，也不能把角色传给子进程 |
| 系统提示支持分段装配 | `docs/modules/skill-guard.md` 所述 `systemPromptOptions.sections` | 角色段可加在同层，不需要新运行时 |
| 设置页专家分节目前只有列表、加载诊断、派生副本与删除，没有创建与编辑入口 | `src/renderer/src/experts/components/ExpertSettingsSection.vue`、`src/main/sessions/expert-files.ts` | 自定义专家在界面上只能从内置派生或手工建目录，本期要补的正是页面内的创建与编辑 |
| 专家标识与目录名同形，且已按该规则固定校验 | `src/shared-process/expert-definitions.ts` 的 `EXPERT_ID` | 标识即目录名，创建时确定后不可改；显示名称与标识是两个字段 |
| 技能装配入口是「随包非子代理专用技能 + 共享目录技能」的全量覆盖点 | `src/sdk-host/product-resources.ts` 的 `skillsOverride` | 技能收窄就在这里过滤；可见集同时是斜杠补全与 Skill 门禁的来源，三处不会漂移 |
| MCP 由内置扩展在会话启动时读 `mcp.json` 并连接，扩展接受 `loadConfig` 钩子 | `@earendil-works/pi-coding-agent` 的 `McpExtensionOptions`，经 `src/sdk-host/session-runtime.ts` 注册 | 会话级收窄可以在钩子里完成，不必改动用户配置文件 |
| 产品 agent 目录是主进程与 SDK 宿主都能读的共享位置 | `src/main/shared/pi-paths.ts`、`src/sdk-host/product-resources.ts` | 默认能力基线放这里两个进程都能读，不需要新增 IPC 到宿主的传递链 |

### 4.1 外部参考：WorkBuddy「我的专家」

WorkBuddy 是闭源商业产品，这里只对照官方文档描述的公开行为，不涉及任何实现。核实于 2026-11-12，来源见 `docs/开源项目参考/workbuddy.md`。

| 对方做法 | 采纳结论 | 本项目的处理 |
| --- | --- | --- |
| 我的专家作为独立入口，创建、修改、分享、删除集中一处 | 借鉴 | 并入现有设置页专家分节，不新开独立页面 |
| 对话式创建：进入创建对话，由内置专家管理工具引导配置，可逐步确认 AI 的分析结果 | 不借鉴 | 与 §3.1「人工配置」冲突；设置页只提供字段与正文编辑 |
| 配置项为头像与显示名称、人设身份、擅长领域、提示词 | 借鉴字段语义 | 落到已有的四类信息：身份、技能范围、MCP 范围、正文（§5.4） |
| 创建前须确定名称，创建后不可修改，改名称需重建 | 部分借鉴 | 标识创建后不可改（它同时是目录名与会话绑定键）；显示名称可改，因为本项目标识与展示名已分离 |
| 分享生成链接，被分享方拿到副本 | 不借鉴 | 需要云端托管与分享面；跨机复用仍靠搬运数据目录（§5.5） |
| 删除后不可恢复 | 借鉴 | 已有确认对话框；只删定义文件，目录里还有其他文件时整体拒绝 |

结论：借鉴「自定义专家在设置页内闭环管理」的产品形态与字段语义；不借鉴依赖云端账号的分享，以及由模型代写正文的创建方式。

## 5. 存放方案

### 5.1 布局

两类来源各一处目录，互不写入：

- **内置专家**：`resources/agent/experts/<id>/expert.md`，随构建暂存产出、只读、随版本升级。
- **自定义专家**：`<agentDir>/experts/<id>/expert.md`，可写，随便携数据目录一起迁移。

两者结构一致：一个专家一个子目录，目录名即专家 id，目录内放专家定义文件。目录结构留出附加资源的位置（头像等），本期不引入其他文件类型。

标识与目录名同形、按固定字符规则校验，因此**标识在创建时确定，之后不可改**；显示名称、简介、能力范围与正文都可以改。改标识等同于换一份专家，会让既有会话绑定失效，所以不提供重命名。

### 5.2 来源与优先级

- 两个来源合并成一份专家列表，每项标注来源，界面上可追溯。
- 内置专家只读，运行期不可修改、不可删除。
- 自定义专家可增删改。
- 不设「内置优先于自定义」的隐式覆盖，同名即冲突，见 §5.3。

### 5.3 冲突、派生与新建

- 自定义专家 id 与内置专家 id 相同，或与另一个自定义专家 id 相同：报冲突诊断，不静默取其一。
- 自定义专家有两条起点：**派生**从内置专家起步，**新建**从空白定义起步。两者落到同一个目录、同一种文件形态，区别只在是否带 `derivedFrom`。
- 新建时标识由主进程分配 `expert-<序号>`（顺延到未占用的编号），落盘前确认不与内置或其他自定义专家重名：中文显示名称无法转成合法标识，而标识创建后不可改，让用户手填只会填错。
- 派生流程：从内置专家复制正文到自定义目录，标识自动顺延为 `<内置 id>-copy`（占用时 `-copy-2`…），并在声明段写入 `derivedFrom` 指回来源；内置保持只读。
- 派生副本不跟随内置专家升级。界面上须标明该专家派生自哪个内置专家；是否已落后于内置版本由用户判断，不做自动合并。

这条取舍的代价是内置改进不会流到派生副本。不做覆写换来的是行为可预测与诊断清晰；如果将来出现大量派生副本落后于内置的情况，需要重新讨论覆写与合并策略。

### 5.4 文件形态

一个专家定义包含四类信息，不在此锁定具体字段：

1. **身份**：显示名称与一句话简介，用于列表与召唤时展示。
2. **技能**：本专家要使用的技能 id 列表，以及它相对默认基线的加减。
3. **MCP 范围**：本专家可连接的 MCP 服务器范围，同样继承默认基线并做加减。
4. **正文**：方法论、工作流程、输出规范——即真正注入系统提示的部分。

正文为空、或只有能力清单而没有正文的专家，视为无效定义（只带能力清单的专家退化为一个开关，失去引入这一层的意义）。

### 5.5 便携与同步

自定义专家位于产品 agent 目录内，随 `data/`（便携态）或用户数据目录一起迁移，不需要额外的同步通道。跨机器复用依赖用户自己搬运数据目录；本期不提供导出/导入。默认能力基线同在 `agentDir` 根下，跟着一起搬运，不单独同步。

### 5.6 默认能力基线与增量

两层：**默认能力基线**（全局一份，设置页可改）与**专家定义**（继承基线并做增减）。

- 基线每个维度只有两种形态：不限制（`null`，等于全部），或一份子集。没写过这份文件时两个维度都是不限制，行为与引入基线之前一致。
- 专家每个维度也有两种口径：**继承**（默认）与**仅用选中**。继承时只记录相对基线的 `Add` 与 `Remove`；仅用选中时列表本身就是完整白名单，与外层基线无关。
- 生效集 = 仅在选中模式下取白名单；否则 `基线 ∪ Add − Remove`。三者都为空时不限制，不把当时的清单固化成白名单，新装的技能与服务器仍能被继承。
- 基线只在召唤了专家时参与计算：没选专家的会话不读基线、不裁剪任何技能或服务器。
- 专家编辑界面每项只呈现勾选状态，行尾标出它是「基线默认」「额外启用」「已排除」还是「当前不可用」；勾选差异由页面自己翻译成 Add 或 Remove，用户不需要理解两套写法。默认能力基线不区分继承与白名单：只有一份勾选集合，勾满即等于不限制，保存时归一成 `null`。

| 议题 | 选择 | 代价 |
| --- | --- | --- |
| 基线放哪里 | 产品 agent 目录下的小 JSON | 不进桌面配置中心，需要自己保证原子写与容错读取 |
| 默认口径 | 继承（不限制） | 用户要“管住”专家时必须显式收窄；换来的是不改变任何现有会话 |
| 收窄维度 | 只做技能与 MCP 服务器 | 工具集仍全量可见，能力上限靠提示词与范围双重约束 |
| 能不能加回基线之外 | 能，以 `Add` 表达 | 需要同时处理加减与“仅用选中”两种口径的展示 |

## 6. 加载与校验

加载发生在会话装配前，产出「可用专家列表 + 诊断」。诊断沿用资源装配现有的方式：在界面上可见、按严重程度分级，不以一句「加载失败」掩盖原因。

需要覆盖的问题类型（不列具体校验实现）：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 结构类 | 目录名与声明 id 不一致、定义文件缺失、正文为空 | 该专家不可用，报诊断 |
| 引用类 | 引用的技能不存在、引用了子代理专用技能 | 专家保留，标记该引用失效 |
| 引用类 | 白名单里引用的 MCP 服务器在全局配置里不存在 | 专家保留，报诊断；项目级服务器因项目而异，不在这里判 |
| 冲突类 | 与内置或另一自定义专家 id 重复 | 冲突项不进入列表，报诊断并给出来源 |

核对原则：**能保留的保留，能标出来的标出来**。引用失效不应让整个专家消失，否则用户改不了、也看不到哪里错了。

一处必须显式拦截的引用：四类子代理专用技能只对子进程可见，不得被专家引用；引用时应报诊断而不是悄悄加载后又失效。

保存期校验与加载期诊断是两套口径，不合并：

- **保存时拒绝**：正文为空、标识写法不合法、与已有标识重复、引用了子代理专用技能、技能白名单为空。这些在写入前就能判定，直接不让落盘，并说明是哪一项不满足。
- **保存时提示但不拦**：引用了当前不可见的技能与 MCP 服务器、正文超过注入上限。用户可能先写引用、后补技能，拦下来会让编辑无法保存。
- **保存后重读**：写回成功即重读清单，新定义立刻出现在设置页；已打开的会话在新建时才重新装配，即下一次装配才读到新正文与新范围。

写回只动这一份 `expert.md`，声明段里本设计不认识的字段原样保留，避免把用户自己加的说明洗掉。

## 7. 会话内生效

### 7.1 召唤

- 一个会话同时只使用一个专家，切换专家等同换一个角色上下文。
- 召唤后把专家正文作为独立的角色段注入系统提示，与既有的其他提示分段并列，不改写用户级与项目级指令。
- 召唤在会话开始前完成，首轮后锁定：绑定随会话持久保存，重新打开或重启应用后仍然带着同一个专家；换专家需要新会话。
- 选择入口在输入坞的 ＋ 菜单里：菜单是双级结构，左列是分类行（添加图片、模型、执行模式、专家、技能、常用消息），右列是当前分类的二级面板。专家面板里直接列出候选项，「不使用专家」为首项，选中即生效；一级列不随专家数量变高，也把「已选哪个」与「有哪些可选」分开。
- 绑定的定义被删除或改名后，界面如实标出「已失效」并提示本会话不再注入角色，但不自动清除绑定——重建同名专家即可恢复，自动清理会把误删变成不可恢复。判定只在清单成功读到后进行，避免一次加载失败被误报成失效。
- 专家只在主会话生效，不写入会话历史，也不随会话记录转移到子进程。
- 在设置页改完正文、技能或 MCP 范围后，从下一次会话装配起生效（技能与 MCP 是创建期装配，已打开的会话要重开）：新建会话就按新范围装配，不打断当前轮；标识不可改，因此编辑不会让既有绑定失效。绑定失效只可能来自定义文件被删除，或目录被手工改名。

### 7.2 技能与 MCP 可见集

技能与 MCP 服务器都受能力范围控制，工具集不受影响。

- 技能：范围由默认能力基线与专家定义合成。范围外的技能不进会话可见集，斜杠补全、Skill 门禁与提示里的技能清单同时跟着变，不会出现“界面能选、模型看不到”。
- MCP：范围外的服务器在会话启动时标记为停用，不连接、不起子进程、不读凭据；它们在 `/mcp` 里仍列出来，让人看得出是被当前专家排掉的，而不是配置丢了。
- 只减不增：专家引用会话环境里没有的技能或服务器时只产生诊断，不会凭空装配出新能力，也不构成新的信任面。
- 收窄是装配期决定：改完要新建会话才生效；已打开的会话按打开时的范围继续运行。角色段会说明本次的实际范围，避免模型把没加载的能力当成可用。

### 7.3 不改变的边界

- **工具集不变**：专家不增删工具，不改变工具白名单与预算口径；技能与 MCP 范围的收紧不等于减少工具。
- **不产生子代理**：专家正文不得包含委派指令，专家定义也不接受与委派相关的配置；子代理侧不认识专家，不加载专家正文。
- **不改变权限与信任**：专家正文与用户自己写的技能同源，不构成新的信任面，也不绕过任何既有确认。

### 7.4 上下文影响

角色段会占用系统提示空间。单专家不叠加，是控制这一成本的主要手段；正文超过注入上限时在前段截断并在尾行说明，定义文件本身不被改写，也不因此报诊断——规则收紧不能让已在用的定义突然失效。上限量与截断判断只有一个来源，主进程视图与宿主角色段共用同一口径；设置页列表与输入坞选择器都标出「已截断」，用户能看出后面那段没进去。

## 8. 与相邻能力的分界

| 能力 | 回答的问题 | 执行位置 | 与专家的关系 |
| --- | --- | --- | --- |
| 技能 | 怎么做某件事 | 主会话（子代理专用技能除外） | 专家可引用技能，但不能内联技能正文 |
| 子代理 | 把一段工作挪到隔离进程里做 | 独立子进程 | 与专家并列，不组合；专家不派子代理，子代理不认识专家 |
| 专家 | 以谁的身份、用什么方法、按什么规范交付 | 主会话 | 本期唯一新增层 |
| 专家团 | 多角色如何分工协作 | 主会话层多角色（另行设计） | 本期不做；团成员是会话级角色，不在子代理层 |

## 9. 关键取舍

| 议题 | 选择 | 代价 |
| --- | --- | --- |
| 存放形态 | 文件化专家目录，两类来源各一处 | 需要新增资源类型与加载校验，不能复用配置中心的字段回退 |
| 同名处理 | 复制派生，不覆写 | 派生副本会落后于内置升级 |
| 作用域 | 只做全局（内置 + 用户级） | 无法为单个项目定制专家，需靠项目指令与技能补 |
| 生效方式 | 系统提示注入 + 技能与 MCP 范围 | 工具集与预算不变，能力上限仍等于单会话上下文 |
| 范围配置 | 默认基线 + 专家增量 | 改基线会同时改掉所有继承型专家，需要界面明说影响面 |
| 与委派的关系 | 完全解耦 | 需要并行或上下文隔离的任务必须走子代理，专家帮不上 |
| 创建方式 | 表单式填写，不由模型代写正文 | 用户要自己写方法论；换来的是与「人工配置」一致、无模型调用成本 |
| 编辑形态 | 设置页内按文本编辑，不复用外部编辑器 | 写回要自己保证格式与未知字段保留；换来的是新用户不必找目录 |
| 标识稳定性 | 标识创建后不可改，显示名称可改 | 名称与标识可能不一致，界面要同时展示；换来的是会话绑定不被编辑打断 |
| 可见性 | 一次会话一个专家 | 无法在一次对话里让多个角色交叉发言 |

## 10. 风险与可行性限制

1. **执行层没有「角色」概念**。现有系统提示装配可以承载分段，但「选中的专家是谁」需要在会话生命周期里被记录与传递；这一条不落地，召唤只是把一段文字塞进提示，界面上无法回显。属本期主要工作，不是纯配置问题。
2. **专家能力偏薄**。因不派子代理、不改工具集，专家只能改善方法与人设，不能缩短长任务、不能隔离噪声。若产品表达暗示了后者，会造成预期落差。
3. **派生副本漂移**。见 §5.3。
4. **专家团缺席导致概念不完整**。只有专家这一层时，用户可能把「多角色协作」的期待压到专家身上；界面与文案须明确当前只支持单一角色。
5. **快速模式的交互未定**。现有执行模式会在新建会话时剔除部分技能与能力；专家在快速模式下是否可选、其引用技能被剔除时如何提示，属待定（§12）。
6. **正文质量不可控**。人工编写意味着质量方差大；本期不做评分、推荐位与质量校验。
7. **页面内写回会碰用户的手工格式**。用户可能手写过声明段里的其他字段或特殊排版，页面保存必须保留未识别字段、只改它能识别的那部分，否则一次保存就洗掉手工内容。
8. **显示名称与标识分离带来理解成本**。两个名字并存时，用户容易以为改显示名称就能换掉绑定；界面需要同时给出标识并说明标识不可改。
9. **基线是共享的**。改默认能力会同时影响所有继承型专家，用户可能只想调一个专家却动了全局；界面必须在基线与专家两处分别说明影响面。
10. **MCP 合并逻辑是本地复刻的**。SDK 没有导出它自己的配置合并函数，收窄只能在 `loadConfig` 钩子里交回一份同形状的结果；Pi 调整覆盖语义时本仓库需跟着核对。

| 阶段 | 范围 | 状态 | 当前事项 | 阻塞/未决 | 前置 |

## 12. 待定项

以下不影响当前设计方向，留到对应开发阶段按当时事实确定：

- 快速模式下专家是否可选、其引用技能被快速模式剔除时如何提示。
- 被能力范围排除的 MCP 服务器在 `/mcp` 里如何呈现：本期按「列出但停用」处理，文案与是否提供“临时启用”入口留到实现阶段定。
- 默认能力基线是否提供项目级覆盖：本期只做全局一份，项目级服务器仍按项目配置装配。
