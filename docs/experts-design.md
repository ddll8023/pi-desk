# 专家配置设计

本文是 pi-desk「专家」能力的初步设计：需求、配置存放方案、加载与校验、会话内生效方式、关键取舍、风险与阶段。本文不描述具体实现细节，不含字段级定义、文件清单、验证方案与推进条件；模块现状以 `docs/modules/` 为准，两者不一致时以模块文档为准。

## 1. 背景与问题

pi-desk 目前有两种可复用指令载体：随包与用户级的**技能**，以及四类**子代理**。技能回答「怎么做某件事」，子代理负责「把一段工作挪到隔离进程里做」，但缺少中间一层：**以固定身份、固定方法论、固定输出规范完成单点任务**。

缺这一层的结果是，每个会话都从通用助手的状态重新开始，专业方法只能靠用户每次粘贴提示词，或靠 `AGENTS.md` 承担本不属于它的角色描述。

本期要解决这一层：引入**专家**——人工配置、可内置也可自定义、在会话里召唤即在系统提示中加入一段角色指令并使用其引用的技能。

## 2. 名词约定

全文只用以下名称，不混用近义词。

| 术语 | 含义 | 代码/配置对应 |
| --- | --- | --- |
| 专家 | 一份人工编写的角色定义：身份、方法论、输出规范，外加对技能的引用 | 定义由 `src/shared-process/expert-definitions.ts` 解析；召唤与注入未接入 |
| 专家定义 | 专家在磁盘上的一份 Markdown 文件（声明段 + 正文） | `expert.md`，声明段只取名称、简介与技能引用 |
| 专家目录 | 存放专家定义的目录，一个专家一个子目录，目录名即 id | 内置 `resources/agent/experts/`，自定义 `<agentDir>/experts/` |
| 内置专家 | 随产品构建分发、只读的专家 | `resources/agent/experts/<id>/expert.md`，经 `bundle.json` 的 `experts` 段声明 |
| 自定义专家 | 用户在产品 agent 目录下自行创建或编辑的专家 | `<agentDir>/experts/<id>/expert.md`，可增删改 |
| 派生 | 从内置专家复制出一份自定义专家，之后两份独立演进 | `<agentDir>/experts/<id>-copy/expert.md`，定义里写入 `derivedFrom` |
| 召唤 | 在会话中选用某个专家，使其角色定义进入本次会话的系统提示 | 新建会话时选择，绑定随会话持久保存，首轮后锁定 |
| 角色段 | 注入系统提示的专家正文分段 | 与系统提示的分段机制同层（现有 `skill_guard` 段采用同一机制） |
| 技能可见集 | 某次会话里模型可用的技能清单 | 现有技能装配结果（`additionalSkillPaths` 与用户技能合并） |
| 子代理 | 由 `delegate_subagent` 派出的独立子进程 | `src/sdk-host/sub-agent/` |
| 专家团 | 多位专家分工协作完成一个任务 | 本期不做 |

## 3. 需求

### 3.1 已确认需求

1. **人工配置**：专家由人编写或编辑，不提供 AI 自动生成、不从历史会话自动沉淀。
2. **双来源**：除内置专家外支持自定义专家，两者在同一界面上并列可选。
3. **可派生**：允许从内置专家复制一份自定义专家再修改；内置专家本身保持只读。
4. **单点任务定位**：专家在单个会话内以固定身份执行任务，不扩展为多角色协作。
5. **专家不产生子代理调用**：专家与子代理是并列的两条执行路径，不组合、不嵌套。

### 3.2 不做项及原因

| 不做 | 原因 |
| --- | --- |
| AI 自动生成专家、从会话记录自动提炼专家 | 与「人工配置」的明确要求冲突 |
| 自定义覆盖内置（同名覆写） | 用户无法判断当前生效的是哪一份，诊断与升级路径都会变复杂 |
| 并入 `desktop-config.json` | 方法论正文会退化为 JSON 字符串，手改、diff、审阅全部劣化 |
| 单独的 `experts.json` 集中清单 | 一份文件装所有正文，无法按专家单独分享与移动 |
| 项目级专家目录 | 项目级已由 `AGENTS.md` 与项目技能承担，再加一层优先级收益低、冲突面大 |
| 按专家收窄主会话工具集 | 主会话工具集是会话级/进程级，按角色改可见集需要新的权限面 |
| 专家内部嵌套子代理 | 团 → 成员 → 子代理会形成三层调度，取消、预算、归属都要跨层穿透 |
| 一次会话并存多个专家 | 多段角色指令互相稀释，主提示失焦 |
| 专家市场、版本、导入外部专家包 | 需要来源标记与信任边界，与本期「本地预设」定位不同 |
| 本期实现专家团 | 团队的定义与执行语义需单独设计，见 §11 阶段四 |

## 4. 项目事实与依据

| 事实 | 出处 | 对设计的作用 |
| --- | --- | --- |
| 产品有自有的 agent 目录（便携态在 `data/` 下），共享目录只读且产品不写入 | `src/main/shared/pi-paths.ts` | 自定义专家有唯一可写落点，且随便携数据目录同步 |
| 随包资源由清单声明（扩展、技能、`subAgentOnly` 标记、必需工具），构建期打包只读 | `resources/agent/bundle.json` | 内置专家沿用同一分发形态，不需要新机制 |
| 技能装配为「随包非 `subAgentOnly` 技能 + 共享目录技能」，与用户技能同名时保留随包、剔除用户 | `src/sdk-host/product-resources.ts` | 专家同名冲突的处理方式可与之对齐，避免两套冲突语义 |
| 配置中心是单个带版本号的 JSON，可选字段缺省回退、临时文件加改名原子写入 | `src/main/config/desktop-config-store.ts` | 该范式适合开关与列表，不适合承载长文本正文 |
| 子代理只认固定任务类型，边界由进程参数强制，不递归、不注入父会话历史 | `docs/modules/sub-agent.md` | 专家不能借用子代理的隔离能力，也不能把角色传给子进程 |
| 系统提示支持分段装配 | `docs/modules/skill-guard.md` 所述 `systemPromptOptions.sections` | 角色段可加在同层，不需要新运行时 |

## 5. 存放方案

### 5.1 布局

两类来源各一处目录，互不写入：

- **内置专家**：`resources/agent/experts/<id>/expert.md`，随构建暂存产出、只读、随版本升级。
- **自定义专家**：`<agentDir>/experts/<id>/expert.md`，可写，随便携数据目录一起迁移。

两者结构一致：一个专家一个子目录，目录名即专家 id，目录内放专家定义文件。目录结构留出附加资源的位置（头像等），本期不引入其他文件类型。

### 5.2 来源与优先级

- 两个来源合并成一份专家列表，每项标注来源，界面上可追溯。
- 内置专家只读，运行期不可修改、不可删除。
- 自定义专家可增删改。
- 不设「内置优先于自定义」的隐式覆盖，同名即冲突，见 §5.3。

### 5.3 冲突与派生

- 自定义专家 id 与内置专家 id 相同，或与另一个自定义专家 id 相同：报冲突诊断，不静默取其一。
- 派生流程：从内置专家复制正文到自定义目录，标识自动顺延为 `<内置 id>-copy`（占用时 `-copy-2`…），并在声明段写入 `derivedFrom` 指回来源；内置保持只读。
- 派生副本不跟随内置专家升级。界面上须标明该专家派生自哪个内置专家；是否已落后于内置版本由用户判断，不做自动合并。

这条取舍的代价是内置改进不会流到派生副本。不做覆写换来的是行为可预测与诊断清晰；如果将来出现大量派生副本落后于内置的情况，需要重新讨论覆写与合并策略。

### 5.4 文件形态

一个专家定义包含三类信息，不在此锁定具体字段：

1. **身份**：显示名称与一句话简介，用于列表与召唤时展示。
2. **引用**：本专家要使用的技能 id 列表。
3. **正文**：方法论、工作流程、输出规范——即真正注入系统提示的部分。

正文为空、或只有技能引用而没有正文的专家，视为无效定义（只带技能清单的专家退化为技能集合，失去引入这一层的意义）。

### 5.5 便携与同步

自定义专家位于产品 agent 目录内，随 `data/`（便携态）或用户数据目录一起迁移，不需要额外的同步通道。跨机器复用依赖用户自己搬运数据目录；本期不提供导出/导入。

## 6. 加载与校验

加载发生在会话装配前，产出「可用专家列表 + 诊断」。诊断沿用资源装配现有的方式：在界面上可见、按严重程度分级，不以一句「加载失败」掩盖原因。

需要覆盖的问题类型（不列具体校验实现）：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 结构类 | 目录名与声明 id 不一致、定义文件缺失、正文为空 | 该专家不可用，报诊断 |
| 引用类 | 引用的技能不存在、引用了子代理专用技能 | 专家保留，标记该引用失效 |
| 冲突类 | 与内置或另一自定义专家 id 重复 | 冲突项不进入列表，报诊断并给出来源 |

核对原则：**能保留的保留，能标出来的标出来**。引用失效不应让整个专家消失，否则用户改不了、也看不到哪里错了。

一处必须显式拦截的引用：四类子代理专用技能只对子进程可见，不得被专家引用；引用时应报诊断而不是悄悄加载后又失效。

## 7. 会话内生效

### 7.1 召唤

- 一个会话同时只使用一个专家，切换专家等同换一个角色上下文。
- 召唤后把专家正文作为独立的角色段注入系统提示，与既有的其他提示分段并列，不改写用户级与项目级指令。
- 召唤在会话开始前完成，首轮后锁定：绑定随会话持久保存，重新打开或重启应用后仍然带着同一个专家；换专家需要新会话。
- 选择入口在输入坞的 ＋ 菜单里：专家段只占一行，显示当前选择，点开二级列表再选具体专家。一级行不随专家数量变高，也把「已选哪个」与「有哪些可选」分开。
- 绑定的定义被删除或改名后，界面如实标出「已失效」并提示本会话不再注入角色，但不自动清除绑定——重建同名专家即可恢复，自动清理会把误删变成不可恢复。判定只在清单成功读到后进行，避免一次加载失败被误报成失效。
- 专家只在主会话生效，不写入会话历史，也不随会话记录转移到子进程。

### 7.2 技能可见集

技能可见集不因专家而变：非子代理专用的技能本就对主会话全量可见，专家引用只用于标注与提示，不额外装配、也不收窄其他技能。未引用不代表禁用其他技能——本期采用「引用即高亮、不引用不禁用」的口径，避免用户以为换了专家就失去能力。

被引用但不可用的技能（不存在、或为子代理专用）在界面上提示，不以静默忽略处理。

### 7.3 不改变的边界

- **工具集不变**：专家不增删工具，不改变工具白名单与预算口径。
- **不产生子代理**：专家正文不得包含委派指令，专家定义也不接受与委派相关的配置；子代理侧不认识专家，不加载专家正文。
- **不改变权限与信任**：专家正文与用户自己写的技能同源，不构成新的信任面，也不绕过任何既有确认。

### 7.4 上下文影响

角色段会占用系统提示空间。单专家不叠加，是控制这一成本的主要手段；正文超过注入上限时在前段截断并在尾行说明，定义文件本身不被改写，也不因此报诊断——规则收紧不能让已在用的定义突然失效。上限量与截断判断只有一个来源，主进程视图与宿主角色段共用同一口径；设置页列表与输入坞选择器都标出「已截断」，用户能看出后面那段没进去。

## 8. 与相邻能力的分界

| 能力 | 回答的问题 | 执行位置 | 与专家的关系 |
| --- | --- | --- | --- |
| 技能 | 怎么做某件事 | 主会话（子代理专用技能除外） | 专家可引用技能，但不能内联技能正文 |
| 子代理 | 把一段工作挪到隔离进程里做 | 独立子进程 | 与专家并列，不组合；专家不派子代理，子代理不认识专家 |
| 专家 | 以谁的身份、用什么方法、按什么规范交付 | 主会话 | 本期唯一新增层 |
| 专家团 | 多角色如何分工协作 | 主会话层多角色（另行设计） | 本期不做；团成员是会话级角色，不在子代理层 |

## 9. 关键取舍

| 议题 | 选择 | 代价 |
| --- | --- | --- |
| 存放形态 | 文件化专家目录，两类来源各一处 | 需要新增资源类型与加载校验，不能复用配置中心的字段回退 |
| 同名处理 | 复制派生，不覆写 | 派生副本会落后于内置升级 |
| 作用域 | 只做全局（内置 + 用户级） | 无法为单个项目定制专家，需靠项目指令与技能补 |
| 生效方式 | 系统提示注入 + 技能引用 | 专家不改变工具与预算，能力上限等于单会话上下文 |
| 与委派的关系 | 完全解耦 | 需要并行或上下文隔离的任务必须走子代理，专家帮不上 |
| 可见性 | 一次会话一个专家 | 无法在一次对话里让多个角色交叉发言 |

## 10. 风险与可行性限制

1. **执行层没有「角色」概念**。现有系统提示装配可以承载分段，但「选中的专家是谁」需要在会话生命周期里被记录与传递；这一条不落地，召唤只是把一段文字塞进提示，界面上无法回显。属本期主要工作，不是纯配置问题。
2. **专家能力偏薄**。因不派子代理、不改工具集，专家只能改善方法与人设，不能缩短长任务、不能隔离噪声。若产品表达暗示了后者，会造成预期落差。
3. **派生副本漂移**。见 §5.3。
4. **专家团缺席导致概念不完整**。只有专家这一层时，用户可能把「多角色协作」的期待压到专家身上；界面与文案须明确当前只支持单一角色。
5. **快速模式的交互未定**。现有执行模式会在新建会话时剔除部分技能与能力；专家在快速模式下是否可选、其引用技能被剔除时如何提示，属待定（§12）。
6. **正文质量不可控**。人工编写意味着质量方差大；本期不做评分、推荐位与质量校验。

## 12. 待定项

以下不影响当前设计方向，留到对应开发阶段按当时事实确定：

- 专家 id 的合法字符集合是否比目录名规则更宽；
