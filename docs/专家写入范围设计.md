# 专家写入范围设计

本文是专家「写入范围」能力的初步设计：问题、已确认需求、项目事实、设计思路与取舍、职责边界、限制与阶段。不含字段级协议、文件清单、实现常数与验证内容；具体实现在各开发阶段按当次事实讨论。

## 1. 问题与目标

专家身份目前只是系统提示里的一段正文。调研专家写着「只写 `docs/` 下的设计文档」，审查专家写着「只审不改」，但宿主只按工具名裁剪能力：这两个专家都还能用 `write`、`edit` 写任意文件，越界没有任何拦截。

已有的事实与缺口：

- 专家能力范围只有技能、MCP、工具三个维度，工具维度按名字取舍，没有路径维度；
- 子代理的写入守卫（`src/sdk-host/sub-agent/write-guard.ts`）能按路径拦截，但它由宿主显式加载进子进程、范围来自环境变量，主会话没有对应加载点；
- 专家角色段（`src/sdk-host/expert-role.ts`）每轮重写，可以承载范围说明，但说明本身不是拦截。

目标是让「专家能写到哪」成为可声明、可由宿主强制的边界：调研专家保留写设计文档的能力，同时在 `src/` 等代码位置被拒绝写入；审查专家可以直接声明为只读。

## 2. 已确认需求、范围与不做项

需求：

1. 专家定义可以声明一组写入范围，表达「目录前缀」与「单个文件」两种粒度；
2. 范围在会话装配期交给宿主执行，越界写入被拒绝并给出原因；
3. 未声明范围时行为与现在完全一致（不限制），旧定义升级后不受影响；
4. 范围要在设置页可编辑、在会话里有可读说明，不只存在于文件里。

不做项：

- 不拦截 `bash`。`bash` 的重定向同样能写文件，本文不假装这一层已经闭合，边界写进文档与专家正文；
- 不拦截 MCP 工具与子代理写入。子代理有自己的 `write_scope` 与守卫，两者不合并成一套规则；
- 不做通配符或 glob 匹配；
- 不改变子代理写入策略（`docs/` 与根 `README.md` 的口径保持现状）；
- 不迁移旧定义、不改写既有专家声明的其余字段。

## 3. 项目事实

- 专家声明的解析与能力范围合并集中在 `src/shared-process/expert-definitions.ts`，主进程、宿主与设置页共用同一份解析，不各自实现；
- 工具范围的裁剪发生在会话装配期（`src/sdk-host/session-runtime.ts`），按许可集把范围外的工具从激活集合移除，受保护工具除外；
- 子代理守卫的价值在于路径处理已经解决过一遍：以真实路径比较、按分隔符边界判断目录、新建文件时取最近存在的祖先解析，避免符号链接逃逸与 `docs-old/` 被误放行；
- 专家定义保存链路（`src/main/sessions/expert-files.ts`）重写声明段时保留本模块不认识的字段，因此新增声明字段不会在设置页保存时被抹掉，只是界面看不见；
- 角色段与执行模式段并列注入，内容每轮重算，改定义文件在下一轮生效。

## 4. 设计思路与取舍

推荐方向：把写入范围作为专家声明的第四个维度，由主会话的一个写入守卫扩展执行。

核心机制：

- **声明**：范围项是相对项目根的路径，目录以分隔符结尾表示前缀，其余按完整文件处理；写法非法的项忽略并在专家清单诊断里报出，不因为一条手写错误让整份定义失效，也不按放行处理；
- **三态语义**：不写该字段＝不限制；写了但列表为空＝只读；有内容＝只允许这些位置。三态在设置页用单选表达，避免「留空」同时被理解成两种意思；
- **强制**：装配期只在专家确实声明了范围时注册拦截，拦截 `write` 与 `edit` 的目标路径；没有专家的会话不加载任何拦截，行为与现在一致；
- **归一化**：沿用子代理守卫的路径处理（真实路径、目录边界、最近存在祖先），抽成一处共享实现，两处共用，不写第二份路径比较；
- **说明**：角色段在范围生效时补一句「写入范围：…，越界会被拒绝」，未声明时不写，避免给普通会话增加无关文字。

关键取舍：

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 强制方式 | 拦截式守卫 | 不新增工具名、不改工具清单与诊断；替换式包装工具会让模型看到与设置页候选不一致的工具名 |
| 匹配粒度 | 目录前缀 + 完整文件 | 与专家实际需要（写一个文档目录）匹配；glob 会引入新的匹配语义与错误面 |
| 缺省值 | 缺省不限制 | 缺省只读会静默改变所有既有专家行为，属破坏性变更 |
| 非法声明 | 忽略该项并诊断 | 手写声明常有拼写偏差，整份定义失效的代价高于丢一项 |
| 与工具范围的关系 | 正交并存 | 工具范围决定「有没有写工具」，写入范围决定「写到哪」，两者不互相替代 |

## 5. 职责与数据流

- **声明解析**（共享进程层）：从声明段读出三态与范围项，作为唯一口径，供主进程、宿主与设置页共用；
- **主进程**：读定义时返回三态与范围，保存时按固定顺序写回声明段，未知字段原样保留；
- **宿主装配**：组装会话时按专家范围决定是否注册拦截，并把范围写进角色段说明；
- **渲染层**：编辑对话框提供三态选择与目录输入，专家列表行显示一句范围摘要。

数据流是单向的：声明段 → 解析 → 装配 → 拦截；拦截不修改声明，也不产生新的会话状态。

## 6. 限制与风险

- **`bash` 不受约束**：重定向、`sed -i` 之类的写入无法通过工具级路径检查拦住。这是本设计明确的边界，不是遗漏；需要更强约束时应把它作为独立问题讨论，而不是在这里假装闭合。
- **范围相对项目根**：会话执行根不同（工作区切换、子目录打开）时按会话实际执行根解析，设计上以会话执行根为基准，不按应用启动目录。
- **真实路径依赖文件系统**：符号链接、大小写不敏感文件系统、新建路径的祖先解析都要走与子代理守卫同一套实现，两处任何一处改动都必须同步。
- **设置页看不见的风险**：旧定义不带该字段时界面显示「不限制」，用户若期待只读需要显式选择；对话框需要把三态含义写清楚，避免「留空」被理解成两种意思。

## 7. 阶段与设计关注点

- **阶段一：声明与解析**。解决三态语义、范围项写法与诊断口径；关注点是「一条写错的范围项如何被忽略并报出」，以及设置页读取时如何区分「未声明」与「声明为空」。
- **阶段二：宿主强制**。解决拦截点与共享路径实现；关注点是「没有专家的会话零影响」、被拒原因的可读性，以及角色段说明与工具范围说明不重复。
- **阶段三：设置页**。解决三态单选、目录输入与列表摘要；关注点是旧定义迁移后的默认显示与新字段被保存链路保留的事实是否一致。

各阶段的具体实现（字段名、上限、错误文案、组件形态）在该阶段结合当次代码再定；本文不预先锁定。
