# 工作流模块初步设计

本文是 pi-desk「工作流」能力的初步设计：说明需求、边界、大致架构与关键取舍，供后续讨论与分阶段开发使用。具体实现细节在各阶段结合当时的代码事实确定，本文不锁死。

## 问题与背景

pi-desk 目前只有交互式会话：一次对话由一个 Agent 在单个上下文里推进，协作形态限于 `delegate_subagent` 的一次性子进程派发与专家团的团长—成员账本。没有把「多个 Agent 按一张固定的图依次/并行推进」表达成可保存、可重跑、可观察的资产。

参考项目里这一形态有两种成熟落法：脚本编排（DSH `dsh-tool-workflow`、WorkBuddy Dynamic Workflows）与节点图画布（Ekko Studio Visual Workflows、EvoFlow 工作流）。本项目选定**节点图画布**：用户要的是看得见、拖得动、能复用的一张图，而不是读一份脚本。

## 已确认需求

1. 用户在工作区里新建一个工作流标签，得到一张可编辑的有向图。
2. 图上每个 Agent 节点各自是一次独立 Agent 会话，彼此上下文不共享。
3. 一次运行按图推进，节点失败可以路由到另一条边；同层节点可并行。
4. 运行过程可见：每个节点的状态、日志、输出，可中途取消。
5. 定义可保存、可多份并存，重启后仍在。
6. 图里可以放人工审批门：运行到它时停下等人给决定，不自动推进。
7. 分支可以按上游结论文本判定，不能只靠节点成败。
8. 历次运行可回看：状态、结论与事件都是记录，不重新执行。

## 目标

- 让「多步、多 Agent、可重复」的工作成为一种一等资产，与专家、专家团并列。
- 复用现有进程与守卫设施，不新引入执行内核。

## 范围与不做项

当前范围（已落地）：

- 节点类型：`start`、`agent`、`approval`、`end`。
- 边路由：`success` / `failure` / `always` 状态边，以及 `condition` 条件边。
- 定义的多份保存与编辑、单次手动运行、运行观察与取消、审批门的通过与拒绝、历史运行回放。
- 节点内的专家、提示词、写入范围配置；节点工具集与写入范围按专家生效集计算。
- 启动参数：定义里声明，运行前填值，节点提示词用占位符引用。
- 定时触发：五段 cron 到点按调度里记录的项目与参数值启动。

当前不做：

- 循环。
- 从某个节点重跑（回放只重演记录）。
- 模板发布与分发。
- 节点之间的消息通道；节点只经由图的边与上游输出单向传递。

## 大致架构与职责

```text
渲染层 src/renderer/src/workflows/
  画布（Vue Flow）→ store → services/desktop.ts → window.desktop
        ↓ Electron IPC（定义 CRUD / 启停运行 / 读取运行）
主进程 src/main/workflows/
  store.ts       定义文件读写（<agentDir>/workflows/<id>/workflow.json）
  runner.ts      图调度：就绪判定、并发上限、状态边与条件边、审批门、取消
  node-runner.ts 节点载体：独立 pi 子进程 + 写入守卫 + 会话落盘
  run-store.ts   运行记录（<agentDir>/workflow-runs/<runId>/run.json）
  ipc.ts         通道注册与运行事件投递
        ↓ 事件推送
渲染层运行面板（节点状态、日志、输出、取消）
```

职责边界：

- **主进程是运行的唯一所有者**。工作流不挂在任何会话上，运行生命周期与会话运行解耦；页面只读运行快照并发出取消。
- **节点执行载体是独立 pi 子进程**，与 `team-runner.ts` 同一套进程习惯（`--session-dir` 落盘、`PI_SUB_AGENT_WRITE_SCOPE` 守卫、超时强杀、输出上限），但会话目录按运行与节点分开，节点之间不共享上下文。
- **画布只负责形态与配置**，不执行任何节点；图的校验在契约层，非法图在保存与启动时都被拒绝。

## 数据与落盘

- 定义：`<agentDir>/workflows/<id>/workflow.json` —— id、名称、说明、参数、节点、边、更新时间。删除走系统废纸篓。
- 定时任务：`<agentDir>/workflows/<id>/schedules.json` —— 每条带 cron、项目与参数值；与定义同目录，删定义时一并移除。
- 运行：`<agentDir>/workflow-runs/<runId>/run.json` —— 运行状态、每个节点的状态与结论摘要、边判定结果、事件流；节点会话落在同目录的 `sessions/<nodeId>/`。
- 启动时按记录收敛：`running` 但没有活跃进程记录的运行标记为中断，不留「永远在跑」的假象。

## 执行语义

- 图必须先通过校验：恰好一个 `start`、至少一个 `end`、无环、边的两端存在、`agent` 节点必填专家与提示词。
- 调度按拓扑序推进：一个节点在其所有入边都被判定后进入待执行；同层并发受运行级上限约束。
- 节点终态为 `completed` / `failed` / `cancelled`；`completed` 走 `success` 边，`failed` 走 `failure` 边，两条都没有时走 `always`。
- 状态边优先：存在可走的状态边时条件边不参与判定；没有时才按定义顺序取第一条命中的条件边（对源节点结论文本求值）。
- 审批门停在 `waiting`，不入进程：通过走 `success` 与 `always`，拒绝记为 `failed`（成因 `rejected`）并走 `failure` 与 `always`。
- 节点进程带 `--no-extensions` 关闭扩展，工具集取专家的生效工具集（并剔除扩展注册的工具）；写入范围优先取节点配置，未配置时沿用专家定义。
- 取消一次运行会释放等待中的审批、终止其全部活跃子进程，并把已开始未收敛的节点记为 `cancelled`。
- 同一工作流同一时刻只允许一次运行：定时触发与手动启动共用这一条，不并行开第二次。
- 没有可走的出边时，该分支停止；全部可达节点收敛后运行结束。

## 关键取舍

| # | 取舍 | 结论 | 理由 |
| --- | --- | --- | --- |
| 1 | 画布库 | `@xyflow/vue`（MIT） | 官方当前版本、与 Tailwind 兼容、自定义节点即 Vue 组件；若遇阻塞按同 API 回落到 `@vue-flow/core` |
| 2 | 页面位置 | 工作区标签 | 复用标签、项目归属与窗口体系，不新增一级页面 |
| 3 | 节点执行载体 | 主进程拉起的独立 pi 子进程 | 宿主会话装配紧绑页面绑定状态，不适合被图调度复用 |
| 4 | 运行归属 | 主进程 | 工作流不依附会话，跨项目运行，崩溃后可按记录收敛 |
| 5 | 边语义 | 退出状态路由；条件分支用显式判定 | 退出状态与显式条件都可静态校验、可预测；模型判定型分支不列入 |
| 6 | 停用语义 | 通道型插件 | 与文件、终端等能力同口径，停用即下次启动不装配 |

## 阶段进度

- **阶段一（已落地）**：定义 CRUD、画布编辑、手动运行、运行观察与取消；节点类型 `start` / `agent` / `end`，边路由 `success` / `failure` / `always`。
- **阶段二（已落地）**：审批门节点（`approval`）、条件边（`condition`）、历史运行回放。
- **阶段三（已落地）**：参数化启动（定义内声明参数、启动填值、节点提示词占位符替换）与定时触发（五段 cron、项目与参数值随调度保存、应用退出即停）。

## 待定问题

- 边上的失败路由是否需要「重试次数」这一层，还是交给节点配置的超时与用户手工重跑。
- 条件边的判定范围是否要从「源节点结论文本」扩到运行级变量（如运行参数）。
- 回放是否要从只重演记录扩到「从某个节点重跑」；后者要重新定义已收敛节点的语义与用量归属。
- 节点是否需要把上游输出作为指令的一部分注入，还是完全依赖各自提示词。
