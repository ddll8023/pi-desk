# pi-memory 旧记忆修复设计

**性质：一次性运维记录，2026-11-12 已完成。** 现行约定（预算、判据、数据口径）见 `.workbuddy/memory/MEMORY.md`；本文保留是为了回答“当初为什么这么定”和“哪六批改了什么”，不是现行设计规范。

任务分级：高风险（批量状态变更 + 规则替代，部分操作不可逆）。本文只写问题、前提验证、修复规则、处置矩阵、批次约束、验收标准与阶段，不列全量记录 ID，也不授权直接写库；任何状态变更仍需单独生成并审核计划。

## 1. 问题与目标

旧记忆库在保存机制收紧前积累了大量实施流水。当前记录同时承载稳定知识、已完成工作、未解决问题和当时有效的事实，导致：

- 已完成的 `progress` 仍以 `active` 进入当前项目近况，而近况只有 3 个名额（实测：当前项目最新 3 条中 2 条是提交流水）。
- 已解决的 `issue` 没有退出当前状态，可能与现行事实冲突。
- 部分 `decision` 夹杂提交哈希、文件清单和过程叙述，读取成本高——常驻段 71 条候选、46,643 字符正文挤 17,000 字符预算，约三分之二拿不到正文。
- 规则类记录不能通过状态更新关闭，错误合并会直接影响后续约定。

目标：在不删除历史正文的前提下，把旧记录重新归入“稳定知识 / 未决状态 / 历史经历”，让当前召回只看到仍然有效的结论与状态。

## 2. 范围与不做项

本次修复范围：

1. 已有记录的状态归类与规则替代。
2. 从已完成流水中提炼仍可复用的结论。
3. 对已解决或不再相关的问题做生命周期收口。
4. 对重复、过时或实现细节过重的规则做合并与替代。
5. 规则类记录的退役出口（见 5.3）。

明确不做：

- 不物理删除旧记录。
- 不修改历史正文，只用新记录替代或状态更新。
- 不根据目录名、提交哈希或文件路径猜测项目归属。
- 不把所有超过七天的记录自动归档；时间只是候选线索。
- 不把普通实现流水改写成新的 `decision`。
- 不在没有批次记录与回滚路径的情况下执行批量写入。
- 不在前提验证（§4）通过之前进入阶段二。
- 不在本文档中展开字段级结构、脚本参数或逐条记录清单。

## 4. 前提验证：归档是否真的退出召回（已完成）

全文收益依赖一个假设——记录转 `archived` / `resolved` 后不再出现在当前上下文。该假设已在本机副本上实测通过，结论为「成立」。

### 4.1 方法与证据

在库文件副本（`--store /tmp/pi-mem-stage0`，未触碰正式库）上执行：

1. 写入三条同关键词、同归属的探针记录：`progress/active`、`progress/archived`、`issue/resolved`（`store_version` 47 → 48）。
2. 读 `project-notes`（近况段的唯一数据来源）。
3. 读 `recall --mode records`（关键词召回）。

| 路径 | 实测结果 | 代码依据 |
| --- | --- | --- |
| 当前项目近况段 | 只返回 `active` 探针，`archived` / `resolved` 均未出现 | `project_notes` 的 `WHERE type IN (...) AND status='active' AND project_id=? AND date>=?` |
| 常驻约定段 | 规则类只有 `active` / `superseded` 两态，已替代的自然排除 | `active_rules` 的 `WHERE type IN (?,?) AND status=?` |
| 关键词召回 | 三条全部命中（`archived`、`active`、`resolved` 各一），结果带状态字段 | `indexed_recall` 无状态过滤，返回 `note` 明示“状态不代表当前适用” |

### 4.2 附带的三条结论

- **近况段是 3 个名额制**，不是“抓一把最近的”。近七天 52 条 `active progress` 中只有最新 3 条（跨 `progress`/`issue`/`fact`/`preference_evidence` 混排）能进正文。因此“已完成流水污染近况”的实际形态是：**最新 3 条里有几条是流水**，而不是库里有 104 条流水。实测当前 `pi-desk` 的近况正文为两条提交流水 + 一条未决 `issue`，即 3 个名额里 2 个被流水占掉。修复的收益集中在这 2 个名额上，与 104 这个数字无关。
- **常驻约定不受 `progress` 影响**，只装 `decision` / `constraint`。所以“归档已完成 `progress`”对常驻段零影响；常驻段的问题只能由阶段三解决。而常驻段恰恰是超载最严重的：71 条候选、46,643 字符文案、17,000 字符预算，约三分之二的规则拿不到正文。
- **无归属记录不进近况**（近况查询强制 `project_id=?`）。21 条无归属 `active` 记录对近况没有贡献，归档它们也不会改变近况；它们的价值只体现在关键词召回与常驻（常驻把无归属视为通用约定）。

### 4.3 对阶段的影响

- 阶段二准入条件已满足，可以按 §7 出清单。
- 但收益排序需要修正：**规则类（阶段三）的杠杆大于 `progress`（阶段二）**。建议阶段二首批只处理“落在近况最新 3 条里的流水”，数量小、影响直接、回滚容易；其余 50 条近七天 `progress` 的批量归档收益有限，可后置到阶段三之后。
- 口径统一：归档 = 退出近况，不等于不可检索。对用户与文档不得表述为“已清理”，关键词检索仍会命中并返回原正文。

## 5. 修复原则

### 5.1 先提炼，后归档

已完成 `progress` 中可能包含仍然有效的设计结论、环境陷阱或未决问题。处理顺序应为：

1. 判断是否含可复用结论。
2. 有结论时先保存为新的 `decision`、`constraint` 或 `issue`，并在正文注明来源旧记录。
3. 确认新记录已落盘后，再把原 `progress` 转 `archived`。
4. 没有可复用结论时直接归档。

不得为了让旧记录“看起来干净”而删除仍然有效的唯一证据。提炼出的新记录必须能追溯到来源，否则只是把噪声换了个位置。

### 5.2 规则用替代，非规则用状态

- `decision` / `constraint`：不使用 `resolved` / `archived`。失效、重复或无实质结论时，用新规则加 `supersede_record_ids` 与理由替代旧规则，出口口径见 5.3。
- `progress` / `fact` / `preference_evidence`：使用 `active` / `archived`。
- `issue`：使用 `active` / `resolved` / `archived`。

`status_updates` 只关闭 `active` 的非规则记录，不能伪装成规则替代，也不能用来绕过 `supersede`。**该约束已在引擎层强制**（`plan` 阶段即报错，不是靠调用方自觉）：对规则类报「规则记录不能用状态更新关闭」，对非 `active` 记录报「只有 active 记录可以关闭」，目标状态只接受 `resolved` / `archived`，且按类型校验（`progress` 不支持 `resolved`）。阶段一的这项前置条件已消除。

### 5.3 规则退役机制

规则类记录的现实缺口：既不能用 `status_updates` 关闭，`supersede` 又要求存在一条“新规则”作为承载体。当旧规则本身只是实施流水、无可提炼结论时，协议里没有合法出口，而这类记录在 `active decision` 中占比最高。两种可行口径：

| 口径 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| A. 显式退役 | 引擎支持记录仅退出活跃召回、不产生替代规则（退役标记或指向自身的替代关系） | 语义清晰，不制造空规则 | 协议、引擎、查看器需同批改版 |
| B. 同键压制 | 创建一条正文为“该主题结论不再适用”的规则，显式替代旧规则列表 | 零协议变更，阶段三即可执行 | 库里留一条空规则，退役理由必须写在正文 |

推荐：阶段三按 B 执行，同时把 A 记为后续项。无论哪种口径，退役前都必须给出“为什么不再是规则”的具体证据，例如正文明细只有提交哈希与文件清单、没有适用条件、没有可执行结论。不允许用 `status_updates` 绕开本节的出口。

B 口径的实测行为（副本上以同 `rule_key` 新建规则）：

- 同归属、同 `rule_key`、目标为 `active` 时自动进入替代链，回执列出被替代 ID；跨归属不会自动命中，需显式 `supersede_record_ids`。
- **自动替代时 `supersession_reason` 被忽略**，替代记录里写入的是固定文案「相同 rule_key 的新决定取代旧决定，旧正文保留」。因此退役理由不能指望替代记录承载，必须写进新规则的正文——否则三个月后没人知道这条规则为什么被废。
- 显式替代不校验归属：从 `pi-desk` 的保存计划可以替代一条无归属规则。这给跨归属合并留了通道，也让误替代更容易发生，所以显式替代必须逐条给理由并人工确认。
- `status_updates` 对规则类会直接报错「规则记录不能用状态更新关闭」；对非 `active` 记录报错「只有 active 记录可以关闭」。协议层已经强制，无需另加校验。

### 5.4 只处理高置信项

候选必须能指出具体证据，例如：

- 正文明确写了“已提交”“已完成”“已修复”“不再适用”。
- 后续记录已经替代同一主题，且新记录明确覆盖旧结论。
- 当前仓库或文档事实直接否定旧状态。

仅有“时间久”“看起来像流水”“包含文件名”不足以单独判定归档。

### 5.5 保留不可逆边界

状态关闭在当前写入协议中没有反向操作。每批必须先出候选清单、展示目标正文与理由，确认后再提交；不将大量未核对记录一次性关闭。

### 5.6 批次可回滚

“不可逆”不应作为结论，而应被处理成“可纠正”。任何批量写入都伴随一份批次记录（§8），使误判可以在不影响其他批次的前提下撤回。没有批次记录的操作不得提交。

## 6. 分类处置矩阵

| 类型 | 保留 `active` | 转 `resolved` | 转 `archived` | 规则替代 |
| --- | --- | --- | --- | --- |
| `progress` | 仍有未决阻塞、依赖或下一步 | 不使用 | 已完成且无可复用结论 | 不使用 |
| `issue` | 问题仍未解决，或复发风险仍存在 | 已修复且有可复用根因/修法 | 已过时、环境不再存在、无复用价值 | 不使用 |
| `fact` | 当前仍成立，且非仓库可推导 | 不使用 | 已被新事实否定或仅对当时有效 | 不使用 |
| `preference_evidence` | 仍支持当前画像 | 不使用 | 已失效或与当前偏好无关 | 不使用 |
| `decision` | 仍是当前有效结论 | 不使用 | 不使用 | 过时、错误或无实质结论时用新决定替代（5.3） |
| `constraint` | 仍必须遵守 | 不使用 | 不使用 | 规则变化时用新约束替代（5.3） |

### 6.1 `progress` 的细分

- **未决状态**：保留 `active`。正文应能回答“当前卡在哪里、下一步是什么”。
- **已完成流水**：转 `archived`。正文保留，不再进入近况。
- **混合记录**：先提炼其中仍然有效的结论或问题，再归档原记录。
- **纯提交/文件清单**：不再作为知识保存；如果用户需要工作史，保留为 `archived` 即可。

### 6.2 `issue` 的细分

- **未决问题**：保留 `active`。
- **已解决且可复用**：转 `resolved`，保留根因、适用环境和修法。
- **一次性或环境已消失**：转 `archived`。
- **与当前仓库事实冲突**：先核实当前事实，再转 `resolved` 或 `archived`，不能继续以 `active` 返回旧结论。

“可复用”不作为主观判断，按可判定条件区分：`resolved` 要求根因与修法能复述且相关代码或依赖当前仍存在；`archived` 用于依赖已删除、工具已更换、环境已不存在的情形。两者都判不出时保留 `active`，不硬分。

### 6.3 `decision` / `constraint` 的细分

先区分真规则与伪规则，这是阶段三的范围前提。**不能用 `rule_key` 是否缺失来判断**：实测 `active` 的 129 条 `decision` 与 8 条 `constraint` 全部带 `rule_key`，无键为 0，键的有无在这里不构成区分。

- **真规则**：有适用条件与可执行结论，脱离当天上下文仍成立。
- **伪规则**：主体是提交哈希、文件清单、diff 行数或过程叙述，结论部分要么缺失，要么只是“做了什么”。

可判定特征（满足任一条即列入候选，仍需人工确认）：

- 正文出现 7 位以上十六进制提交号，或以 `+N/−N` 形式给出改动行数。
- 正文以文件清单为主体（反引号包裹的路径 ≥ 4 处）而非结论为主体。
- 标题句式是“落地 / 提交 / 收敛 / 对接完成”，而非“X 必须 / X 应 / X 不使用”。

按上述特征粗筛，137 条 `active` 规则中约 47 条疑似流水，其中 33 条落在近七天窗口内——这 33 条正是挤占常驻正文预算的主力，应作为阶段三首批。

处置：

- **仍然有效**：保留；正文过重时只在新记录中提炼，不直接改写旧记录。
- **被后续方案替代**：用相同 `rule_key` 创建新决定，自动进入替代链；跨键、跨归属时显式指定旧 ID。
- **重复规则**：合并为一条更完整的当前规则，显式替代所有重复旧规则，并写清合并理由。
- **伪规则**：按 5.3 的 B 口径退役，不进入活跃规则召回。退役前必须答出“这条本该是哪条规则”，否则说明它确实无结论，可直接压制而不必提炼。

## 7. 修复流程

1. **前提验证**：按 §4 已通过（2026-11-12）。后续批次不再重复验证，但若读取侧代码变更，需重跑一次。
2. **生成只读清单**：按项目、类型、日期和状态筛选候选，展示标题、正文摘要、日期、归属、判定依据，并补「是否含提交痕迹」「是否含可复用结论」「是否落在近况最新 3 条内」三列。第三列决定收益，前两列决定判定。产出见《pi-memory 修复候选清单》。
3. **人工核对**：区分高置信项、需补充证据项和保留项；无法判定归属的记录不自动改写。
4. **提炼新知识**：将混合记录中的有效结论保存为新的 `decision`、`constraint` 或 `issue`，并注明来源旧记录。
5. **生成计划**：对非规则记录使用 `status_updates`；对规则使用新规则与 `supersede_record_ids`。计划中逐条写明原状态、新状态与理由。
6. **分批提交**：按项目或主题分批，单批条数设上限（见 D6），不将跨项目、跨类型、规则与非规则的候选混在同一批不可逆操作中。
7. **提交后核对**：确认目标记录状态、近况段是否排除已关闭记录、规则替代链是否可追溯、原正文是否完整，并把结果写回批次记录。

## 8. 批次记录与回滚

每批写入生成一份批次记录，内容至少包括：批次 ID、时间、执行者、筛选条件、目标记录 ID、原状态、新状态、判定依据、提炼出的新记录 ID（如有）、失败项与原因。

回滚规则：

- 非规则批次：按原状态逐条写回，可整批撤回。
- 规则替代批次：需反向替代（新规则再被旧规则替代），因此规则类必须单独成批，不与状态类混批，否则整批不可回滚。
- 回滚同样记录在批次记录中，保留原始批次，不删除、不覆盖。

批次记录不进入记忆召回，存于项目侧的操作日志，仅用于审计与纠错。

## 9. 验收标准

修复结束需同时满足（判据已按实测收敛，见 9.2 的废弃项）：

- 近况段：当前项目最新 3 条中，已完成流水为 0。
- 常驻段：注入正文的规则中，不存在「只有实施过程、没有适用条件」的记录（抽样 10 条人工复核）。
- 生命周期：`resolved` 与 `archived` 两种状态都有实际使用记录，不再出现「状态机制从未启用」。
- 每条被关闭或被替代的记录都有批次记录与判定依据，覆盖率 100%。
- 任意 `active` 规则都能回答“它替代了什么、是否被替代”；任意被 B 口径压制的旧规则，其退役理由能在新规则正文里读到。
- 阶段四结束时，无归属记录数量仍为 21 条 `active`（修复不改归属）。

### 9.1 不把预算当修复目标（已定，不再讨论）

`RESIDENT_RULES_BUDGET = 17,000` 保持不动。不要因为“近七天规则装不下”去压缩规则、合并规则或上调预算。

- 17,000 是当时拍的数，不是从需求推导的；它既不能用来证明“规则太多”，也不是要优化的目标。
- 重点是近期，不是全部。近期装得下就够了，远期降为索引行是设计意图。近三天当前 21 条 / 9,311 字，本就装得下。
- 只有真契约装不下时才考虑调预算：判据是「所有 `constraint` + 仍需生效的 `decision` 在近三天装不下」，或真契约总量超过约 40 条。当前 3 条约束 + 近三天决策约 10,600 字，占预算 62%。
- 禁止用「当前总量 + 余量」反推预算。曾据此算出 27,000，属把症状当需求，已否决。
- **“降级为索引行”不能当兜底**：`access_events` 自 2026-11-04 起仅 59 次、覆盖 52 条记录，按需检索在实践中几乎不发生，掉出预算的规则接近无效。因此要让它进预算，就不要把它存成 `decision`。
- 缩减靠降低流入，不靠调上限：主因是“做完即失效”的实施记录被存成了 `decision`（候选集里粗筛 18 条 / 10,235 字），正确处置是转 `archived` 或降级为 `progress`。

判断一条记录该不该常驻，只问一句：**这条规则会不会在下周改变某个具体决定。** 不会的就不该是 `decision`。

## 10. 风险与不可逆点

- **误归档**：状态关闭后不会自动恢复；如果仍有未决事项，归档会让后续会话失去当前上下文。缓解手段是批次回滚与逐条理由，而不是降低核对强度。
- **误替代**：错误的新规则会改变后续行为，且旧规则只保留为历史；替代前必须核对适用范围。显式替代不校验归属，跨归属替代在协议层是放行的，必须靠批次核对拦住。
- **理由丢失**：B 口径下自动替代会丢掉 `supersession_reason`，只留固定文案；理由没写进新规则正文就等于没记录。
- **空规则噪音**：按 B 口径退役会留下“该主题已失效”的规则，若批量滥用，召回质量会以另一种方式变差；退役必须逐条给证据。
- **收益错配**：`progress` 归档只影响近况 3 个名额，规则类才影响常驻预算；把力气全押在 `progress` 上会看不出效果。
- **归属错误**：无归属记录不能靠目录名推断；错误归属会让其他项目的约定进入当前项目。
- **遗漏证据**：只按日期或关键词批量处理，会误伤仍然有效的长期事实。
- **历史丢失的假象**：归档不等于删除，但默认近况与常驻不再显示；用户需要知道记录仍可检索。
