# 内置 Pi agent 与扩展更新：设计文档

## 1. 文档定位与范围

本文是初步设计文档，用于说明「在应用内更新内置 Pi agent」与「在应用内更新 Pi 包（扩展）」这两件事的需求、事实依据、大致设计思路、关键取舍与风险。它提供后续开发阶段讨论的起点，不是开发规格；具体实现、依赖选择、文件改动与操作步骤在对应开发阶段结合当时事实单独讨论。

**本文覆盖**

- 扩展（Pi 包）的更新执行：从「检测到可更新」到「在应用内完成更新」。
- 内置 Pi agent 的版本更新：让随应用加载的 Pi agent SDK 可以在应用内升级。

**本文不覆盖（明确排除）**

- pi-desk 应用自身的自动更新。当前分发形态是免安装便携包，官方打包工具对便携目标的自动更新需要自行实现，且 macOS 侧还涉及签名方案；这属于另一条独立议题。
- 制品托管位置与 CI 建设。它服务于应用自身更新，与本文两条线无关。
- 应用目录内的文件替换。项目已有实际踩坑记录表明该路径在 Windows 上不可靠，本文所有方案都不触碰应用目录内文件。

## 2. 已确认需求与不做项

**已确认需求**

- 扩展能在应用内更新，不需要用户到命令行执行更新命令。
- 内置 Pi agent 能在应用内更新，不需要每次重新出包并让用户替换应用目录。
- 更新过程要能反映真实原因：工具缺失、网络失败、权限/信任不足、无需更新必须是不同状态，不能混为一谈。

**不做项**

- 不绕过 Pi 的项目信任边界。项目级包在项目未被信任时不更新。
- 不新建会话、不代用户改 Pi 的配置声明；更新只针对已声明的包。
- 不在离线模式下发起远端请求（沿用现有的离线语义）。
- 不自动执行内置 Pi agent 更新（见第 5 节取舍 4）。

## 3. 项目事实与依据

本节区分项目事实、外部证据与设计推断。项目事实来自当前仓库与项目记忆；外部证据来自官方文档与官方安装脚本；设计推断在第 4、5 节给出。

### 3.1 加载链路（项目事实）

- 主进程不导入 Pi agent SDK；SDK 只在四个受管入口中加载：常驻 SDK 宿主（持有会话）、认证辅助进程（一次性）、CLI 运行器（一次性）、版本检查脚本（一次性）。
  来源：`src/main/**` 中无 SDK 导入；`src/sdk-host/index.ts`、`src/auth-helper/index.ts`、`src/pi-cli/index.ts`、`src/update-check/index.ts`。
- 受管入口由主进程用 Electron 自带的 Node 启动，入口文件与参数由调用点固定给出，页面不能指定入口、可执行文件或参数；超时与进程树终止由调用方负责。
  来源：`src/main/pi-cli-process.ts`、`src/main/update-checker.ts`。
- agent 目录由应用统一解析，并通过环境变量注入给所有受管进程；当前没有设置 Pi 的受管安装根目录变量。
  来源：`src/main/pi-paths.ts`。

**设计含义**：切换 SDK 版本只需重启这些子进程，不需要替换应用本体或改动主进程。这是本方案成立的基础。

### 3.2 SDK 能力边界（项目事实）

- SDK 包的公开入口只有 `.` 与 `./rpc-entry` 两个导出；官方受管安装（managed install）的实现位于包内私有模块，未对外导出。
  来源：SDK 包 `package.json` 的 `exports`、包内 `package-manager-cli` 模块。
- 官方自更新只在三种安装形态下可用：受管安装、npm 全局安装、pnpm 全局安装；其他形态直接报「cannot self-update this installation」，Windows 上非 npm/pnpm 形态同样直接失败。
  来源：SDK 包内 `package-manager-cli` 模块的自更新分支。
- 受管安装的判定条件：进程环境中的受管安装根目录变量指向的目录含合法标记文件，且**当前正在加载的 SDK 包目录必须位于该根目录下的 releases 布局中**；否则一律不认定为受管安装。
  来源：SDK 包内 `getActiveManagedInstallRoot()` 的实现与注释。

**设计含义**：官方那套受管安装与自更新逻辑无法被 pi-desk 程序化调用，只能经 CLI 触发；而 CLI 触发的前提是「当前运行的 SDK 已经在受管布局里」。因此首次迁移无论如何都要由 pi-desk 自己完成一次安装。

### 3.3 官方安装流程与制品通道（外部证据）

官方安装脚本给出的流程（可作为实现蓝本）：

1. 在受管根目录下建 staging 临时目录；
2. 从官方 installer 制品接口按版本拉取 `package.json` 与 `package-lock.json`；
3. 在 staging 目录执行 `npm ci`（省略开发依赖、包含可选依赖）；
4. **冒烟校验**：执行安装后的 CLI 入口并比对版本号，不一致即视为失败并丢弃 staging；
5. 原子重命名 staging 目录为 `releases/<版本>`；
6. 写入「当前版本」指针完成激活；
7. 清理旧版本，但**保留当前激活版本与正在运行的版本**——官方注释明确说明这是为了能够通过改写指针回滚。

来源：官方安装脚本（`pi.dev/install.sh` 原文）与 SDK 包内 `runManagedSelfUpdate`、`activateManagedRelease`、`pruneManagedReleases`。

制品通道方面：官方 installer 接口按版本提供 `package.json` 与 `package-lock.json`；lock 文件包含每个依赖的下载地址与完整性校验值。来源：官方安装脚本。

**设计含义**：这是一条带 lock、带校验、带冒烟与原子激活、且自带回滚手段的现成通道，没有理由自创替换逻辑。

### 3.4 更新执行的外部依赖（项目事实 + 外部证据）

- 扩展更新的执行路径依赖外部命令行工具：npm 源走 `npm install`，git 源走 git；SDK 更新走 `npm ci`。
  来源：SDK 包内 package-manager 模块。
- 使用的 npm 命令默认取自 PATH 的 `npm`，可由 Pi settings 的 `npmCommand` 字段覆盖。
  来源：SDK 包内 `getNpmCommand()`；settings schema 中确实存在 `npmCommand` 字段。
- 项目既有约定：图形界面启动的应用只拿到最小 PATH，不能假定 npm、git 这类工具可用；需要外部工具的能力要么改走 HTTP，要么在结果里区分「检查失败」与「没有变化」。
  来源：`.agents/memory/topics/gotchas/gui-launch-path.md`。

**设计含义**：检测环节可以完全无外部工具依赖（现有检测已经走 HTTP），但**执行环节无法绕开外部工具**。这是本设计中最硬的约束，必须在取舍 1 中正面处理。

### 3.5 其它相关项目事实

- 应用目录内的文件被其他进程持有时，改名与删除会失败；项目打包时已经因此踩坑。
  来源：`.agents/memory/topics/gotchas/portable-package-lock.md`。
- Pi 只在启动时读取配置，改动后需要重启 Runtime 才生效；项目已有「重启 Runtime 以重新加载」入口，且约定不为配置写入单独增加常驻重载按钮。
  来源：`.agents/memory/topics/conventions/pi-config-reload.md`。
- 版本检查的契约起点是「只读」：检查本身不写 Pi 配置、不安装也不更新任何东西；后来在同一份契约里加了三个显式动作（重新检查、更新扩展、安装内置 Pi agent），这三个动作都必须由页面主动发起，页面仍然不能指定查询地址、执行入口、安装路径或运行时目录。
  来源：`src/shared/updates-api.ts` 的契约注释与形状校验。
- 扩展来源分 npm、git、local 三类；local 源没有可比版本；项目级包在项目未被信任时会被 SDK 直接拒绝。
  来源：`src/update-check/index.ts`、SDK 包内 package-manager 模块的信任校验。

### 3.6 外部对照：VS Code 的扩展更新策略（外部证据）

VS Code 的做法：默认开启扩展自动更新；可全局或按扩展关闭；默认在发布后延迟一段时间（默认 12 小时）才自动安装；更新完成后提示重启扩展宿主；通过手动安装包（VSIX）装上的扩展默认关闭自动更新。

来源：VS Code《Extension Marketplace》官方文档。

**设计含义**：扩展更新在成熟产品里是「默认开 + 可关 + 延迟窗口 + 更新后提示重启」的组合。pi-desk 的扩展宿主就是会话所用的 SDK 宿主，「重启扩展宿主」对应现有的「重启 Runtime」。

## 4. 设计思路

### 4.1 线一：扩展更新

**职责划分**：主进程负责动作编排与状态广播；执行安装的动作放在一个新的受管一次性入口里（与现有版本检查脚本同一模式：入口与参数由调用点固定、页面不能指定），入口内部调用 SDK 的包管理能力执行更新，并把进度以结构化事件逐条输出；渲染端只负责展示与发起动作。

**要点**

- 用 SDK 的包管理接口执行更新，而不是让页面拼一条更新命令。理由：进度事件（开始/进行中/完成/失败，含动作与来源）是结构化的，按包更新与整体更新都能表达，失败原因也能被分类而不是只能读文本。
- 沿用现有受管入口的安全边界：参数由主进程固定给出、同一时刻只允许一次更新、超时与进程树终止由主进程负责、入口崩溃按协议错误处理。
- 契约扩展方向：现有契约的「读取快照」语义保持只读不变，新增的是「执行更新」这一动作及其状态流。动作与状态仍走纯形状校验，不引入 Node 能力到共享层。
- 失败分类至少覆盖：外部工具缺失（npm/git 不可用）、网络失败、项目未信任、来源为固定版本或本地源（无需更新）、单个包失败但其它包成功。
- 更新完成后提示重启 Runtime 才生效；存在活动会话时先说明影响，由用户决定何时重启。
- 策略上采用 VS Code 的组合：默认只提示、由用户点击执行；可另设「延迟自动更新」开关，默认关闭（取舍 4）。

**不采用的做法**：把更新实现成「让页面提交一条命令给 CLI 运行器执行」。理由是参数面会被页面影响，且只能拿到给人看的文本输出，无法做可靠的进度与失败分类。

### 4.2 线二：内置 Pi agent 更新

**核心是把 SDK 的加载位置从「只在应用包内」变为「应用自有数据区下的版本化目录 + 指针，应用包内版本兜底」。**

**加载解析**：由一个统一位置决定本次运行从哪个目录加载 SDK，四个受管入口共用同一结论。解析优先级：

1. 当前版本指针指向的发布目录里的 SDK 入口；
2. 指针缺失、目录不完整、入口文件不存在，或运行时入口加载失败时，回退到应用包内自带的版本。

加载失败的降级是有意的：宁可暂时少用一个新版本，也不要让应用起不来；降级原因只写诊断输出，不进协议通道。

**保留应用包内自带版本作为出厂兜底**，而不是把 SDK 从应用依赖中移除。理由：首次启动、离线环境、更新失败、运行时目录损坏四种情况下应用仍可用；同时它天然构成回滚路径。

**目录与隔离**：运行时根目录取应用自有数据区下的 `pi-runtime/`，内部是 `releases/<版本>/` 与 `current-version` 指针。**不与用户已安装的官方 Pi CLI 的受管安装目录（在 agent 目录下）混用**：若共用，在 pi-desk 内升级会改变用户命令行的版本，反之亦然，排障时会把问题来源搞混。

**更新流程**：完全复用第 3.3 节的官方流程（staging → 拉官方 lock 制品 → 安装 → 冒烟校验 → 原子激活 → 保留旧版本），由 pi-desk 自己执行，而不是依赖官方自更新。理由见 3.2 的设计含义。

**版本范围策略**：只安装与随应用发布的版本**同一主版本**的官方发布；跨主版本的升级不提供应用内安装，由新的应用发布带上。
理由是 pi-desk 深度依赖 SDK 的内部结构，冒烟校验只能证明「装好的 SDK 能加载」，
不能证明 pi-desk 依赖的会话运行时、扩展 UI 桥接与消息投影仍然兼容；
基线版本读不到或版本号无法解析时不拦，也不假装已经判定过。
检查结果里超出范围的版本标为 `unsupported`，只在界面上说明，不提供按钮；安装入口也独立再判一次，不依赖调用方。

**激活后**：常驻宿主已加载旧版本，必须重启 Runtime 才切换到新版本；有活动会话时先提示影响。

## 5. 关键取舍

| # | 决策 | 推荐与理由 | 替代项 | 影响 |
|---|---|---|---|---|
| 1 | 更新执行所需的 npm 从哪来 | **已采用**：使用系统 npm 或全局设置 `settings.json` 里的 `npmCommand`；不可用时明确报「缺少命令」并给出可复制的命令。理由：不增加分发体积，且符合项目既有「区分失败原因」的约定 | ①应用内置 Node 与 npm（自包含、离线可用，但分发体积与维护成本明显增加）；②只走 HTTP 按 lock 下载并自行解包（彻底摆脱外部工具，但需要自实现依赖布局与可执行链接语义，正确性风险高） | 决定「无 npm 的机器上能否安装」，也决定实现量 |
| 2 | 内置 SDK 的加载位置 | **已采用**：应用自有数据区下的版本化目录 + 指针，应用包内版本兜底 | ①只保留运行时目录里的版本（离线与首次启动不可用）；②继续只打包（等于不做更新） | 决定离线可用性与回滚能力 |
| 3 | 允许更新到哪个版本 | **已采用（主版本一致）**：只接受与随应用发布的版本同一主版本的官方发布，其余只提示不安装。理由：pi-desk 依赖 SDK 内部结构，冒烟校验不足以证明兼容 | 允许任意官方新版（省维护，但存在更新后应用直接不可用的风险） | 决定崩溃风险与长期维护成本 |
| 4 | 是否自动执行 | **已采用**：扩展默认只提示、点击执行；内置 Pi agent 安装一律需要用户确认。理由：两者都会中断活动会话，内置 SDK 升级还叠加兼容风险 | 两者都默认自动执行 | 决定是否会出现用户未预期的会话中断或崩溃 |

## 6. 架构与职责边界

- **主进程**：动作编排、入口与参数的固定、输入白名单校验（可选来源必须已经报告过）、快照与广播、运行时目录与 SDK 入口的解析结论。不直接执行任何安装动作。
- **受管入口执行器**：启动一次性入口、按行读取输出、超时终止进程树、校验退出码与结论；不理解协议内容，也不写任何配置。版本检查、扩展更新与内置 Pi agent 安装共用这一份。
- **受管一次性入口**：执行扩展更新与内置 Pi agent 安装，只输出结构化事件；不读页面输入，不决定路径。
- **共享契约层**：通道与动作状态的形状定义与校验，保持纯形状判定、不引入 Node 能力。
- **渲染端**：展示当前状态与进度、发起动作、呈现分类后的失败原因、提示重启 Runtime；不指定任何路径或参数。
- **依赖方向**：渲染端 → 共享契约 → 主进程 → 受管入口执行器 → 受管入口。受管入口是唯一接触安装动作的地方。

## 7. 风险与不可逆点

- **API 契约漂移（最大风险）**：pi-desk 编译期的类型来自打包时的 SDK 版本，运行期可能是另一个版本。冒烟校验只能证明安装产物能启动，不能证明 pi-desk 依赖的内部结构仍然兼容。缓解手段是取舍 3 的版本区间与指针回滚，但**无法完全消除**。
- **更新会中断活动会话**：常驻宿主持有会话，切换版本必须重启它。这是设计上无法回避的，只能通过「默认不自动执行 + 明确提示」降低意外。
- **外部工具缺失**：图形启动场景下 npm/git 不可用是常态而非异常，必须作为一等状态处理，不能退化成笼统的失败提示。
- **项目级扩展的信任边界**：项目未信任时更新会被 SDK 拒绝，这是既有边界，不应绕过。
- **与用户官方 Pi CLI 的目录冲突**：通过目录隔离规避；若未来决定共用目录，需要重新评估。
- **不可逆点**：无。所有改动都能通过「指针回退」或「回退到应用包内版本」恢复，不涉及数据删除。

## 8. 开发阶段

阶段只说明目标、设计关注点与前置依赖；具体实现、文件改动与操作方式在各阶段单独讨论。

**阶段一：扩展更新**

- 目标：把「检测到可更新」变成「可在应用内执行更新」。
- 设计关注点：受管入口的进度事件形状；失败分类的边界；契约从只读扩展为含动作时如何保持读取语义不变；更新与活动会话的时序（何时提示重启）；按包更新与整体更新的交互。
- 前置依赖：无。不涉及 SDK 布局迁移，是本设计中最先可交付的部分。

**阶段二：运行时迁移与内置 Pi agent 安装**

- 目标：SDK 能从运行时目录加载且自带版本兜底生效；同时具备把官方发布安装到运行时目录的能力，并由页面显式触发。
- 设计关注点：四个入口的 SDK 解析方式统一到单一结论；编译期类型与运行期版本不一致时的处理方式；离线与首次启动行为；指针与目录完整性校验；加载失败的降级路径；安装流程的原子性与失败不切指针；进度与失败原因的呈现；重启 Runtime 才生效的提示。
- 前置依赖：阶段一完成（复用同一套受管入口模式与契约扩展方式），且取舍 1、2 已定。

**阶段三：版本区间策略与回滚交互**

- 目标：把「装到哪个版本」变成一个可控策略，并给用户一条明确的后退路径。
- 设计关注点：兼容区间的表达与维护（取舍 3）；指针回退与旧版本保留策略；降级原因的可见性（当前只写诊断输出）；进度与失败呈现的细化。
