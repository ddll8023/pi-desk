# 版本与更新：开发交接文档

## 1. 用途与范围

这份文档用于把「版本与更新」这条子系统的现状、边界与继续开发的落点交接给新的开发者。

覆盖范围：应用自身版本的展示、内置 Pi agent（随应用发布的 SDK）的版本检查与安装、Pi 包（扩展）的版本检查与更新，以及这三件事用到的契约、子进程与落盘位置。

不在范围内：pi-desk 的其余功能（项目管理、会话、消息投影、扩展 UI、认证、模型配置等），以及应用自身的自动更新（当前不做）。项目级的约定与坑统一记在 `.agents/memory/`，本文只做索引，不重复其内容。

## 2. 功能现状

### 2.1 三条版本线

| 版本线 | 版本从哪来 | 能做什么 |
|---|---|---|
| 应用自身（Pi Desktop） | `package.json` 的 `version`，运行时由 `app.getVersion()` 给出 | 只展示（含 Electron、平台、架构）；没有「检查应用自身是否有新版」的能力 |
| 内置 Pi agent | 受管入口实际加载的 SDK 版本：有可用运行时目录时取它，否则取随应用发布的版本 | 展示实际版本与官方最新版本；可在应用内安装官方发布到运行时目录 |
| 扩展（Pi 包） | Pi 的包声明（`settings.json` 的 `packages`）；npm 源比版本号，git 源比提交短哈希，local 源不比较 | 展示已安装与远端版本；可在应用内更新；可开启启动时自动更新 |

### 2.2 五类动作

- **检查**：只读。读取三条版本线的当前状态与远端最新状态，形成快照供界面展示；启动时后台自动跑一次，之后可由界面触发重查。
- **更新扩展**：更新 Pi 已声明的包。只更新已安装的内容，不改动包声明本身。
- **自动更新扩展（可选）**：设置页的「启动时自动更新扩展」开关为开时，启动检查发现可更新条目就自动执行一次更新，与手动更新走同一条链路、共用同一个执行槽；手动重查一律不触发它。
- **安装内置 Pi agent**：把官方发布安装到应用自有的运行时目录，并切换「当前版本」指针。不写 Pi 的配置文件，也不影响系统里用官方 installer 装的 Pi。
- **修复运行时回退**：仅在「指针版本 ≠ 实际加载版本」时可用，两个动作：重装指针指向的那个版本（复用安装流程），或清除指针回到随应用发布的版本。两者都只写应用自有的运行时目录；清除只删指针文件，不删已安装的发布目录。

### 2.3 内置 Pi agent 的版本来源与优先级

1. 运行时目录中「当前版本指针」指向的发布目录里的 SDK 入口；
2. 指针缺失、发布目录不完整、入口文件不存在，或该入口加载失败时，回退到应用自带的版本。

回退是为了让应用始终可用：宁可暂时少用一个新版本，也不让应用起不来。回退原因会写进诊断输出（stderr），并可通过「指针版本 ≠ 实际加载版本」在设置页看到提示；设置页同时提供上面的两个修复动作。

注意两个口径不同：检查快照里的版本是一次性进程真的加载一次 SDK 得到的，代表「下次启动会加载的版本」；设置页「运行中宿主」一行才是当前宿主进程实际用的版本。两者不同时说明还没重启 Runtime。

### 2.4 版本范围策略

内置 Pi agent 只安装与**随应用发布的版本同一主版本**的官方发布。跨主版本的升级不提供应用内安装，需要新的应用发布。

理由：pi-desk 深度依赖 SDK 的内部结构（会话运行时、扩展 UI 桥接、消息投影等），安装后的冒烟校验只能证明「装好的 SDK 能加载并报出版本号」，不能证明这些内部结构仍然兼容。

策略在两处独立判定：检查阶段把越界版本标为 `unsupported`（界面只提示、不给按钮），安装入口在执行前再判一次（不依赖调用方）。基线版本读不到或版本号无法解析时**不拦**，也不假装已经判定过。

## 3. 代码地图

### 3.1 主进程

| 文件 | 职责 | 不该由它承担 |
|---|---|---|
| `src/main/update-checker.ts` | 版本检查的编排：快照缓存、广播、失败时保留上一次成功的结论 | 不做进程的启动与超时管理（交给 3.2） |
| `src/main/package-updater.ts` | 扩展更新的编排：进度广播、结论解析、单次执行 | 不校验要更新的来源是否合法（由 IPC 处理器校验） |
| `src/main/pi-agent-updater.ts` | 内置 Pi agent 安装与运行时指针清除的编排，同上；清指针不启动子进程 | 不决定运行时目录与目标版本；安装进行中时拒绝清指针 |
| `src/main/managed-entry-runner.ts` | 受管一次性入口的通用执行：启动、按行缓冲、超时终止进程树、退出码与结论校验；`SingleFlight` 保证同一时刻只跑一次 | 不理解协议内容、不写配置 |
| `src/main/process-tree-termination.ts` | 子进程树的终止（POSIX 进程组信号；Windows 定向 taskkill） | 不判定成败、不等待退出 |
| `src/main/pi-cli-process.ts` | 受管入口的定位与启动；入口文件名与产物目录在这里固定，参数由调用点给出 | 不判定成败；失败分类与超时终止由调用方负责 |
| `src/main/pi-runtime.ts` | 运行时根目录（`userData/pi-runtime`）与受管进程的 SDK 入口注入值 | 不创建目录、不安装、不改指针 |
| `src/main/pi-paths.ts` | agent 目录与环境注入（含运行时入口）；agent 目录与运行时入口都不接受调用方覆盖 | 不读取其他配置 |
| `src/main/index.ts` | IPC 通道注册、入参白名单、进度与快照广播、启动时的一次检查与按开关执行的一次自动更新 | 不直接执行安装动作 |

### 3.2 受管一次性入口（`vite.sdk-host.config.ts` 的构建入口）

| 产物 | 源文件 | 作用 |
|---|---|---|
| `out/sdk-host/index.mjs` | `src/sdk-host/index.ts` | 常驻 SDK 宿主（`utilityProcess`），持有会话；在 ready 帧里回报 `sdkVersion` |
| `out/sdk-host/pi-cli.mjs` | `src/pi-cli/index.ts` | 一次性 CLI 运行器：资源与模型预读（`--mode rpc`）、MCP 探测（`mcp list --json`） |
| `out/sdk-host/update-check.mjs` | `src/update-check/index.ts` | 一次性版本检查，输出一行 JSON 结论 |
| `out/sdk-host/package-update.mjs` | `src/package-update/index.ts` | 一次性扩展更新，输出带标记的进度与结论行 |
| `out/sdk-host/runtime-install.mjs` | `src/runtime-install/index.ts` | 一次性内置 Pi agent 安装，输出带标记的进度与结论行 |

`src/auth-helper/index.ts` 由另一份构建配置产出，属于认证子系统，但同样通过下面的 `loadSdkModule()` 加载 SDK。

### 3.3 运行时布局与 SDK 加载（受管入口共用）

`src/runtime-install/runtime.ts` 是这一层的唯一实现：

- 布局常量：`releases`、`staging`、`current-version`、SDK 包名、入口注入变量名。
- 路径拼装：`releasesRoot`、`releaseDir`、`stagingRoot`、`pointerPath`。
- 指针读写：`readCurrentVersion`、`writeCurrentVersion`（同目录临时文件 + 改名）、`clearCurrentVersion`（只删指针文件，返回被清掉的版本）。
- 入口解析：`resolveSdkEntryInRelease(releaseDir, 期望版本)` 读包声明的 `exports['.'].import`（回退 `main`），校验声明的版本与入口文件存在；`resolveActiveRuntime(root)` 组合指针与解析结果。
- SDK 加载：`loadSdkModule()` —— 有入口注入时加载它，否则加载应用自带的版本；注入的入口加载失败时回退到自带版本并写 stderr。
- 版本工具：`isValidReleaseVersion`、`majorVersion`、`readBundledSdkVersion(entryUrl)`（从受管入口位置向上两级读自带包声明）。

**约定**：这个模块**不引用 `import.meta`**（`readBundledSdkVersion` 的 URL 由调用方传入）。原因是主进程也会打包它，而主进程产物不是 ESM。

### 3.4 共享契约与渲染端

| 文件 | 职责 |
|---|---|
| `src/shared/updates-api.ts` | 通道与事件常量、协议行标记、全部载荷形状与运行时校验、`UpdatesApi` 接口。**同时被主进程、preload 与沙箱页面加载，因此必须保持无 Node 能力** |
| `src/preload/index.ts` | 桥接 `UpdatesApi` 的方法（含重装与清除指针）；所有进出载荷都过形状校验，不符即丢弃或返回 `INVALID_RESPONSE` |
| `src/renderer/src/services/updates.ts` | 桥接调用包装，把桥接缺失与调用异常转成统一的失败结果 |
| `src/renderer/src/stores/updates.ts` | 检查快照、扩展更新、内置 Pi agent 安装与运行时指针清除四套状态（进行中、进度列表、结论、失败原因）、启动提示开关；动作结束后重新检查一次；启动时自动执行的更新不是本页发起的，靠事件把进度与结论收敛到同一套状态 |
| `src/renderer/src/components/VersionUpdateSection.vue` | 设置页的「版本与更新」区块：展示、按钮、启动时自动更新开关、进度、失败分开展示、运行时回退提示与修复按钮、重启 Runtime 提示；由 `SettingsView.vue` 挂载 |
| `src/renderer/src/components/UpdateNoticeDialog.vue` | 启动时的一次性提示，只提示「有可更新的扩展」；由 `App.vue` 挂载 |

## 4. 数据与落盘位置

### 4.1 运行时目录（内置 Pi agent）

```
<Electron userData>/pi-runtime/
├── current-version          # 当前版本指针，内容是一行版本号
├── releases/<版本>/         # 一次安装的完整 npm 工程（package.json、package-lock.json、node_modules/）
└── staging/install-<pid>-<时间戳>/   # 安装中间态；失败或中断后由下一次安装清理
```

- `<Electron userData>` 由 `app.getPath('userData')` 给出，与桌面配置 `desktop-config.json` 同级；不写进 Pi 的 agent 目录，以便与用户用官方 installer 装的 Pi（其受管安装目录在 agent 目录下）保持隔离。
- 发布目录里的 SDK 位于 `<发布目录>/node_modules/@earendil-works/pi-coding-agent`。
- `releases` 下的其他版本会在安装成功后清理，只保留当前版本与切换前的那一个（回滚用）。

### 4.2 Pi 的目录与扩展安装位置

- agent 目录：`PI_CODING_AGENT_DIR`，未设置时为 `<home>/.pi/agent`。由应用统一解析并注入给所有受管进程。
- 扩展安装位置（由 SDK 决定，本应用不自行拼装）：
  - npm 源、用户级：`<agentDir>/npm/node_modules/<包名>`
  - npm 源、项目级：`<项目>/.pi/npm/node_modules/<包名>`
  - git 源、用户级：`<agentDir>/git/<host>/<path>`
  - git 源、项目级：`<项目>/.pi/git/<host>/<path>`
- 项目级包所在的存储只在项目被信任后才可访问，否则 SDK 直接拒绝。

### 4.3 应用自身的配置

`desktop-config.json`（Electron `userData` 下）保存最近项目、界面偏好、窗口状态、信任决定等；本子系统的检查与安装只读它，不写。唯一的例外是「启动时自动更新扩展」开关：它存在同一份文件的 `extensionAutoUpdate` 字段（缺省关），由偏好通道读写，本子系统只读该字段来决定启动时要不要自动更新。

## 5. 契约与通信

### 5.1 通道与事件

| 常量 | 值 | 方向 | 参数与含义 |
|---|---|---|---|
| `UPDATES_GET_CHANNEL` | `desktop:updates-get` | invoke | 零参；读最近一次检查的快照，不触发检查 |
| `UPDATES_CHECK_CHANNEL` | `desktop:updates-check` | invoke | 零参；重查一次，进行中时复用 |
| `UPDATES_STATE_EVENT` | `desktop:updates-state` | event | 快照变化（开始检查与结束各一次） |
| `UPDATES_UPDATE_CHANNEL` | `desktop:updates-update` | invoke | 可选一个来源字符串；省略表示全部已声明的包 |
| `UPDATES_UPDATE_PROGRESS_EVENT` | `desktop:updates-update-progress` | event | 扩展更新进度 |
| `UPDATES_UPDATE_OUTCOME_EVENT` | `desktop:updates-update-outcome` | event | 扩展更新结论（含启动时自动执行的那一次） |
| `UPDATES_INSTALL_AGENT_CHANNEL` | `desktop:updates-install-agent` | invoke | 可选一个版本号；省略表示官方最新 |
| `UPDATES_INSTALL_AGENT_PROGRESS_EVENT` | `desktop:updates-install-agent-progress` | event | 内置 Pi agent 安装进度 |
| `UPDATES_REINSTALL_AGENT_CHANNEL` | `desktop:updates-reinstall-agent` | invoke | 一个版本号（必填，且必须等于快照的 `piAgent.runtimeVersion`）；只用于回退修复 |
| `UPDATES_RESET_AGENT_RUNTIME_CHANNEL` | `desktop:updates-reset-runtime` | invoke | 零参；清除运行时指针，只用于回退修复 |

所有 invoke 都要求调用方是当前唯一可信窗口；事件只发给该窗口。

自动更新开关不走本子系统的通道，而走偏好通道：`desktop:preferences-get-auto-update` / `desktop:preferences-set-auto-update`，存储与校验由偏好子系统负责（见 4.3）。

### 5.2 入参白名单（主进程侧）

- 扩展更新：来源必须出现在最近一次检查快照的 `extensions[].source` 里。
- 内置 Pi agent 安装：版本必须等于快照里 `piAgent.latestVersion`，且 `piAgent.status` 必须是 `update-available`。省略版本号时由安装入口取官方最新。
- 运行时重装：参数必须等于快照里 `piAgent.runtimeVersion`，且快照必须处于回退（`runtimeVersion` 非空且与 `version` 不同）。
- 清除运行时指针：同样要求快照处于回退；执行前再判一次安装是否在进行（在跑时拒绝，避免与指针写入竞态），指针已不在时返回 `INVALID_REQUEST`。
- 上述通道都不接受多余参数；不满足即返回 `INVALID_REQUEST`。

### 5.3 协议行（受管入口 → 主进程）

扩展更新与内置 Pi agent 安装的入口，其 stdout 上既有协议行也可能混有依赖命令的输出（扩展更新场景下 npm 由 SDK 启动，无法控制其 stdio）。因此：

- 协议行格式：`<标记><一行 JSON>`，且每行前会先补一个换行，避免与没有换行的依赖输出拼成同一行。
- 标记：扩展更新 `PI_PACKAGE_UPDATE `，内置 Pi agent 安装 `PI_AGENT_INSTALL `。
- 主进程只解析带标记且能通过形状校验的整行；结论取最后一条能通过校验的结果行。
- 版本检查脚本是另一套：它输出一行完整 JSON，主进程取 stdout 的最后一个非空行解析。

### 5.4 快照与结论形状

快照 `UpdatesSnapshot`（在结论上叠加 `checking`）：

- `offline`：处于 `PI_OFFLINE` 语义，未做远端查询。
- `checkedAt`：上一次成功检查的时刻；没有成功过为 null。
- `piAgent`：`{ version, runtimeVersion, latestVersion, note, status, error }`；`status` 取值 `up-to-date` / `update-available` / `unsupported` / `unchecked`。
- `extensions[]`：`{ source, scope, type, displayName, installedVersion, latestVersion, status, error }`；`status` 取值 `up-to-date` / `update-available` / `not-installed` / `pinned` / `local` / `unchecked`。
- `error`：整体失败原因；单个条目失败写在各自的 `error` 里。

动作结论：

- 扩展更新 `PackageUpdateOutcome`：`{ offline, updated[], failed[{ source, reason, message }], error }`；`reason` 取值 `tool-missing` / `network` / `untrusted` / `unknown`。
- 内置 Pi agent 安装 `AgentInstallOutcome`：`{ offline, installedVersion, previousVersion, reason, error }`；`reason` 取值 `tool-missing` / `network` / `verify-failed` / `unsupported-version` / `unknown`。重装复用同一形状与同一套进度事件。
- 清除运行时指针 `AgentRuntimeResetOutcome`：`{ clearedVersion }`；没有进度事件，失败时用同一个错误包装。

进度事件：

- 扩展更新 `{ phase, action, source, message }`；`phase` 沿用 SDK 的 `start` / `progress` / `complete` / `error`，`action` 为 `install` / `remove` / `update` / `clone` / `pull`。
- 扩展更新结论 `PackageUpdateOutcome`：一次更新结束时广播一次；手动更新也能从 invoke 返回值拿到同一份结论，两条路径写的是同一个展示字段。
- 内置 Pi agent 安装 `{ phase, version, message }`；`phase` 为 `download` / `install` / `verify` / `activate` / `done`。

失败结果的包装在两层：主进程侧统一为 `{ ok: false, error: { code, message } }`（执行失败多为 `INTERNAL_ERROR`）；渲染端的服务层另外区分 `BRIDGE_UNAVAILABLE`（桥接不存在）与 `BRIDGE_CALL_FAILED`（调用抛错），preload 侧不符合契约时返回 `INVALID_RESPONSE`。

## 6. 环境与外部依赖约束

- **外部命令**：扩展更新与内置 Pi agent 安装都要执行外部命令（npm；git 源还需要 git）。扩展更新由 SDK 内部启动 npm/git；安装入口自己启动 npm，并优先读 Pi 全局设置 `settings.json` 的 `npmCommand`，否则用 PATH 里的 `npm`，并先跑一次 `--version` 探测可用性。
- **PATH 约定**：图形界面启动的应用只拿到最小 PATH，不能假定 npm、git 可用。因此**检测一律走 HTTP**（npm registry、pi.dev、git `ls-remote`），只有执行才用外部命令，并且必须把「命令缺失」与「没有变化」分成不同状态。见 `.agents/memory/topics/gotchas/gui-launch-path.md`。
- **离线**：`PI_OFFLINE`（`1` / `true` / `yes`）生效时不做任何远端请求，安装与更新直接跳过并如实报告。
- **项目信任**：项目级扩展的读写受 Pi 的信任边界约束，未信任时报错，不应绕过。
- **打包布局**：受管入口产物固定在 `<应用根>/out/sdk-host/`（打包后为 `resources/app/out/sdk-host/`）。`readBundledSdkVersion` 依赖这一相对位置（`../../node_modules/...`）找随应用发布的 SDK；改动产物目录会同时影响它与 SDK 的模块解析。
- **模块格式**：主进程产物是 CJS，受管入口产物是 ESM。`import.meta` 只能出现在 ESM 产物里；被两边共用的模块（如 `src/runtime-install/runtime.ts`）不得引用它。
- **SDK 解析**：`vite.sdk-host.config.ts` 把 `@earendil-works/pi-coding-agent` 设为 external，受管入口用裸模块名或注入的入口 URL 加载它；因此生产依赖必须落在应用目录的 `node_modules` 下（见 `electron-builder.yml` 的说明）。
- **打包时的目录占用**：Windows 上应用目录内的文件被其他进程持有时，改名与删除会失败；这是出包时的既有坑，见 `.agents/memory/topics/gotchas/portable-package-lock.md`。
- **生效时机**：Pi 只在启动时读配置，扩展更新或 SDK 版本切换后需要重启 Runtime 才生效；目前界面只给提示，重载入口在「Pi 资源」页。见 `.agents/memory/topics/conventions/pi-config-reload.md`。

## 7. 子进程与并发语义

`executeManagedEntry()` 是三个编排器共用的骨架：

- **启动**：调用方给出 `spawn()`，入口与参数由调用点固定；页面无法指定入口、可执行文件或参数。
- **读取**：stdout 按行缓冲，只保留未结束的一行；超过 1 MiB 的残行直接丢弃（协议行都很短），因此内存不随依赖输出增长，也不会因为输出总量大而误判失败。
- **逐行处理**：`onLine` 抛错会被当作真失败：报明确原因并终止进程树，避免回调异常拖垮主进程。
- **超时**：超时后先 `SIGTERM` 收进程树，宽限期内未退出再 `SIGKILL`。三个超时分别独立：版本检查 30 秒、扩展更新 10 分钟、内置 Pi agent 安装 15 分钟。
- **结论判定**：退出码非 0、被信号结束、正常退出但拿不到结论，都属于失败；失败文案由 `label`（「版本检查」/「扩展更新」/「内置 Pi agent 安装」）拼装。
- **stderr**：只保留尾部 600 字符用于诊断，不进入结果；安装入口会把自己的 stdout 全部转到 stderr，避免污染协议通道。
- **并发**：`SingleFlight` 保证同一时刻只跑一次；并发调用复用进行中的那一次，不排队、不叠加。三个编排器各自持有一个执行槽。启动时的自动更新与手动更新共用同一个扩展更新执行槽，因此不会并发跑两次。
- **失败不破坏现状**：检查失败时保留上一次成功的快照（含它自己的 `checkedAt`），只把本次原因写进 `error`；安装失败时不切换指针，旧运行时继续可用。

## 8. 排查指南

| 现象 | 先看什么 |
|---|---|
| 设置页显示的是随应用发布的版本，但明明装过运行时版本 | 读 `<userData>/pi-runtime/current-version` 与对应 `releases/<版本>/node_modules/@earendil-works/pi-coding-agent/package.json`：指针是否合法、版本是否一致、入口文件是否存在。界面在「指针版本 ≠ 实际加载版本」时也会给出提示 |
| 装完之后版本没变 | 运行时目录只在子进程启动时被解析，且 Pi 只在启动时读配置：需要重启 Runtime（「Pi 资源」页的重载入口）。另外确认 `current-version` 是否被切到了新版本 |
| 扩展更新报「缺少命令」 | 图形启动下 PATH 可能没有 npm（git 源还需要 git）。检查 Pi 全局 `settings.json` 的 `npmCommand`、或让用户在终端确认 npm 可用 |
| 扩展更新报「项目未信任」 | 项目级包需要项目已被信任；这是 Pi 的既有边界，不是缺陷 |
| 安装失败且原因含「校验未通过」 | 依赖装上了但加载候选 SDK 失败：staging 目录会在下次安装前被清理，指针未切换，可重试 |
| 安装失败且原因含「版本不在支持范围」 | 目标版本与随应用发布的版本主版本不一致；这属于预期行为，需要新的应用发布 |
| 安装目录里出现 `staging/install-*` 残留 | 上一次安装中断；下一次安装会自动清理，不必手工干预 |
| 端口/服务侧的 `release/` 出包失败并留下 `.tmp` | 与本文无关的既有坑，见 `.agents/memory/topics/gotchas/portable-package-lock.md` |
| 怀疑运行中的宿主用的是哪个 SDK 版本 | 「版本与更新」区块里的「运行中宿主」一行就是宿主实际加载的版本；它与「Pi agent（内置）」那一行不同时，说明重启 Runtime 后才会切换 |

## 9. 常见改动的落点

**新增一个受管一次性入口**：

1. 新建入口源文件（放在与其他入口同级的目录下）；
2. `vite.sdk-host.config.ts` 的 `rollupOptions.input` 增加一项（决定产物名）；
3. `src/main/pi-cli-process.ts` 增加入口文件名常量、路径函数与启动函数；
4. `tsconfig.node.json` 的 `include` 增加该目录（否则类型检查不覆盖它）；
5. 在主进程编排里通过 `executeManagedEntry()` 调用。

**新增一个 IPC 动作**（本子系统现有动作都走这条链路）：

1. `src/shared/updates-api.ts`：通道常量、载荷类型与运行时校验、`UpdatesApi` 方法；
2. `src/main/index.ts`：注册处理器（可信调用方校验 + 入参白名单 + 调编排层），必要时广播事件；
3. `src/preload/index.ts`：桥接方法（对返回值与事件载荷都做形状校验）；
4. `src/renderer/src/services/updates.ts`：包装调用，统一桥接失败语义；
5. `src/renderer/src/stores/updates.ts`：状态与动作（注意进行中状态、结束后是否要重新检查）；
6. 组件：展示与触发。

**改动运行时布局**（目录名、指针文件名，或发布目录内的相对位置）：

- 同时改 `src/runtime-install/runtime.ts`（唯一布局来源）与使用方；`src/main/pi-runtime.ts` 只负责给根目录。
- 指针与发布目录的语义参考 Pi 官方受管安装（`<agentDir>/install`，同样用 `releases/<版本>` + `current-version`），但本应用的目录与其隔离，不要合并。

**改动契约形状**：`src/shared/updates-api.ts`、`src/preload/index.ts`、`src/main/index.ts` 三处必须同步；渲染端与服务层只消费，不自行放宽。
