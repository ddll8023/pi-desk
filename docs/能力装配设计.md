# 能力装配设计

本文是 pi-desk 能力层（扩展、技能、专家、MCP 服务器）如何在会话中装配、收窄与诊断的初步设计，说明后续演进方向与边界。不描述逐文件实现，也不代替各阶段开发时的详细讨论。

## 1. 名词约定

| 术语 | 含义 | 代码或配置对应 |
| --- | --- | --- |
| 能力 | 会话中可用的一项受控资源：技能、MCP 服务器、扩展工具 | 技能目录、`mcp.json`、扩展模块 |
| 能力单元 | 可独立声明、启停与收窄的最小装配对象 | `bundle.json` 条目、专家定义 |
| 组合清单 | 决定「某会话有哪些能力」的唯一声明来源 | 待建立 |
| 许可集 | 某个会话允许装载的能力标识集合，`null` 表示不限制 | `skillPermit`、专家能力范围 |
| 能力面 | 能力对用户与设置页暴露的装配、裁剪与诊断界面 | 设置页资源分节、专家分节 |
| 内核 | 不由插件决定的运行时职责：agent loop、会话与压缩、模型接入、界面 | Pi SDK 宿主进程 |
| 缺席诊断 | 说明某项能力为何不在当前会话生效的结构化条目 | `ResourceIssue` |

## 2. 问题与已确认需求

现状有三类问题，都是「同一事实存在多个写入方」的具体形态：

1. **能力声明分散**。决定「某能力在当前会话是否可用」的来源有四处：产品资源清单、用户设置的包与扩展、技能目录扫描、专家能力范围。另有一份按执行模式剔除的名单。想回答「这个技能为什么没加载」需要顺着四处推理。
2. **扩展不参与裁剪**。技能与 MCP 服务器可按专家与执行模式收窄，扩展没有对应通道；一旦需要按会话关掉一个扩展，只能改产品代码。
3. **同一契约多处重写**。专家能力字段在设置页契约、会话视图、定义解析与保存接口里各声明一遍，改一个字段要同步多处，漏改不会编译报错、只会静默失效。

已确认需求：能力单元的声明、启停、裁剪与诊断应收敛为一等公民；扩展与技能的分工保持不变。

## 3. 目标、范围与不做项

**目标**：新增一项能力（含需随会话变化的）时，改动落在能力自己的声明与实现内，不扩散到无关模块；某能力缺席时能给出可读原因。

**范围内**：能力契约单一来源、扩展纳入许可集、组合清单收敛、能力自带使用时机描述。

**不做项**：

| 方向 | 不做原因 |
| --- | --- |
| 取消扩展与技能的分工，一切写成可执行插件 | 技能的价值是不执行代码、按需加载、可跨宿主移植；合并后失去可移植性与渐进披露 |
| 内核插件化（loop、模型接入、界面、权限策略都可替换） | 会重写 Pi SDK 已承担的会话、压缩与资源加载，收益仅是可换模型层，而该能力已由 provider 机制提供 |
| 权限与安全策略作为可移除的插件 | 安全策略可被组合删除，等于默认不设防；最小权限必须留在不可移除的内核 |
| 引入 Profile／Bundle／Patch 三层组合配置 | 组合面会原样进到设置页，桌面用户需理解装配规则才能判断能力为何不生效 |

## 4. 事实与依据

同为「加一项能力」，仓库内的改动面差异来自能力是否被清单承载：

| 工作类型 | 示例性质 | 改动面 |
| --- | --- | --- |
| 由技能或扩展承载 | 记忆常驻背景、规则去重 | 3–6 个文件，且全部在 `resources/agent/` |
| 需要界面与 IPC 参与 | 专家编辑、专家能力范围 | 14–26 个文件，横穿共享契约、共享进程、主进程、preload、宿主与渲染进程六层 |

结论：产品面能力的耦合根因是缺少纵向切片边界，而不是缺少插件机制。另一处成因是同一契约在多层重写——专家能力字段曾在六个接口、三处模式别名中重复。

内核插件化不可行的依据是运行时归属：宿主进程内的会话、压缩、JSONL 历史、资源加载与 provider 认证均由 Pi SDK 承担，替换意味着自建运行时。

## 5. 推荐方向：能力组合面

三个支点，按依赖顺序：

1. **契约单一来源**。一个能力的跨进程字段结构只在一处声明，其余层引用类型，只保留进程边界上的显式白名单拷贝。
2. **能力自带描述与裁剪**。扩展通过工具自带的提示片段说明「何时使用」，不再由产品集中段落代述；扩展与技能一样进入许可集，可按会话收窄。
3. **组合清单单一来源**。四处来源合并为一份可查询的清单，每条能回答「来自哪里、作用于哪个范围、为什么当前不生效」。

## 6. 职责边界

| 层 | 职责 | 不承担 |
| --- | --- | --- |
| 共享契约 | 字段结构、通道与错误码的唯一声明 | 解析规则、默认值、业务判断 |
| 共享进程 | 定义解析、许可集计算 | 装配会话、注入提示 |
| 主进程 | 通道注册、文件读写、白名单投影 | 解析规则与许可语义 |
| 宿主进程 | 按许可集装配资源、产出缺席诊断 | 决定许可集内容 |
| 渲染进程 | 展示与编辑，能力状态归能力自己的 store | 跨能力的目录状态、路径拼接 |

依赖方向单向：契约 ← 共享进程 ← 主进程／宿主；渲染进程只依赖契约与自己的 store。

## 7. 关键取舍与约束

**取舍一：集中式提示段落与扩展自带描述并存。** 集中段落的收益是措辞统一、便于审查；分散到扩展的收益是随启停自动消失，不会在工具下线后仍残留使用指引。当前保留集中段落，下沉是有条件的演进。

**取舍二：许可集只作用于能力，不作用于权限。** 收窄能改变模型看得见什么，不改变它被允许做什么；两者混在一处会让「关闭一个能力」变成「放宽一次授权」。

**约束（可校验）**：

1. 纯能力改动只落 `resources/agent/**` 与资源清单，不碰源码。
2. 需要界面参与的能力允许跨层，但字段只在共享契约声明一次。
3. 进程边界的字段拷贝保持显式，不用类型复用代替拷贝。
4. 权限与安全策略不进入许可集，不做成可关闭项。

## 8. 风险与待定问题

| 项 | 状态 | 说明 |
| --- | --- | --- |
| 组合清单会新增一个中心 | 非阻塞假设 | 清单本身若布局成跨层契约，会复制旧的散落模式；须遵守约束 2 |
| 缺席诊断覆盖不足 | 待定 | 现有诊断只覆盖加载失败与工具名冲突，未覆盖「被许可集排除」 |
| 用户侧组合推理成本 | 待定 | 能力可裁剪后，设置页需要能回答「为何不生效」，否则可解释性下降 |
| 集中段落的下沉退出条件 | 待定 | 条件为不再存在跨能力的编排需求，届时再评估 |
