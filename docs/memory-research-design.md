# 记忆系统调研与方案设计

## 1. 文档定位

本文整理记忆系统的当前实现事实、外部借鉴线索与候选优化方向。

首阶段已完成全局词法索引、统一检索与定向读取工具、配套发布资源及桌面工具语义展示。**本文关于后续阶段（如请求前按任务自动召回）的内容仍属方案设计，不构成开发或执行授权。实施前须明确需求边界并取得逐文件执行清单批准。**

第三方能力和历史实现仅作为事实与参考，不自动成为必须保留或新增的需求。

## 2. 问题与目标方向

讨论围绕以下问题展开：

- 如何让相关记忆在运行过程中主动进入上下文，而不是完全依赖模型记得搜索？
- 是否需要新增工具、MCP 服务，或者引入 OpenViking 一类系统？
- DSH 接入网站和 QQ 后，记忆究竟由消息渠道、宿主程序还是模型调用？
- 如何在提高召回可用性的同时，控制无关内容、历史误用和写入权限？

候选目标是：在模型处理任务前提供必要背景和相关记忆，保留深入读取能力，并让来源、适用范围与失败状态可解释。不以“调用过工具”代表模型理解或遵守，也不承诺检索必然命中。

## 3. 当前实现事实

### 3.1 组件与所有权

当前记忆能力由以下组件协作：

| 组件 | 当前职责 |
| --- | --- |
| Memory Skill | 统一管理工作日记、项目知识、月度总结与画像，规范查询、整理与两阶段保存流程 |
| 用户级 `pi-memory` 扩展 | 请求级背景注入、记忆工具注册、会话控制与保存审批通道 |
| Python 文件引擎 | 用户级数据读写、两阶段保存计划与事务、全局派生索引（含检索与规则索引）及词法排序 |
| `pi-skill-setup` | 配套发布资源、指纹清单与跨机配置对齐，保持 Skill、扩展与引擎版本一致 |
| pi-desk 桌面端 | SDK 宿主、截断前工具语义摘要提取、实时/历史投影与结果优先卡片展示 |

共享扩展与配套资源的统一维护源位于 `~/.pi/agent/skills/pi-skill-setup/assets/`；实际 agentDir 下的 `extensions/pi-memory/` 是部署副本，不应作为另一套独立维护源。

pi-desk 通过 `src/main/shared/pi-paths.ts` 解析 agentDir，并在 `src/sdk-host/session-runtime.ts` 创建 SDK 会话服务；桌面端提供工具摘要投影与卡片展示，但扩展本身作为用户级通用扩展运行。

### 3.2 数据边界

| 数据域 | 当前权威位置 | 用途 |
| --- | --- | --- |
| 工作日记 | `~/.agents/memory-store/daily/` | 按日期、项目记录事件、进展、决定和约束，统一全局存储 |
| 个人画像 | `~/.agents/memory-store/profile/` | 按领域与作用域保存偏好 |
| 月度总结 | `~/.agents/memory-store/monthly/` | 关联日记来源的历史回顾 |
| 派生索引 | `~/.agents/memory-store/index/` | 记录定位、当前有效规则、月份及全局词法检索（`search.json`） |
| 项目知识 | `<项目根>/.agents/memory/` | 独立可选域：维护项目现行约定、特殊配置、选型理由和棘手问题 |

用户库通过 Markdown 正文与 JSON 项目表、派生索引组织数据。项目知识是独立可选域，不自动复制进用户库，也不作为全局日记查询的前置。未建立项目知识目录不影响全局记忆检索。

### 3.3 自动读取与工具

当前扩展在 `context` 钩子中为每次模型请求提供独立背景消息，内容主要是适用画像和项目索引：

- 不覆盖系统提示词，不改写用户输入。
- 自动召回正文不追加到持久会话历史；显式工具结果仍按宿主工具消息机制处理。
- 画像使用内存缓存，来源变化时刷新；项目索引按请求读取。
- **自动背景当前尚未接入按任务问题自动检索日记或规则**；自动召回仍属待设计的后续能力。

当前工具能力包括：

- `memory_search`：默认按任务检索全局已保存日记，支持中文词法相关度排序、明确项目过滤、近期／月摘要模式与分页。
- `memory_rules`：默认查询全局各项目当前有效决定与约束，支持明确项目过滤与词法匹配，不受近期窗口限制。
- `memory_read`：按记录 ID 从索引定向读取完整原文，核对来源并保留历史状态，支持可选项目限定，不要求目录绑定。
- `memory_profiles`：按领域与作用域读取画像。
- `memory_project_read`：按需分页读取项目本地索引和规范主题。
- `memory_save`、`memory_profile_save`：分别提交日记、画像候选，经完整计划展示与真实用户批准后保存。

### 3.4 当前检索与保存的边界

引擎检索基于 `index/search.json` 派生索引，采用中文双字词元与英文词元的 BM25 词法相关度，支持跨词匹配与词项命中解释。记录定位采用索引定向读取来源文件并核对指纹，单条读取不再遍历全历史日记。

检索默认面向全局全部日记，项目、模式与月份仅作显式过滤，未限定时不按目录强行绑定。索引覆盖日记与月摘要，来源清单或内容指纹不符时如实报错，不伪装为无命中，也不在查询中自动全历史扫描或隐式修复索引。

保存通道先生成短期计划，完整展示新旧正文、来源和替代／撤回影响，再等待真实用户批准。提交前复核会话、分支、项目、计划及来源状态。日记保存不顺带维护画像，项目知识维护也不借用用户库写入授权。

`/memory off`、`on`、`refresh` 管理启停和旧操作状态；刷新不重载配置与代码，停用也不能清除已经进入模型上下文的内容。缺库、读取失败和待恢复事务不自动触发初始化或修复。

## 4. 外部调研线索

本节只记录与本次问题直接相关的机制，不作产品总体排名，不据插件数量判断普及程度，也不把第三方说明中的效果描述当成本项目已取得的收益。

### 4.1 DSH：消息渠道与记忆触发分离

DSH 官方将 `agent/pre-step` 定义为模型请求推导前的钩子，插件可以替换进入本步的消息。

已读 `tencent-connect/dsh-qqbot` 的会话管理与入站源码：插件按私聊用户或群定位 Agent，再调用 `agent.followup(message)`。QQ 是消息入口，不负责决定是否搜索记忆。网站接入同样需要将消息送入承载记忆插件的宿主执行链；不能据此推断任意网站都天然支持记忆。

会话隔离不等于记忆隔离。即使每个用户或群拥有独立 Agent，用户级或项目级记忆是否共享，仍取决于记忆系统自己的作用域与访问控制。

### 4.2 Culeot/dsh-agent-memory：自动检索与模型工具并存

已读 `src/index.ts` 的实现：

- 在 `agent/pre-step` 中根据用户消息形成查询，直接调用内部召回逻辑。
- 对结果进行相关度筛选、数量控制和重复抑制，再加入本步输入。
- 自动召回采用不更新访问状态的读取方式。
- 同时注册主动检索、保存与目录浏览工具，并提供记忆使用提示。

可借鉴的是“程序主动提供相关摘要，模型按需深入读取”的分工。工具使用提示仍依赖模型选择，不能当成程序强制调用。无相关命中或检索失败时，该实现可以不注入记忆，也不是保证每步都有结果。

### 4.3 zhbcher/dsh-memory：自动召回之外还有自动沉淀

已读 `lib/index.js` 的实现：

- 在请求前组合用户级与项目级记忆，按相关性和预算选择内容，并抑制重复注入。
- 在空闲、会话释放和压缩摘要等生命周期事件上，满足条件后调用模型提炼记忆操作。
- 自动提炼受开关控制，并与存储更新、来源记录和去重协作。

自动沉淀是独立的写入策略，不是 QQ 接入自动附带的功能。它增加模型调用、错误知识沉淀和维护责任，与当前明确批准后写入的边界不同，不宜仅因外部插件支持就照搬。

### 4.4 OpenViking：检索能力、自动接入与 MCP 分层

本次将“Viking”按 OpenViking 理解。依据其官方 MCP 文档与 OpenCode 插件说明：

- 服务提供检索、读取和记忆相关能力，并通过 MCP 暴露工具。
- 官方集成同时使用生命周期钩子，自动召回相关记忆并提供上下文。
- 模型仍可通过 MCP 工具主动查找和读取详情。
- 部分集成还捕获会话并在生命周期边界提交记忆提炼；这是另外的数据收集与写入行为。

这支持“检索核心、自动召回入口、模型工具入口分离”的方向，而不是证明必须采用完整 OpenViking。

本轮对 OpenViking 的上述结论主要来自官方文档和集成说明，未完成其服务端检索实现、运行成本和权限边界的深入审查。若考虑实际引入，必须重新调研，不能据此直接决定替换当前存储或部署服务。

### 4.5 可采纳方向与不照搬部分

| 参考 | 可采纳方向 | 需适配的边界 |
| --- | --- | --- |
| DSH 请求前钩子 | 把自动召回放在宿主生命周期中 | Pi 使用自己的 `context` 钩子；每请求重新构建，不按结果 ID 跳过单次注入 |
| dsh-agent-memory | 自动摘要与模型工具共用检索能力 | 已作为统一检索核心采纳；保留请求级背景，被动读取不写回访问统计 |
| dsh-memory | 相关度、来源与预算协作 | 跨项目检索不等于规则跨项目生效；自动提炼和会话挖掘不纳入推荐范围 |
| OpenViking 集成 | 上下文装配与模型工具解耦 | 全局任务检索已采纳；不引入独立向量服务、会话捕获或跨工作区无界召回 |

这些是机制借鉴与适配边界。外部插件报告的效果数字不代表本项目已取得同等收益。

## 5. 候选方案：统一检索核心与请求前自动召回

### 5.1 推荐方向与当前分工

优先在现有架构内演进：文件引擎提供统一的词法检索、规则投影与定向读取；扩展工具与桌面展示已完成接入；下一阶段重点将统一检索核心引入请求级自动召回钩子。暂不以建设独立 MCP 服务或替换存储引擎为起点。

职责分工：

- **固定必要背景**：适用画像、项目索引中的通用硬约束（当前已在 `context` 注入）。
- **任务相关自动召回（待接入）**：每次请求根据当前任务问题，复用引擎检索核心召回相关有效决定与必要日记。
- **模型深入读取**：完整原文、特定主题、历史经过与摘要来源，使用同一套工具协议深入读取。
- **权威存储与保存流程**：继续提供权威 Markdown 正文、派生索引和两阶段审批保存，不因自动读取开放自动写入。

### 5.2 查询与作用域

自动召回应从真实用户问题提炼任务查询，排除自动背景、旧召回消息及工具输出，避免记忆反复检索自身。工具续步没有新用户问题时，可复用仍有效的任务查询；话题切换后更新。

作用域原则：

- 用户级记忆统一存储于全局库，默认面向全部日记检索相关候选。
- 项目、目录和分支是相关度与适用范围线索，不是存储位置或默认硬过滤边界。
- 用户显式限定项目或时间时按条件过滤；未绑定项目不阻断默认全局检索。
- 项目专属决定可以作为参考召回，但不自动提升为其他项目的通用规则。
- 项目本地知识保持为独立可选域，不与用户级库合并，也不作为全局查询前置。

当前没有足够依据将 QQ 或其他多用户入口纳入本轮开发范围。

### 5.3 相关度、有效性与无匹配静默

词法相关度基于中文双字片段与英文词元（BM25），已在引擎层统一实现；自动召回与模型工具共用该核心。

内容性质区分：

- 当前有效决定不受近期窗口限制，保留稳定规则键与适用条件。
- 历史日记保留发生日期与生命周期状态，被替代条目不冒充现行决定。
- 月度摘要是定位历史的线索，必要时回溯日记来源，不替代原文。
- 检索相关度与正文存在不等于事实已核实。
- **无匹配静默**：相关度未达到阈值时不硬凑无关记忆，宁可不注入也不带偏模型判断。

### 5.4 上下文预算、缓存与可观察性

自动召回与固定背景统一控制上下文占用，去除重复内容，优先保留适用条件、来源项目、日期和有效状态。无关内容不为凑数量进入上下文。

长内容提供明确标注的摘要或原文定位，不截断必要条件后冒充完整约束。必要背景因预算未能完整提供时明确说明缺口。

缓存保持为请求或会话级内存派生结果，问题、项目、分支或来源变化时失效。读取失败如实报告，不使用旧结果，不建立持久访问日志。

可观察性：桌面端已实现工具语义摘要与卡片展示，清楚表达操作身份、查询、实际范围、计数口径与来源；自动召回接入后同样需要最小可观察表达，区分无命中、读取失败和预算省略。

## 6. 工具与 MCP 的取舍

三者解决的问题不同：

| 层次 | 解决的问题 |
| --- | --- |
| 检索核心 | 哪些内容相关、有效、可访问，以及如何返回来源 |
| 自动钩子 | 何时在不等待模型选择工具的情况下提供记忆 |
| 原生工具或 MCP | 哪些客户端可以主动调用这项能力 |

当前 Pi CLI 与 pi-desk 已共享扩展，已有原生工具入口。候选默认方向是先改善共享检索能力，不额外启动 MCP 服务。

若以后确认 Claude Code、Codex 或其他独立客户端需要访问同一记忆系统，再考虑薄 MCP 适配层，复用同一检索核心和权威存储。跨客户端需求也不意味着 MCP 是唯一接入方式，仍需结合实际客户端能力重新选择。

MCP 不保证模型主动调用，也不自动提高搜索质量。若未来开放写入，必须独立解决真实用户审批与身份授权，不能把现有插件通道的确认能力当作所有客户端天然具备。

## 7. 已实现事实与下一阶段候选范围

### 7.1 已落实事实

- 统一词法检索核心：引擎实现全局 bigram + BM25 词法检索（`recall`）、有效规则查询与按 ID 定向读取。
- 全局检索派生索引：`index/search.json` 覆盖日记与月摘要，来源指纹核对，事务同步发布。
- 工具协议对齐：扩展工具支持默认全局日记检索、明确项目过滤、分页与状态保留。
- 跨机配套资源：`pi-skill-setup` 统一携带匹配的 Memory Skill 发布快照、引擎与指纹清单。
- 桌面结果展示：截断前提取语义摘要，工具卡提供操作分类、查询、范围、计数口径与来源展示。

### 7.2 下一阶段候选范围

- `context` 钩子中按当前任务问题自动调用检索核心。
- 任务查询提取、工具续步复用与多轮话题漂移处理。
- 自动召回的无匹配静默门槛与上下文预算控制。
- 自动召回状态的最小可观察表达。

暂不建议纳入：

- 替换权威存储或在 pi-desk 中建立第二套记忆库。
- 引入独立向量数据库服务或自建模型嵌入管线。
- 自动保存日记、提炼画像、捕获完整会话或自动生成月总结。
- 新增 QQ、网站或其他客户端入口。
- 强制模型调用工具的门禁。
- 自动初始化、自动修复索引或恢复事务。

## 8. 取舍与待定项

### 8.1 主要取舍

- 自动召回减少对模型主动检索的依赖，但增加每次请求的检索与上下文开销；需要严格的无匹配静默和预算控制。
- 轻量词法检索保持标准库零依赖和确定性，但在隐含语义或跨语言问题上弱于语义向量；现阶段优先保持部署简单与可解释。
- 保持人工审批写入限制错误知识自动沉淀，但也意味着没有用户明确触发就不会自动产生新的权威记忆。
- 统一全局存储便于跨项目借鉴，但需要显式保留项目归属与适用条件，避免其他项目的特定方案被误当全局硬约束。

### 8.2 留到后续讨论

- 自动召回在 `context` 钩子中的具体装配协议与预算上限。
- 任务查询形成的过滤规则（如何准确剥离工具输出与历史背景）。
- 无匹配静默的分数门槛与动态预算比例。
- 自动召回命中在界面上的最小提示形式。
- 未来独立客户端需求出现后，是否需要提供薄 MCP 适配层。

本文没有将这些事项作为已确定的实现细节。

## 9. 后续重新调研的重点

进入开发前，应围绕实际阶段重新取得事实：

- 重新读取共享扩展维护源、部署配置、Python 引擎与 pi-desk SDK 接入点，确认本文现状仍成立。
