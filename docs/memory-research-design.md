# 记忆系统初步调研与方案草案

## 1. 文档定位

本文整理当前记忆系统的已知事实、外部实现线索和候选优化方向，供后续讨论使用。

**本文不是确定方案、选型结论、实现规格或开发授权。进入开发前，必须重新调研上游官方资料与实际源码，重新读取本项目及共享扩展的现状，再调整需求、边界和设计。不能直接依据本文开始实现。**

本轮明确的交付范围只有这份初步文档。下文推荐方向尚未作为实施需求逐项确认；第三方能力和现有实现也不自动成为必须保留或新增的需求。

## 2. 问题与目标方向

讨论围绕以下问题展开：

- 如何让相关记忆在运行过程中主动进入上下文，而不是完全依赖模型记得搜索？
- 是否需要新增工具、MCP 服务，或者引入 OpenViking 一类系统？
- DSH 接入网站和 QQ 后，记忆究竟由消息渠道、宿主程序还是模型调用？
- 如何在提高召回可用性的同时，控制无关内容、历史误用和写入权限？

候选目标是：在模型处理任务前提供必要背景和相关记忆，保留深入读取能力，并让来源、适用范围与失败状态可解释。不以“调用过工具”代表模型理解或遵守，也不承诺检索必然命中。

## 3. 当前实现事实

### 3.1 组件与所有权

当前记忆能力不是 pi-desk 内置的独立数据库，而是以下组件协作：

| 组件 | 当前职责 |
| --- | --- |
| Memory Skill | 判断何时使用记忆、选择检索范围、核实与整理内容，约束保存流程 |
| 用户级 `pi-memory` 扩展 | 请求级背景注入、记忆工具、会话控制与保存审批 |
| Python 文件引擎 | 用户级数据读写、计划、锁、事务与派生索引 |
| pi-desk SDK 宿主 | 加载扩展，并通过桌面交互桥提供完整正文确认能力 |

当前共享扩展的统一维护源位于 `~/.pi/agent/skills/pi-skill-setup/assets/extensions/pi-memory/`；实际 agentDir 下的 `extensions/pi-memory/` 是部署副本，不应作为另一套独立维护源。这是当前环境的路径事实，不是跨设备安装路径约定。

pi-desk 通过 `src/main/shared/pi-paths.ts` 解析 agentDir，并在 `src/sdk-host/session-runtime.ts` 创建 SDK 会话服务；不能仅因桌面端加载了扩展，就将其视为仓库内置业务模块。

### 3.2 数据边界

| 数据域 | 当前权威位置 | 用途 |
| --- | --- | --- |
| 工作日记 | `~/.agents/memory-store/daily/` | 按日期、项目记录事件、进展、决定和约束 |
| 个人画像 | `~/.agents/memory-store/profile/` | 按领域与作用域保存偏好 |
| 月度总结 | `~/.agents/memory-store/monthly/` | 关联日记来源的历史回顾 |
| 项目知识 | `<项目根>/.agents/memory/` | 项目现行约定、特殊配置、选型理由和棘手问题 |

用户库通过 Markdown 正文与 JSON 项目表、派生索引组织数据。项目知识由独立的索引与主题文件维护，不自动复制进用户库。

当前配置将本仓库绑定到真实项目 ID `pi-desktop`。前述调查中，本项目尚未建立 `.agents/memory/`，因此不能把“没有项目知识文件”误解为“没有用户级项目记录”。本文件也不创建该目录或补写记忆。

### 3.3 自动读取与工具

当前扩展在 `context` 钩子中为每次模型请求提供独立背景消息，内容主要是适用画像和项目索引：

- 不覆盖系统提示词，不改写用户输入。
- 自动召回正文不追加到持久会话历史；显式工具结果则仍按宿主工具消息机制处理。
- 画像使用内存缓存，来源变化时刷新；项目索引按请求读取。
- 自动背景目前不按本轮问题检索规则、项目主题或日记。

已经存在的工具包括：

- `memory_profiles`：按领域与作用域读取画像。
- `memory_rules`：读取当前有效决定与约束，不受近期窗口限制。
- `memory_search`：搜索近期日记或已有月摘要。
- `memory_read`：按记录 ID 读取原文。
- `memory_project_read`：读取当前项目索引和规范主题。
- `memory_save`、`memory_profile_save`：分别提交日记、画像候选，经过完整计划审批后保存。

因此，当前并不缺“可调用工具”这一基础能力。主要候选优化点是检索质量、自动触发和两种入口的一致性。

### 3.4 当前检索与保存的边界

现有引擎的近期日记搜索主要采用整段子串匹配，当前有效规则查询支持按空白拆分的词项过滤。它们不能直接等同于面向自然语言问题的相关度检索；把完整用户问题原样传给当前搜索，不会自动获得语义理解。

现有保存通道先生成短期计划，完整展示内容与影响，再等待真实用户批准。提交前复核会话、分支、项目、计划及来源状态。日记保存不顺带维护画像，项目知识维护也不借用用户库写入授权。

`/memory off`、`on`、`refresh` 管理启停和旧操作状态；刷新不重载配置与代码，停用也不能清除已经进入模型上下文的内容。缺库、读取失败和待恢复事务不自动触发初始化或修复。

以上是已读实现与当前使用约束，不代表全部机制都已作为未来方案不可改变的产品要求。

## 4. 外部调研线索

本节只记录与本次问题直接相关的机制，不作产品总体排名，不据插件数量判断普及程度，也不把第三方说明中的效果描述当成本项目已取得的收益。

### 4.1 DSH：消息渠道与记忆触发分离

DSH 官方将 `agent/pre-step` 定义为模型请求推导前的钩子，插件可以替换进入本步的消息。

已读 `tencent-connect/dsh-qqbot` 的会话管理与入站源码：插件按私聊用户或群定位 Agent，再调用 `agent.followup(message)`。QQ 是消息入口，不负责决定是否搜索记忆。网站接入同样需要将消息送入承载记忆插件的宿主执行链；不能据此推断任意网站都天然支持记忆。

会话隔离不等于记忆隔离。即使每个用户或群拥有独立 Agent，用户级或项目级记忆是否共享，仍取决于记忆系统自己的作用域与访问控制。

### 4.2 Culeot/dsh-agent-memory：自动检索与模型工具并存

已读 `src/index.ts` 的实现：

- 在 `agent/pre-step` 中根据用户消息形成查询，直接调用内部召回逻辑。
- 对结果进行相关度筛选、数量控制和重复抑制，再加入本步输入。
- 自动召回采用不更新访问状态的读取方式。
- 同时注册主动检索、保存与目录浏览工具，并提供记忆使用提示。

可借鉴的是“程序主动提供相关摘要，模型按需深入读取”的分工。工具使用提示仍依赖模型选择，不能当成程序强制调用。无相关命中或检索失败时，该实现可以不注入记忆，也不是保证每步都有结果。

### 4.3 zhbcher/dsh-memory：自动召回之外还有自动沉淀

已读 `lib/index.js` 的实现：

- 在请求前组合用户级与项目级记忆，按相关性和预算选择内容，并抑制重复注入。
- 在空闲、会话释放和压缩摘要等生命周期事件上，满足条件后调用模型提炼记忆操作。
- 自动提炼受开关控制，并与存储更新、来源记录和去重协作。

自动沉淀是独立的写入策略，不是 QQ 接入自动附带的功能。它增加模型调用、错误知识沉淀和维护责任，与当前明确批准后写入的边界不同，不宜仅因外部插件支持就照搬。

### 4.4 OpenViking：检索能力、自动接入与 MCP 分层

本次将“Viking”按 OpenViking 理解。依据其官方 MCP 文档与 OpenCode 插件说明：

- 服务提供检索、读取和记忆相关能力，并通过 MCP 暴露工具。
- 官方集成同时使用生命周期钩子，自动召回相关记忆并提供上下文。
- 模型仍可通过 MCP 工具主动查找和读取详情。
- 部分集成还捕获会话并在生命周期边界提交记忆提炼；这是另外的数据收集与写入行为。

这支持“检索核心、自动召回入口、模型工具入口分离”的方向，而不是证明必须采用完整 OpenViking。

本轮对 OpenViking 的上述结论主要来自官方文档和集成说明，未完成其服务端检索实现、运行成本和权限边界的深入审查。若考虑实际引入，必须重新调研，不能据此直接决定替换当前存储或部署服务。

### 4.5 可采纳方向与不照搬部分

| 参考 | 可采纳方向 | 需适配的边界 |
| --- | --- | --- |
| DSH 请求前钩子 | 把自动召回放在宿主生命周期中 | Pi 已有自己的 `context` 钩子，不引入 DSH 运行时 |
| dsh-agent-memory | 自动摘要与模型工具共用检索能力 | 保留请求级背景，不直接复制其提示协议与写入策略 |
| dsh-memory | 相关度、去重、来源与预算协作 | 自动提炼和自动写入另行讨论，不纳入当前推荐范围 |
| OpenViking 集成 | 将检索能力与 MCP、自动召回入口解耦 | 不据接口存在就引入完整服务、会话捕获或跨项目召回 |

这些是候选借鉴方向，不是已确认选型。没有量化依据证明它们在当前数据和工作流下带来确定收益。

## 5. 候选方案：统一检索能力与双入口

### 5.1 推荐方向，尚未定案

优先考虑增强现有检索能力，让自动钩子和模型工具复用同一套范围判定、检索、排序、来源及预算逻辑；暂不以建设 MCP 服务或替换存储引擎为起点。

大致职责分工：

- **固定必要背景**：适用画像、项目索引中明确的通用硬约束。
- **任务相关自动召回**：当前任务适用的有效规则、项目知识与必要近期记录。
- **模型深入读取**：完整原文、特定主题、历史经过及摘要来源。
- **既有存储与保存流程**：继续提供权威内容、历史状态和受控提交，不因自动读取而获得自动写入权限。

工具名称与能力拆分不在本文锁定。可以增强已有工具，也可以在职责明确后调整入口，但应避免再造一套与自动召回结果不一致的搜索实现。

### 5.2 查询与作用域

候选设计应从真实用户问题形成任务查询，排除自动背景、旧召回消息及工具输出，避免记忆反复检索自身。工具续步没有新用户问题时，可复用仍有效的任务查询；话题切换或来源变化后需要更新。

作用域应在检索前确定：

- 项目相关内容按真实项目绑定读取，不从目录名猜测 ID。
- 项目知识与用户级日记、画像保持不同的权威位置。
- 未映射项目时，不静默改用其他项目或通用库。
- 不因一次无命中就扩大到所有项目或全部历史。
- 若以后接入多用户聊天入口，需要另行设计真实用户、群与记忆范围的授权关系，不能只凭会话 ID 隔离。

当前没有足够依据将 QQ 或其他多用户入口纳入本轮开发范围。

### 5.3 相关度与有效性

候选检索应支持中文友好的词法相关度，结合主题、标题和正文线索，而不是直接匹配整段用户问题。先考虑不增加外部服务或额外模型调用的轻量方向；具体算法与是否需要语义检索留到开发阶段重新讨论。

还需区分内容性质：

- 明确的通用硬约束不应仅因关键词未命中而消失。
- 当前有效决定不应因超过近期窗口而被排除。
- 任务相关规则应保留其适用条件，不能全部提升为全局要求。
- 历史日记可用于还原经过，被替代条目不能冒充现行决定。
- 月摘要是定位线索，必要时回溯日记来源，不替代原文。
- 当前存在或处于有效状态，不等于正文事实已经核实。

自动召回只负责提供候选证据，不负责让历史内容覆盖当前用户要求和已核实的项目事实。

### 5.4 上下文、缓存与可观察性

候选方案应统一考虑固定背景与动态结果的上下文占用，去除重复内容，并优先保留适用条件、来源和有效状态。无关内容不为凑数量进入上下文。

长内容可以提供明确标注的摘要或原文定位，但不能截断必要条件后冒充完整约束。必要背景因预算未能完整提供时，应明确说明缺口。

缓存优先保持为内存派生结果，问题、项目、分支或来源变化时失效。不能在读取失败后无提示地沿用旧结果，也不应为记录召回而自动建立持久访问日志。

可观察信息以本次召回范围、来源、是否完整及失败原因类别为主，区分无命中、读取失败和预算省略；不重复向用户展示整段内部背景。是否需要桌面专用入口，留到交互设计阶段决定。

## 6. 工具与 MCP 的取舍

三者解决的问题不同：

| 层次 | 解决的问题 |
| --- | --- |
| 检索核心 | 哪些内容相关、有效、可访问，以及如何返回来源 |
| 自动钩子 | 何时在不等待模型选择工具的情况下提供记忆 |
| 原生工具或 MCP | 哪些客户端可以主动调用这项能力 |

当前 Pi CLI 与 pi-desk 已共享扩展，已有原生工具入口。候选默认方向是先改善共享检索能力，不额外启动 MCP 服务。

若以后确认 Claude Code、Codex 或其他独立客户端需要访问同一记忆系统，再考虑薄 MCP 适配层，复用同一检索核心和权威存储。跨客户端需求也不意味着 MCP 是唯一接入方式，仍需结合实际客户端能力重新选择。

MCP 不保证模型主动调用，也不自动提高搜索质量。若未来开放写入，必须独立解决真实用户审批与身份授权，不能把现有插件通道的确认能力当作所有客户端天然具备。

## 7. 候选范围与暂不纳入的事项

推荐第一轮仅围绕以下职责讨论：

- 统一任务相关检索能力及现有工具的职责。
- 请求前自动召回与固定必要背景的协作。
- 中文相关度、作用域、有效性、来源、缓存和上下文预算。
- 召回状态的最小可观察表达。

暂不建议纳入：

- 替换权威存储或在 pi-desk 中建立第二套记忆库。
- 直接引入完整 OpenViking 或独立向量服务。
- 自动保存日记、提炼画像、捕获完整会话或自动生成月总结。
- 新增 QQ、网站或其他客户端入口。
- 强制模型调用工具的门禁、全局文件沙箱。
- 自动初始化、修复索引、恢复事务或全历史扫描。

这些是不扩大本轮候选范围的建议，不代表永久排除上述能力。

## 8. 取舍、限制与开发阶段待定项

### 8.1 主要取舍

- 自动召回减少对模型主动检索的依赖，但增加每次请求的读取、筛选与上下文开销。
- 轻量词法检索降低依赖与部署复杂度，但对改写、隐含语义和跨语言问题的支持有限。
- 共用检索核心减少多入口差异，但工具和自动背景的展示形态、内容深度仍需分别设计。
- 保持人工审批写入限制错误知识自动沉淀，但也意味着没有用户触发就不会自动产生新的权威记忆。
- 读取失败时如实降级有利于识别缺口，但对确实依赖关键约束的操作是否需要暂停，必须另行确定，不能默认引入门禁。

### 8.2 非阻塞假设

- 当前优先服务个人在 Pi CLI 与 pi-desk 中的项目工作，而不是多租户记忆服务。
- 现有文件引擎与数据规模仍可作为第一轮候选基础；实际开销尚不能据本文断言。
- 先解决自动召回与现有工具质量，较早部署通用 MCP 服务更贴近当前讨论目标。

上述假设一旦变化，应重新评估方案，而不是为了保持本文结论继续推进。

### 8.3 留到后续讨论

- 哪些规则明确属于通用硬约束，如何表达其适用条件。
- 检索核心位于现有引擎还是共享扩展，如何避免两处维护同一语义。
- 中文检索方法、查询形成方式、结果解释与摘要策略。
- 工具公开行为、缓存失效机制、预算及读取开销控制。
- 是否需要独立状态界面，以及错误状态由哪一层表达。
- 真实跨客户端需求出现后，是否增加 MCP、如何认证与保持审批边界。

本文没有将这些事项作为已确定的实现细节。

## 9. 后续重新调研的重点

进入开发前，应围绕实际阶段重新取得事实：

- 重新读取共享扩展维护源、部署配置、Python 引擎与 pi-desk SDK 接入点，确认本文现状仍成立。
- 根据实际记忆内容及任务类型，重新判断检索范围、适用条件和主要查询困难，避免把“没有相关内容”误判为检索算法问题。
- 重新核实 DSH 插件与 OpenViking 官方源码及接口变化，重点确认请求前召回、消息归属、数据作用域和写入行为。
- 若拟引入第三方代码、依赖或服务，再核实许可、维护情况、部署条件、数据流向及成本；本文不提供直接引入的结论。
- 结合重新取得的事实，重新确认候选方向与范围，再形成该开发阶段的具体设计。

这是后续设计所需的资料范围，不构成当前开发、安装、启动、重载或任何运行操作的授权。
