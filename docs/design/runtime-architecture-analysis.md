# 运行时架构调研与判断

## 1. 定位与证据边界

本文维护架构判断、项目源码依据与外部参考的适用性。已确认需求与架构决策统一见[设计基线](./runtime-sdk-migration.md)，开发阶段统一见[开发总览](./runtime-development.md)，不在本文重复维护实现清单。

本轮依据是静态源码阅读，没有运行 pi-desk 或参考客户端，没有测量启动、切换、IPC、CPU 或内存。用户报告的等待与 Runtime 故障是问题线索，不是性能分段结果。不能给出具体耗时、改善倍数或“换 SDK 即可解决”的承诺。

第三方源码链接指向可变分支。所述机制来自实际阅读的文件；后续实现仍需核实本项目依赖。项目作者关于性能、内存或跨平台效果的描述不作为本项目实测证据。

## 2. 判断依据的代码范围

本轮判断覆盖旧会话链路的调用链：会话编排（`src/main/session-manager.ts`）、Runtime 与进程（`src/main/runtime-manager.ts`、`src/main/pi-process.ts`）、资源预读（`src/main/resource-preview.ts`）、展示状态（`src/renderer/src/stores/runtime.ts`）、会话文件读取（`src/main/session-store.ts`）、协议适配（`src/main/pi-protocol.ts`），以及构建与依赖入口（`electron.vite.config.ts`、`package.json`）。

逐文件的当前事实、职责与结论只在代码及其注释中维护，本文不复制这类清单；判断与取舍见下文各节与[设计基线](./runtime-sdk-migration.md)。


### 2.1 明确判断

**现有“会话切换即关闭旧 Pi、启动新 Pi，并同步重置能力展示”的生命周期组合，不适合本项目以对话为中心的桌面交互。**

理由是它在高频操作上重复支付宿主建立成本，并将局部会话变化扩散到全局展示。这个判断不依赖未经测量的性能数字。独立进程、RPC 和单活动会话本身都不是错误。

### 2.2 问题分类

| 类别 | 判断与证据限制 | 设计回应 |
|---|---|---|
| 操作等待 | 关闭、初始化、状态读取、历史恢复与投影建立在关键路径上；各环节占比未知 | 分离宿主与会话，保留真实准备状态；不把完整设置查询放到切换关键路径 |
| 界面线程阻塞 | 静态阅读不能确认渲染线程是否被长任务阻塞，也不能确认 IPC 数据量造成的影响 | Agent 执行移到独立宿主；投影、序列化和页面更新仍需控制数据范围，隔离不等于消除所有阻塞 |
| 资源初始化成本 | 启动重建上下文有重复初始化的可能；扩展、MCP、凭据解析的实际耗时未确认 | 区分静态目录、全局服务与会话动态资源；只复用能够证明安全的服务 |
| 生命周期错误 | 进程代际已有保护，但 SDK 会话替换后还需要独立会话代际；现有具体报错没有逐条根因证据 | 集中请求归属、失效、重绑和恢复，不把所有报错归为 RPC 问题 |
| 具体实现问题 | 仅用展示流式状态决定切换许可不足以覆盖 preflight、压缩、排队和扩展等待；该风险不代表已复现竞态 | 以官方权威执行状态守门，让中止与交互响应可解除等待 |
| 待核实问题 | 文件扫描、长历史解析、同步计算、扩展清理和故障日志尚不足以完整归因 | 保持未知标注；不能断言它们与架构完全无关，也不能预先归罪 |

## 3. 实际阅读的外部源码

### 3.1 openpi：常驻宿主不等于复用会话对象

源码：[宿主监督](https://github.com/heyhuynhgiabuu/openpi/blob/main/electron/pi/sidecarHost.ts)、[会话生命周期](https://github.com/heyhuynhgiabuu/openpi/blob/main/electron/pi/sessionLifecycle.ts)、[命令队列](https://github.com/heyhuynhgiabuu/openpi/blob/main/electron/pi/sidecarCommandQueue.ts)、[宿主入口](https://github.com/heyhuynhgiabuu/openpi/blob/main/electron/pi/sidecar.ts)。

- `PiSidecarHost` 在开发环境可用 Node child process，在打包环境使用 Electron utility process；通过结构化消息通信，不是以 Pi CLI 的 stdio JSONL 作为业务协议。
- `startSession` 在原宿主内解绑、关闭旧会话，再调用 SDK 创建新会话；进程复用与会话对象替换是两件事。
- 关闭路径向扩展发送 shutdown，并处理未完成 UI 请求；说明扩展上下文和异步引用必须随会话失效。
- 命令队列区分替换、运行命令和解除 UI 等待的响应。不能照抄为所有命令统一排队，也不能把 prompt、模型切换与回退都看作中断命令。
- 宿主监督有请求形状校验、超时、退出后 pending 收敛与有上限重启。但读取这些机制不能证明其性能，也不能证明恢复时已解决所有会话归属问题。
- 源码说明打包时 ASAR 解析与开发时原生模块 ABI 是宿主选择因素。这是兼容性线索，不是采用 utilityProcess 即兼容所有扩展的保证。

**采纳**：常驻独立宿主、结构化通信、会话替换后的交互清理、解除等待通道。**不照搬**：开发和发行环境自动换宿主、错误过滤、自动恢复的全部策略。

### 3.2 pi-gui：查询职责分离，并且模型服务有范围

源码：[资源监督](https://github.com/minghinmatthewlam/pi-gui/blob/main/packages/pi-sdk-driver/src/runtime-supervisor.ts)、[会话监督](https://github.com/minghinmatthewlam/pi-gui/blob/main/packages/pi-sdk-driver/src/session-supervisor.ts)。本轮只使用这些文件中实际阅读的相关职责与生命周期段落，不声称完整审查全包。

- `RuntimeSupervisor` 维护按 workspace 归属的资源加载器、设置和模型上下文；`SessionSupervisor` 管理活动记录、事件与交互。
- 资源监督会调用资源加载器 reload 并处理扩展注册的 provider。它不是本项目要求的“完全不执行扩展的静态预览”，只能采纳职责分离思想。
- 模型运行时按 workspace 或会话构建，不把各项目扩展的 provider 注册放入同一个全局可变容器。
- `readTranscriptFromDisk` 从官方 `SessionManager` 构建非活动会话的展示内容，不必为阅读历史创建完整 Agent 运行环境。
- 会话管理有 preflight、取消、租约和外部文件变化处理的状态。租约只协调遵守相同协议的参与者，不能据此宣称官方 CLI 会服从 GUI 的写锁。
- 所读模块并不自行创建独立进程；仅凭包名或 supervisor 名不能判定整个应用实际在哪个进程执行 SDK。本轮不将其宿主位置作为选型证据。

**采纳**：查询与执行分离、模型注册范围隔离、非活动历史阅读与外部变更协调。**不照搬**：多会话记录体系、自管队列、并行调度、查询时加载扩展的方式。

### 3.3 pi-app：官方替换钩子与宿主形态是独立问题

源码：[会话运行时](https://github.com/justhil/pi-app/blob/main/src/worker/worker-runtime.ts)。

- 所读文件使用 `AgentSessionRuntime`，通过 invalidation 与 rebind 回调清理旧订阅并绑定新会话；热切换调用官方 `switchSession`，新建调用官方生命周期入口。
- 自定义创建工厂会重新建立 services。由此不能推出“复用 runtime 必然复用 ModelRuntime、扩展加载器或 MCP 连接”。
- 创建后的会话显式绑定桌面 UI 和官方内建扩展，不假定 SDK 默认具备完整 CLI 入口行为。
- 文件名中的 worker 只是模块名称；本轮未重新读取其实际进程创建入口，不以该文件证明线程或进程池形态。

**采纳**：官方替换语义、失效与重绑钩子、必要内建能力显式接入。**不照搬**：额外兼容层、分支上下文手工改写、多会话路由体系。

### 3.4 percho：信任必须发生在受保护资源加载前

源码：[信任加载](https://github.com/Jaxton07/percho/blob/main/packages/backend/src/project/trust-loader.ts)。

- `ProjectResourceLoader` 以项目未信任的设置建立加载器，在资源 reload 的信任决策点确认是否允许项目资源。
- 无交互或不询问时有保守处理；内建能力另行接入。
- 该文件还组合了项目自己的权限扩展；不意味着 pi-desk 必须采用它的工具覆盖顺序或权限体系。

**采纳**：前置的信任判定和加载顺序。**不照搬**：信任存储、权限规则或工具替换策略。

### 3.5 仍属于候选入口的项目

设计基线保留的 DLYZZT/pi-desktop、vastsa/PI-Desktop、PiDeck 入口，本轮尚未完成实际源码复核。不能将旧文档中对它们的描述提升为已证实结论。尤其不能把不同作者的 pi-desktop 合并成同一实现，或把 PiDeck 的 RPC 路线视为必然低效。

当前推荐的生命周期与隔离方向可由以上已读源码和本项目事实支持；未复核项目不作为推荐的关键证据。

## 4. 从调研提炼出的关键取舍

| 问题 | 推荐与依据 | 代价与限制 |
|---|---|---|
| 宿主放在哪里 | 独立 SDK 宿主，主进程保留桌面权威与监督；避免扩展和资源初始化占据主进程 | 新增内部通信、退出收敛与发行边界；不是权限沙箱 |
| 复用什么 | 正常切换复用进程；全局查询服务独立持有；官方会话及其服务可按语义替换 | 不承诺复用所有 SDK 对象，特别是项目扩展上下文 |
| 谁定义 Agent 行为 | 官方 SDK 管理会话树、压缩、队列、模型与工具；桌面端管理操作归属与展示 | 需要明确接入 SDK 与 CLI 入口的差异，不能用手工修改消息树兜底 |
| 展示与执行是否一起准备 | 允许先展示范围正确的目录或历史，执行入口以实际会话准备结果为准 | 展示已可读不等于可提交；预览和活动状态必须明确区别 |
| 失败如何恢复 | 宿主可有上限重建，写操作不自动重放，按实际失效阶段恢复 | 工具副作用与未持久化输出无法承诺恢复；不能“保留”已销毁会话 |

## 5. 有价值的替代方向

### 常驻 Pi CLI RPC 宿主

如果官方 RPC 能覆盖目标会话替换、资源刷新、信任和扩展交互，可用常驻 CLI 进程加独立查询快照达到生命周期解耦。不需要因继续使用 RPC 而引入进程池。

价值是保留官方 CLI 的启动行为与运行环境；代价是继续承担协议、版本和能力缺口适配。本轮尚未核实 RPC 能否完整满足主链要求，不能将其视为等价可直接实施的方案。用户已经采纳 SDK 方向，本轮不建设双后端。

### SDK 放入 Electron 主进程

可以降低宿主通信和监督的集成负担，但扩展阻塞、原生模块故障及资源初始化会影响桌面权威进程。与本项目可靠性目标不如独立宿主匹配，因此不推荐。它也不自动消除历史读取和页面投影成本。

## 6. 事实来源

官方 SDK 的生命周期入口、重绑方式与 services 重建行为，静态资源读取路径，历史快照与实时事件的交接，宿主模块格式与发行解析边界，以及项目切换中的扩展清理、配置与认证外部变化，都以代码、已安装依赖源码和[各阶段开发文档](./runtime-development.md)为准；本文不复制这些事实清单。
