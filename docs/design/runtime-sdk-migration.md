# Runtime 生命周期重构与官方 SDK 迁移

## 1. 文档定位

本文是 pi-desk 的需求与初步设计基线，首要目标是降低新建、打开和切换对话的明显等待及生命周期失败风险。SDK 迁移服务于这个目标，不以先完成全部模型、认证和资源查询迁移为目标。

本文维护已确认需求与架构决策，是本轮重构的设计基线，不是业务代码开发授权。项目事实与外部源码依据见[架构调研](./runtime-architecture-analysis.md)，开发职责与阶段依赖见[开发总览](./runtime-development.md)。

具体实现应在各阶段结合实际依赖与调用链讨论，不预先锁定实现文件、SDK 调用、通信字段或构建配置。启动参数、通道、错误码、常量和依赖版本只在代码及配置中维护；文档不复制这些清单。测试安排不属于本文。

## 2. 问题与架构判断

当前设计将应用宿主、活动会话和能力快照的生命周期耦合。新建或打开另一个会话走旧 Runtime 关闭、新 Pi 进程启动、状态读取及历史恢复链路；页面能力数据又随 Runtime 状态变化清空和重新获取。

问题定位指向：[会话编排](../../src/main/session-manager.ts)、[Runtime 管理](../../src/main/runtime-manager.ts)、[Pi 进程管理](../../src/main/pi-process.ts)、[资源预读](../../src/main/resource-preview.ts)、[渲染端 Runtime 状态](../../src/renderer/src/stores/runtime.ts)。

**架构判断**：RPC 或独立进程本身不是错误，单个活动会话也不是错误；但让高频对话操作反复拆除和重建整个运行环境，不适合本项目的桌面使用方式。本次是对生命周期耦合的架构纠正，不只是更换通信方式。

启动初始化、模型目录刷新、已启用扩展与 MCP、历史读取及投影重建都可能产生等待。不能把所有现有 Runtime 报错归因于 RPC，也不能把观察到的切换等待直接等同于渲染线程阻塞。迁移需同时收敛生命周期管理，不能仅把进程启动替换为 SDK 调用。

## 3. 已确认的核心需求

1. **会话主链优先**：优先处理新建、打开和切换对话的等待与生命周期问题，不把完整资源页、设置页或认证执行链迁移放在会话主链之前。
2. **分离生命周期**：应用宿主、会话对象、全局快照分别管理。同项目新建和切换对话的正常路径不重启宿主进程；允许 Pi SDK 按官方生命周期替换会话对象及会话服务，不强行复用旧扩展上下文。
3. **用户操作对话而非 Runtime**：日常新建、打开和切换不要求用户先手动启停 Runtime。切换只影响对话区及当前会话执行入口，不因切换清空模型、认证和静态资源快照；内部 Runtime 状态与故障诊断仍然存在。
4. **统一会话操作边界**：集中处理切换互斥、用户确认中断、旧请求与事件失效、订阅重绑、扩展交互清理、投影替换及失败恢复。请求超时或宿主退出不构成重新执行的授权，不自动重发已提交操作。
5. **保持 Pi 数据真相**：Pi 的 JSONL 是会话唯一真相，Pi agent 目录是模型、认证、资源与设置配置的唯一真相。桌面端不持久化平行消息或 Pi 配置副本；CLI 与 GUI 支持轮流接管同一会话，不承诺同时写入。
6. **信任前置与无执行预览**：桌面端仍拥有 Project Trust 确认点，信任决定在加载受保护项目资源之前生效。静态预览不执行扩展、不连接 MCP，不为了填充目录而启动会话。
7. **不作零等待或万能修复承诺**：SDK 迁移去除正常切换中的进程启停与 CLI 协议适配成本，但资源加载、凭据解析、会话恢复和投影仍可能耗时。各类 Runtime 失败按实际边界处理，不用增大超时或隐藏错误代替生命周期收敛。

## 4. 已确定的范围与不做项

### 4.1 宿主与会话数量

- Agent 会话运行在应用管理的一个 `utilityProcess` SDK 宿主中，不在 Electron 主进程或渲染进程中执行。
- 本轮只保留一个活动会话，不引入会话进程池、后台并发会话或多会话常驻缓存。
- 新建和切换复用宿主，使用官方会话管理及替换机制。宿主生命周期不再等同于当前会话生命周期。
- 宿主在首次需要会话或查询时建立；静态查询不得顺便创建 Agent 会话、执行扩展或连接 MCP。正常会话切换不关闭宿主。
- 跨项目切换先处理项目、信任与扩展上下文的变化，不以项目变化本身作为必然重启条件。遇到不可收敛的进程级副作用或宿主故障时才重建宿主，不保留多个项目的活动会话对象。

宿主位置与会话数量是两个独立决策。每会话一个 worker 可以同样使用 `utilityProcess`，但其进程池和前后台路由成本不属于本轮范围。

### 4.2 引擎与发布

- 从独立 Pi 二进制的 stdio RPC 会话后端迁移到官方 coding-agent SDK。
- 不保留外部 Pi 二进制或协议兼容第三方引擎，不建设双引擎抽象。
- 不自动寻找或切换到另一份 SDK；SDK 随应用依赖与应用发行物管理。
- SDK 负责 Agent 语义，包括会话树、压缩、队列、工具执行、扩展及模型行为；桌面端只负责宿主、交互、数据展示与受支持的适配，不自研替代 Agent 实现。

### 4.3 认证及既有能力

- 认证先沿用现有 SDK auth-helper，不把立即合并认证执行链作为会话迁移前提。
- 认证变化需通知模型与相关展示快照刷新，不能让查询副本长期保留旧凭据状态。是否合并 helper 留在会话主链完成后的职责讨论中。
- 保持模型可见性、默认模型、项目记忆及现有对话操作的业务语义。
- rewind 仍只回退对话，不撤销项目文件；历史和分支写入由 Pi SDK 管理。
- 迁移现有工具审批和扩展交互，不借机新增权限规则引擎或扩大权限策略。

迁移期间可以按模块保留旧查询或旧会话后端，但同一活动会话只由一个后端负责。会话链路切换到 SDK 后不保留运行时引擎选择，也不让旧 RPC 与 SDK 同时接管同一个 JSONL。

## 5. 架构与职责边界

### 5.1 依赖方向

渲染端通过现有 preload 桥接调用 Electron 主进程；主进程校验业务请求并监督 SDK 宿主；宿主调用 Pi SDK 并返回可序列化的展示结果与事件。

- **渲染端**：展示状态、对话选择和用户交互，不直接访问 Node、文件系统或凭据存储，不持久化密钥；认证输入只通过受校验的认证流程转交。
- **主进程**：窗口与 IPC、项目及信任决定、桌面配置、宿主监督、展示快照和请求归属，不承担 Agent 执行。
- **SDK 宿主**：模型服务、静态资源查询及一个活动会话的 SDK 生命周期、事件和扩展绑定。
- **认证 helper**：过渡期间继续承担既有登录流程与凭据操作，配置真相仍由 Pi 管理。

沿用统一结果与错误契约、preload 桥接和主进程校验模式。宿主内部消息与 SDK 对象不直接作为页面契约；不绕过主进程校验建立渲染端到宿主的直接业务通道。内部状态和视图可以适配新的生命周期，不为保留旧状态机而继续让全局数据依赖会话启停。

### 5.2 数据范围

| 范围 | 内容与责任 | 展示边界 |
|---|---|---|
| 桌面本机数据 | 项目、界面偏好、JSONL 会话索引；由桌面端读取和管理 | 不依赖 Agent 会话就绪；局部读取不阻塞窗口和其他功能 |
| Pi 全局基础快照 | 基础模型目录与能力、provider 认证状态、静态用户资源 | 独立于活动会话；有合适范围的旧快照时继续展示，刷新失败不伪装为空清单 |
| 项目静态预览 | 受当前项目及信任决定约束的静态资源 | 不执行扩展或连接 MCP；项目与信任变化后不能套用旧范围结果 |
| 会话实际能力与运行态 | 扩展贡献的模型和命令、工具与 MCP 连接、消息及工具投影、当前模型、中止和回退 | 以当前 SDK 会话为准，只影响当前对话和执行入口 |

全局模型服务与会话的项目扩展注册隔离。不能把一个可被项目扩展修改的模型运行时同时当作全局目录和所有项目的注册容器，也不能把尚未加载的动态能力伪装成静态预览中的确定事实。

快照只作展示副本，不成为第二套配置或会话真相。模型、认证、资源分别刷新，不能因为一项失败让其他已可用数据一起消失。配置刷新、资源重载与宿主重启是不同操作，不再一律以进程重启表达配置生效。

### 5.3 会话切换与失效管理

会话编排由一个所有者集中管理。空闲时执行新建或切换；需要中止当前操作时先取得用户确认，再由 SDK 收敛旧会话执行，随后替换会话及展示基准。不能仅依据页面上的流式状态判断 SDK 是否已经空闲。

宿主代际与活动会话代际分开。进程仍在并不意味着旧请求、旧事件、旧扩展上下文和旧投影仍然有效；会话替换后必须重新绑定订阅与扩展交互，清理旧弹窗及未完成请求，并以新会话权威数据替换投影。

会话替换与冲突写操作需互斥，但中止、工具审批回应、扩展弹窗回应和登录回应不能被阻塞在它们要解除的等待之后。宿主通信不能采用覆盖所有请求的一条无差别串行队列。

失败按实际进度表达：目标准备失败与旧会话已经销毁后的创建失败不能当作同一种状态。旧会话已经失效时不得继续展示为可操作的 ready；宿主重建也不得把未完成的用户操作当成可以自动重放的任务。

### 5.4 交互与隔离

- 展示状态区分可用、正在读取或切换、需要用户动作、错误；加载只表示实际正在进行的工作。
- 未创建会话不等于模型目录或认证不可用；会话切换不造成全局目录重新等待。
- 会话操作失败收敛在对话范围。宿主故障时窗口仍可响应，已有全局快照与本机数据仍可展示，但失效能力不能继续标为可执行。
- `utilityProcess` 提供故障与阻塞隔离，不提供权限沙箱，也不保证所有原生扩展与 Electron 兼容。
- 宿主异常退出时采用有上限的自动重建，连续失败后停止循环并显示诊断。主动退出不触发重建。恢复宿主只恢复基础设施，不自动重发 prompt、回退、工具操作或其他结果未知的写操作；恢复活动会话需重新读取权威状态。
- 宿主退出使活动执行上下文失效，不等于 JSONL 历史丢失；未持久化的输出与未确认的工具副作用可能无法恢复。

## 7. 迁移涉及的职责

- **宿主监督与会话编排**：分离进程与会话生命周期，集中操作互斥、失效处理和故障收敛。
- **消息、工具与扩展交互**：从 SDK 权威事件与历史构建现有展示投影，保持中止、回退及审批边界。
- **模型、认证与资源**：建立独立快照及刷新机制，区分全局基础、项目静态预览和会话实际能力；先沿用认证 helper。
- **契约与渲染交互**：维持 preload 和主进程校验，取消日常对话操作对手动 Runtime 启停的依赖，不随切换清空全局能力。
- **构建与发行**：独立构建 SDK 宿主，随应用提供运行时依赖，下线不再使用的 standalone 二进制准备链路。

具体文件清单和操作范围在对应开发阶段确定，本文不构成代码修改授权。开发总览与分阶段文档只规划职责、数据流、交付方向和待定问题，不将推测的 API 或配置当作可直接实施的规格。

## 8. 开发阶段

整体包括三个阶段，不以完成阶段 1 代替整个重构。开发文档入口：

- [开发总览](./runtime-development.md)：阶段依赖、共享边界与迁移安排。
- [阶段 1](./phase-1-implementation.md)：宿主与完整会话主链。
- [阶段 2](./phase-2-implementation.md)：独立查询、配置生效与恢复完善。
- [阶段 3](./phase-3-implementation.md)：旧链路退役与发行整合。

### 阶段 1：SDK 宿主与完整会话主链

**目标**：优先让新建、打开、切换、提交、中止、消息及工具投影、回退走常驻 SDK 宿主，正常同项目切换不启停进程。

**设计关注点**：宿主与会话代际、权威会话恢复、互斥与用户确认中断、失效请求、投影替换、失败后的实际会话状态。Project Trust、基本扩展 UI 绑定、既有审批交互和必要的 SDK 内建能力随主链接入，不能推迟到会话开始执行之后。

**边界**：全局快照不随会话切换清空、认证变化不留下长期旧状态、宿主退出及切换失败能够收敛，均属于阶段 1，不推迟到阶段 2。完整资源页和设置页迁移不作为会话主链前提。认证执行继续使用既有 helper，补齐认证变化通知。宿主的构建入口与应用集成也随主链建立，阶段 3 再退役旧发行资源。

**依赖**：无。

### 阶段 2：独立查询、配置生效与故障处理完善

**目标**：完成模型、认证状态、静态资源及会话实际能力的范围划分和刷新，让会话切换不再影响全局查询；完善资源重载、MCP 交互和宿主故障处理。

**设计关注点**：扩展 provider 隔离、快照失效与保留、认证及配置变化后的同步、资源重载与宿主重启的区别、各操作的失败归属。认证 helper 是否合并在本阶段详细讨论，不作为前置条件。

**依赖**：阶段 1 的宿主、会话与交互边界。

### 阶段 3：旧链路清理

**目标**：移除被 SDK 替代的 RPC 会话链路、一次性预读探针、协议适配及 standalone 二进制准备流程，不留下第二套活动会话后端。

**设计关注点**：旧查询入口和诊断入口的职责归属、打包资源边界、与已授权维护文档的描述一致性。项目记忆维护需单独授权，不自动随开发更新。

**依赖**：阶段 2 的替代职责已明确。

## 9. 风险与约束

- **剩余加载成本**：SDK 会话替换可能重建服务和扩展，历史恢复及投影也可能耗时；复用宿主并不等于复用所有对象，更不等于零等待。
- **生命周期失败**：SDK 可能在新会话创建之前销毁旧会话；恢复必须依据实际状态，不能假装旧会话仍可操作。
- **宿主共享影响**：单宿主中的扩展阻塞或崩溃可能影响该宿主的查询与活动会话。主进程保留展示副本只能保护界面可读性，不能让失效服务继续执行。
- **版本与扩展兼容**：SDK 更新会改变应用运行时；自动换用另一份 SDK 不能视为兼容性保障，运行时随应用管理。
- **打包与原生依赖**：ESM、动态加载、ASAR 与原生扩展兼容属于宿主集成边界；进程隔离不自动解决模块解析或 ABI 差异。
- **CLI 与 SDK 差异**：宿主需明确接入应用已有的 CLI 内建能力及扩展交互，不假定 SDK 默认拥有全部 CLI 行为；不以适配为名重写 Agent 语义。
- **跨应用接管**：本应用单活动会话不构成 CLI 与 GUI 之间的写锁；无共同协调时不承诺并发写同一 JSONL 安全。
- **现有报错归因**：进程启停、协议、资源、认证、SDK 操作及页面状态错误不能混为一类；迁移不能代替对具体失败边界的分析。

## 10. 留待开发阶段确定的事项

已确认的宿主形态、单活动会话和不保留外部引擎不再作为开放问题。后续仅按阶段讨论：

- 宿主按需建立、正常切换复用及有上限的故障重建已经确定；关闭收敛、恢复会话的交互，以及进程级副作用需要重建宿主的具体边界在阶段 1 讨论。
- 内部通信、代际与请求归属的具体表达，现有公开契约的适配方式。
- 会话服务和资源的复用边界、官方内建能力与既有扩展交互的接线方式。
- 模型及资源快照刷新触发点、配置和认证变化后的同步策略。
- ESM 宿主的构建与发行资源组织，认证 helper 是否合并。

这些是实现阶段的设计事项，不重新开放本轮已确认需求，也不授权扩大到多引擎、多会话并发或新权限策略。
