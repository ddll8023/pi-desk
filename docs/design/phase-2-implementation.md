# 阶段 2：独立查询、配置生效与恢复完善

## 1. 定位与依赖

本阶段在[阶段 1](./phase-1-implementation.md)已经分离宿主与会话、建立必要快照解耦和基础故障收敛的前提下，完善查询、配置、认证、资源与 MCP 的职责覆盖。

架构约束见[设计基线](./runtime-sdk-migration.md)，开发关系见[开发总览](./runtime-development.md)。本文是开发讨论依据，不固定 API、文件结构、依赖版本或常量，不表示功能已实现。

## 2. 目标与范围

- 将模型、认证、静态资源和会话实际能力按来源与作用范围查询，不让完整目录依赖活动会话创建。
- 完善 Pi 配置与外部变化的刷新、生效及错误表达，区分配置读取、资源重载和宿主重启。
- 明确模型注册与认证服务的全局、项目和会话边界，避免跨项目可变 provider 污染。
- 完善资源重载、MCP 交互、宿主与会话恢复的诊断归属。
- 讨论认证 helper 是否合并；合并不是阶段 1 的前提，也不是本阶段必须采用的结果。

不新增配置副本、通用 provider 管理平台、权限规则引擎或多会话并发体系。Pi 配置与凭据机制继续由官方实现负责。

## 3. 查询责任与数据范围

| 范围 | 查询内容 | 不包含的能力 |
|---|---|---|
| Pi 全局基础 | 基础模型、认证是否配置、用户静态目录和默认设置的展示 | 当前项目扩展运行时的可变 provider、工具与连接 |
| 项目静态 | 当前项目与信任范围内的静态资源及设置预览 | 执行扩展、连接 MCP、把动态注册当作已确认能力 |
| 活动会话实际能力 | 当前模型、扩展贡献、工具、命令、MCP 和执行态 | 把当前会话状态冒充所有项目或全局目录 |
| 桌面索引与偏好 | 项目、会话文件索引和 GUI 偏好 | 平行消息持久化或 Pi 配置替代品 |

全局基础模型服务不接受项目扩展对其注册容器的长期修改。会话服务可以按官方生命周期重新创建，但基础展示快照独立保留。

资源加载器的名字不代表它不执行扩展。静态查询路径必须依据实际调用行为选择；无法安全静态获取的动态信息标作尚未加载，不为填充列表建立执行上下文。

## 4. 快照生命周期

每类快照明确来源、范围、当前刷新状态与错误。项目、信任、配置和认证变化分别使对应范围失效，不用一个全局刷新标记覆盖所有责任。

- 有相同安全范围的旧结果时继续展示，并明确正在刷新或刷新失败。
- 不用空清单代表查询失败；真实为空与没有取得结果必须区分。
- 查询并发可以合并，强制刷新后旧请求不得覆盖新结果。
- 会话切换不清空全局基础快照；项目变化不能沿用旧项目静态结果。
- 信任被撤回或资源范围变化时，旧快照不能继续被用作执行授权。
- 快照只是展示副本；模型真正是否可执行、认证是否有效仍由官方当前状态决定。

模型、认证和资源分别刷新。一项失败不使其他已有效数据消失；读取失败也不触发隐式配置重写。

## 5. 配置变化与生效数据流

### GUI 修改 Pi 配置

主进程校验业务意图，沿用 Pi 文件或官方受支持入口更新真实配置；随后通知相应查询和活动会话同步。文件写入结果、快照刷新结果、活动会话生效结果分别表达，不能以页面刷新成功冒充执行环境已经改变。

涉及模型、认证或资源上下文变化时，依据当前执行状态决定立即同步还是等待安全的空闲点。不能在运行中替换其正在使用的注册或连接，也不能因为暂时无法生效而重做已经写入的操作。

### CLI 或外部工具修改

应用重新获得焦点、接管会话或显式刷新时重新协调 Pi 配置与文件；若采用文件观察，需处理事件合并和不完整写入，具体方式留在详细设计中。

CLI 与 GUI 轮流接管后不使用旧会话内存继续写入；外部修改冲突与版本不支持应明确报告，不自动覆盖文件或丢弃未知条目。

### 生效层级

- **基础配置刷新**：重新读取设置、模型或认证，不代表会话已经替换。
- **会话资源重载**：由官方生命周期收敛扩展与资源，重新绑定相关交互和能力。
- **宿主重建**：仅用于故障或无法收敛的进程级状态，不作为普通配置生效的默认手段。

## 6. 认证服务与 helper 取舍

### 默认方向

先保留 helper，完善认证变化传播与生命周期。是否合并由真实 SDK 接口、登录交互、取消行为和凭据同步责任决定，不为了减少一个进程而合并。

### 有价值的合并条件

若统一到 SDK 宿主后，登录、查询和会话能够共享清晰的凭据更新责任，且长时间交互不阻塞会话中止和宿主恢复，可在本阶段讨论合并。若合并使宿主故障同时中断全部认证交互，或需要自行重写官方认证语义，保留 helper 更合适。

无论形态如何：

- 凭据真相继续由 Pi 管理，不持久化 GUI 副本。
- 页面只获得必要的认证状态和受限交互，不获得令牌或原始凭据记录。
- 登录、取消、退出与凭据修改有独立请求归属，旧登录回应不得作用于新流程。
- 认证变化同步到查询和活动会话；刷新失败保持真实错误，不伪装认证成功。
- 诊断和快照不携带凭据；对可执行的凭据解析来源不当作普通静态元数据读取。

## 7. 资源重载与 MCP

保留现有资源页、命令与 MCP 的业务语义，区分三个动作：

1. 静态列举配置，不连接服务器。
2. 主动连接或探测，可能启动进程或产生网络副作用。
3. 活动会话中的实际连接、工具、登录和重连，由官方能力负责。

资源目录查询不能隐式执行后两类动作。MCP 登录、工具审批和扩展弹窗回应仍通过可解除等待的交互通道；连接失败不清空无关模型和历史。

资源重载与会话替换共享失效、互斥和重绑规则。扩展退出时未清理的任务、计时器或外部连接是生命周期风险，不以过滤 stale-context 错误作为清理替代。

必要审批或信任机制不可用时禁止依赖它的执行，不为了容错降级成绕过权限。

## 8. 恢复与诊断完善

基础退出和结果未知处理已经在阶段 1 建立。本阶段补齐失败来源：宿主建立、配置读取、认证、静态查询、会话创建、资源加载、扩展执行、MCP 和投影同步。

诊断关联实际操作与范围，不将所有失败都展示为通用 Runtime 错误。保留安全的原因信息，不在日志里输出敏感配置或凭据。

- 宿主恢复只恢复基础设施，不能自动重放模型请求、回退、工具或认证写操作。
- 会话恢复重新读取 JSONL 与官方状态；活动上下文失效不等于文件历史丢失。
- 旧查询结果可读不等于当前可执行，旧工具结果也不表示副作用已撤销。
- 连续失败停止自动循环，保留窗口响应和可读数据；日常对话操作仍由应用管理宿主，不让用户反复处理 Runtime。

## 9. 开发拆分与待定问题

开发按查询范围、快照刷新、配置生效、认证同步、资源与 MCP、恢复诊断逐项收敛。各责任可以内部拆分，但配置与会话真相不复制到新的存储体系。

需要在本阶段讨论：

- 当前 SDK 的安全静态读取、模型 refresh 和凭据同步能力。
- 设置、模型、认证及资源变化如何影响活动会话，忙碌时如何明确延后生效。
- 外部文件变化的协调方式与 CLI 接管后的内存失效。
- 重载是否替换会话或 services，以及相关订阅和交互如何重绑。
- MCP 配置列举、实际连接、登录和探测的入口归属。
- helper 保留或合并的实质性收益与故障代价。

本阶段向[阶段 3](./phase-3-implementation.md)交接每个旧查询、认证和诊断入口的明确归属。仍在承担业务的旧责任不能只因迁移计划进入下一阶段而删除。
