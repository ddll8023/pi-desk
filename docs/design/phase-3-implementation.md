# 阶段 3：旧链路退役与发行整合

## 1. 定位与依赖

本阶段将[阶段 1](./phase-1-implementation.md)的会话主链与[阶段 2](./phase-2-implementation.md)的查询、配置和恢复责任收敛为单一发行架构。设计约束见[设计基线](./runtime-sdk-migration.md)，整体关系见[开发总览](./runtime-development.md)。

本文描述退役责任、发行边界和风险，不预先列出要删除的业务文件或假设所有旧模块都已无调用者。实际清理范围需在本阶段读取当时源码后逐项确定；本文不授权删除或运行操作。

## 2. 目标与范围

- 退役被 SDK 会话后端替代的 Pi standalone 启停、stdio 会话协议和旧状态编排。
- 退役被独立查询替代的一次性资源探针与命令适配，保留仍有业务用途的职责。
- 移除不再使用的独立二进制准备、复制与发行资源链。
- 收敛 SDK 宿主入口、依赖、资源路径和开发与发行组织。
- 清理旧用户入口和重复状态来源，Runtime 只保留内部监督、故障信息与必要诊断。

不删除 Pi JSONL、凭据、设置、项目目录或用户扩展；不迁移会话到 GUI 数据库，不创建平行配置。认证 helper 若阶段 2 决定保留，就作为正式职责保留，不为了“清理干净”删除。

## 3. 旧责任如何退役

| 旧责任 | 退役方向 | 必须保留的语义 |
|---|---|---|
| Pi standalone 会话进程 | 由 SDK 宿主接管活动会话后，退役对应启动与关闭入口 | 项目范围、信任、定向退出及应用关闭收敛 |
| 会话 stdio 协议 | 退役不再使用的分帧、请求关联和命令适配 | 结果未知、不重放、请求失效；仍用于其他正式进程的通信不连带删除 |
| 一次性资源与模型探针 | 在查询责任明确后退役相应探针 | 无执行静态预览、范围缓存和查询错误区分 |
| MCP 探测及旧命令桥 | 按阶段 2 的实际归属处理，不视为全部必删 | 静态配置与主动连接区分、用户取消和副作用边界 |
| 进程与会话共用状态模型 | 收敛为宿主、会话、执行和快照各自状态 | 用户动作与实际接管区分，失效旧态不能继续执行 |
| 独立二进制准备链 | SDK 随应用发行后退役旧下载与复制职责 | 可确定的应用运行环境，用户配置继续来自 Pi |
| 日常 Runtime 启停界面 | 从会话操作主路径移除，诊断另有归属 | 用户能理解故障并恢复对话，不被迫日常手动管理进程 |

删除条件是职责已经有明确承接，而不是文件名含 pi、runtime 或 protocol。需要同时阅读实际调用方、配置、脚本和用户入口，避免删掉仍服务认证或诊断的共用逻辑。

## 4. 构建与发行责任

### 宿主构建

阶段 1 已经建立可集成的宿主构建入口。本阶段统一应用主进程、沙箱 preload、页面、SDK 宿主和保留 helper 的组织，不引入没有事实支持的构建目标或脚本。

模块格式按 SDK 及动态加载的实际要求确定，不能因为主进程是某种格式，就强行让宿主采用相同格式。SDK、工具资源与动态导入的解析从发行物真实位置出发，不假设独立 Node 与 Electron 都能读取同一归档结构。

### 依赖与运行环境

SDK 随应用依赖和发行物管理，不自动寻找另一份 SDK，不依赖用户机器上偶然可用的 CLI。开发和发行宿主默认保持所选运行形态一致；若原生依赖需要差异方案，应作为明确兼容性取舍重新讨论，不暗中切换运行时。

处理 ESM、动态导入、ASAR 和原生模块的边界时，以真实依赖与发行配置为依据。进程隔离并不解决 ABI 不匹配，也不保证用户任意原生扩展都可加载。

宿主路径由应用控制，不接受页面传入的可执行文件、入口脚本或运行参数。内部通信继续经主进程校验，不借发行整合建立页面直连 Agent 的特权业务通道。

### 资源准备

区分应用自带运行资源与用户 Pi 数据：前者可随发行组织调整，后者不清理、不复制为应用私有真相。若发现废弃 staging 或缓存占用，应另行明确具体目录与清理授权，不随开发文档顺便安排删除。

## 5. 契约与用户入口收敛

- 页面使用对话操作与范围明确的查询契约，不依赖旧进程启停顺序表达加载状态。
- preload 保持窄桥；内部 SDK 对象与宿主消息不直接变成页面契约。
- 旧 RPC 错误码、状态和通道按实际调用关系处理，不为兼容已退役实现保留第二套状态源。
- 工具与扩展 UI、认证输入、外部 URL 打开和路径访问仍保留主进程权威边界。
- 诊断应区分宿主、会话、资源、认证和投影，不能把所有问题再次聚合为用户必须手动处理的 Runtime。

会话执行只有一个正式后端。不保留自动降级到旧 CLI 的路径，不以特性开关建设长期双引擎产品。

## 6. 数据与故障边界

退役代码不删除用户会话或配置，不尝试迁移、重写或“修复” JSONL。应用内部缓存与索引可重建，仍不能当作丢失会话的替代真相。

发行资源缺失、模块解析失败、原生扩展加载失败和会话恢复失败分别报告。宿主无法建立时保留窗口与本机信息，不启动未知外部运行时兜底。

正常退出终止应用拥有的活动宿主与必要子资源，防止恢复安排重新拉起进程；不按进程名批量结束用户 CLI 或其他应用。

CLI 与 GUI 交接继续采用结束旧所有权、重新读取权威文件的方式。应用内单活动会话不构成跨应用锁，也不扩大到并发写会话的承诺。

## 7. 开发拆分方向

1. **旧职责归属调查**：确定会话、查询、认证、MCP、投影、诊断和构建链的实际调用者，形成当阶段精确操作范围。
2. **旧业务入口退役**：解除旧会话后端与新主链的连接，处理重复状态和已替代契约；保留正式 helper 与必要查询职责。
3. **发行资源收敛**：统一 SDK 宿主与应用的依赖解析，退役独立二进制准备、复制及不再使用的发行入口。
4. **维护描述收敛**：若另获授权，按实际改动处理开发与使用说明；不扩大为全仓库文档维护，不自动更新项目记忆。

以上仅描述交付方向，不是删除文件清单，也不把测试、构建或运行写作默认收尾操作。

## 8. 本阶段待定事项与风险

需要依据前两阶段最终实现确定：

- 哪些旧模块、脚本、通道与资源已经无正式调用者，哪些仍承担独立职责。
- 宿主、SDK、动态工具资源和保留 helper 在发行物中的真实组织。
- 归档与外部资源的选择，以及用户原生扩展的兼容范围。
- 日常启停入口移除后，诊断和基础设施恢复如何保持可理解性。
- 如果新发行集成出现阻塞，如何暂停发布或回到对应设计点，而不是同时启用双会话写入后端。

主要风险是误删共用责任、发行解析与开发环境不同、原生依赖不匹配，以及把旧执行对象或用户数据误当作可清理资源。重构结束的方向是单一会话真相、单一正式执行后端和明确的生命周期，并不意味着全部等待和故障已经被证实消除。
