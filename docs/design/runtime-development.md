# 运行时与会话重构开发总览

## 1. 文档职责

本轮开发包含三个阶段，阶段 1 不是整个任务。本文维护职责拆分、阶段依赖与迁移边界，不重复设计决策或源码事实。

- [设计基线](./runtime-sdk-migration.md)：需求、约束、架构与已确认取舍。
- [架构调研](./runtime-architecture-analysis.md)：已读源码、判断依据与证据限制。
- [阶段 1](./phase-1-implementation.md)：SDK 宿主与完整会话主链。
- [阶段 2](./phase-2-implementation.md)：独立查询、配置生效与恢复完善。
- [阶段 3](./phase-3-implementation.md)：旧链路退役与发行整合。

本组文档是开发讨论与拆分依据，不表示业务代码已经实现，也不授权修改源码、执行测试、构建或启动服务。每个阶段的实际文件与操作范围，应在详细讨论后另行确定。

## 2. 总体交付方向

将当前以 Runtime 启停为核心的实现替换为以对话操作为核心的应用模型：

1. 一个应用管理的独立 SDK 宿主，一个活动 Agent 会话；宿主不随正常对话切换退出。
2. 宿主状态、目标会话准备状态、活动执行状态、展示快照状态分别表达，不用一个 ready 标志代表所有能力。
3. 会话树、队列、压缩与模型执行由 Pi 官方实现负责；桌面端只编排用户意图、权限边界、请求归属和展示投影。
4. Pi JSONL 与 Pi 配置继续是真相；缓存与索引可重新生成，不成为第二套消息或配置存储。
5. Runtime 在日常交互中退居内部，不把手动启停作为用户完成新建、打开或切换的常规前提。

## 3. 责任划分

| 责任 | 所有者 | 边界 |
|---|---|---|
| 桌面权威 | Electron 主进程 | 项目、信任、IPC 校验、路径归属、宿主监督与对外请求归属 |
| Agent 执行 | SDK 宿主与官方 SDK | 一个活动会话、工具与扩展执行、官方生命周期与模型服务 |
| 会话编排 | 桌面会话操作所有者 | 串行替换、用户确认中断、实际状态收敛；不重写官方 Agent 队列 |
| 查询与快照 | 范围明确的查询责任 | 全局基础、项目静态和会话动态能力分别刷新；不共享跨项目可变注册 |
| 消息展示 | 展示投影与渲染端 | 从权威历史和事件生成可重建视图，不反向成为会话真相 |
| 交互回应 | 代际明确的交互桥 | 审批、扩展弹窗、登录回应可解除执行等待，不排在等待它们的操作之后 |
| 认证执行 | 过渡期认证 helper | 沿用 Pi 凭据机制；状态变化通知查询与会话，是否合并在阶段 2 讨论 |

责任划分不要求每一项都独立成包、类、线程或进程。只有职责边界需要才拆模块，不额外建设多引擎框架、权限规则平台或事件持久化系统。

## 4. 三阶段规划

| 阶段 | 解决的问题 | 交付方向 | 依赖 |
|---|---|---|---|
| 1：会话主链 | 会话操作反复拆除环境，事件与交互归属耦合 | 可集成的常驻宿主、完整会话操作、独立代际、权威历史基准、必要快照解耦及基本故障收敛 | 设计基线；当阶段的官方 SDK 与调用链事实 |
| 2：查询与恢复完善 | 全局、项目和会话能力混用，配置生效与错误归属不清 | 独立查询责任、配置及认证同步、资源重载、MCP 交互和恢复诊断完善 | 阶段 1 的生命周期、信任和事件归属边界 |
| 3：旧链退役与发行 | 旧后端、探针、发行物和入口残留 | 单一会话后端、统一宿主发行资源、旧入口退役和维护边界收敛 | 前两阶段已经明确替代职责，不能删除仍承担业务的旧模块 |

宿主构建与依赖解析从阶段 1 就处理，不推迟到阶段 3。阶段 3 负责退役旧准备链和收敛发行方式，不负责首次让宿主能够集成。

## 5. 不能推迟的基础边界

以下内容随会话主链进入阶段 1：

- Project Trust 与主进程校验；必要工具审批、扩展 UI 和 SDK 内建能力。
- 宿主和会话分别换代，旧请求、事件、弹窗与投影不得覆盖新会话。
- preflight、压缩、排队、工具或扩展等待的操作守门，不只读取页面流式状态。
- 权威历史快照与实时事件的正确交接；失败不能把空历史伪装成恢复成功。
- 模型、认证和静态目录不因为会话切换被清空；认证变化不能长期停留在旧查询副本。
- 宿主退出后 pending 收敛、写入能力失效、结果未知不重放，以及基础设施的有上限恢复。

阶段 2 完善这些职责的覆盖面，不用阶段划分为阶段 1 的生命周期错误或安全缺口开豁免。

## 6. 迁移与交接

### 活动会话后端

迁移可以按职责保留旧查询或暂未替换的入口，但同一个活动 JSONL 只允许一个后端负责。会话执行转入 SDK 后，不自动降级到旧 CLI 重做未确认操作，也不保留日常引擎切换选项。

遇到 SDK 集成障碍，应回到受影响的设计点讨论，不以临时双写、手工改消息树或隐藏错误继续推进。若需要退回旧实现，必须先结束新后端的所有权并明确交接，不在故障处理中暗中切换。

### CLI 与 GUI 轮流接管

GUI 结束当前执行与写入责任后可交给 CLI。重新接管时从 Pi 文件读取，不能继续使用接管前的会话内存或历史投影。应用内单会话互斥不等于跨应用写锁；无共同协议时不承诺检测并阻止所有 CLI 并发写入。

### 项目与信任变化

项目切换或信任变化必须失效对应资源与执行上下文。正常项目变化优先替换会话和有范围的服务；进程级污染无法收敛时才重建宿主。全局快照仍可保留，项目快照不得跨范围混用。

## 7. 各阶段的设计关注点

各阶段的实际实现状态与具体接口只以代码及其注释为准，本文不记录进度与流水。

| 阶段 | 实质性设计问题 |
|---|---|
| 1 | 官方替换入口及失效顺序、宿主与会话请求归属、写操作互斥与解除等待、权威历史与事件交接、宿主构建及基础恢复 |
| 2 | 静态与动态查询的获取方式、配置和认证变更的作用范围、空闲与忙碌时生效行为、MCP 状态与执行隔离、认证 helper 是否合并 |
| 3 | 旧模块实际调用者与残留职责、SDK 宿主和发行依赖的组织、旧用户入口归属、配置与 JSONL 保留边界 |

各阶段文档覆盖目标、模块责任、数据流、失败边界、风险与待定问题，不提前固定业务代码路径、接口字段、依赖版本或容量常量。

## 8. 范围限制与不确定性

不扩展多活动会话、后台执行池、多引擎或新权限规则；不创建 Pi 配置副本、平行消息存储或数据迁移体系。文档工作不修改项目记忆。

独立宿主只能隔离部分故障和阻塞，不能保证消除页面长任务、历史解析或扩展初始化成本。没有实测数据时，不写切换时间、内存、CPU 或改善倍数承诺。具体 SDK、构建与原生扩展的适配仍是开发阶段需要核实的事实。
