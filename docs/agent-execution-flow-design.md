# Agent 执行流程优化设计文档

> **文档定位**：本文是初步设计，只界定问题、需求边界、机制方向与阶段目标。它不构成实施授权，
> 也不提供可直接照做的实现规格；具体实现与流程效果的确认在各阶段结合实际代码单独讨论。

---

## 1. 背景与问题

### 1.1 当前三个核心问题

**问题 1：简单任务与复杂任务共用同一套流程，成本结构失衡**

- 改一行注释同样要走：讨论阶段 → Skill 注册与正文加载 → 方案确认 → 执行清单 → 审核 → 执行。
- 主要成本来自两处：每条消息前必须完成的 Skill 登记与正文加载，以及简单任务上不可省的讨论轮次。
- 本次未对单任务 token 消耗做测量，上述为未验证的定性判断；若后续需要量化，应先建立计数口径再谈目标值。

**问题 2：需求分析没有分流点**

- 模糊输入直接进入执行，多种理解并行尝试，方向错了再重来。缺的不是「更严格的识别」，而是「按信号决定是否需要显式识别」。
- 现有规则只描述了讨论阶段该做什么，没有描述何种情况下可以缩短这一轮。

**问题 3：多轮对话的任务边界不清**

- 用户说「再加个搜索功能」时，无法区分它是上一个任务的延续还是新任务，前一个任务的假设与未完成讨论会混入后一个任务。
- 现有会话投影只记录消息与回合，没有任务级对象，也就没有可供判断与展示的边界信息。

### 1.2 设计目标

1. **简单任务可分流**：目标明确、改动面单一的请求减少强制 Skill 加载与讨论轮次，同时不削弱授权门。
2. **任务边界可判定且可纠正**：宿主与模型都能拿到「上一任务做了什么、影响哪些文件」，判定错误时用户可一句话纠正。
3. **宿主提供可观测的约束点**：流程约束落在可检查的钩子上，而不是只靠指令文字。

明确不做：

- 不改变文件修改、执行清单与运行操作的授权规则；任何模式都不豁免这些环节。
- 不引入新的沙箱或权限模型。
- 不在本设计内改写跨项目的全局规则文件（已单独落地，见第 7 节）。

### 1.3 参考项目与可采纳结论

参考 `docs/开源项目参考/` 下的四项调研。此处只保留对当前设计真正起作用的结论：

| 参考 | 可采纳结论 | 不采纳或需适配的部分 |
|---|---|---|
| TencentDB Agent Memory（`tencentdb-agent-memory.md`） | 检查点必须可观测，由宿主而非仅靠指令判定 | 其双阶段审批面向记忆写入，不适用于文件改动流程 |
| EvoFlow（`evoflow.md`） | 用户显式选择执行强度，系统据此收缩可用能力 | 「模式锁定」在本项目中即 Skill 集合裁剪，不是沙箱能力限制 |
| DeepSeek Harness（`deepseek-harness.md`） | 不同模式对应不同的能力集组合 | 其 Profile 组合面向工具集，本项目还需覆盖规范类 Skill |
| Lancer（`lancer.md`） | 多轮交互需要显式的任务拓扑与父任务关系 | 其 GitTree 结构依赖分支模型，本项目只需要任务级父子关系 |

## 2. 总体架构

### 2.1 执行流程

```
用户输入
  ↓
[宿主 input 钩子] 读取上一任务摘要与增量信号
  ├─ 信号充分 → 直接按判定结果继续，不额外产出识别段落
  └─ 信号不足 → 在输入上下文里标注「需显式识别」，由模型输出一次识别结果并等确认
  ↓
[模式决定] 快速 / 标准
  ↓
[宿主能力集裁剪] standard 保留全部 Skill；fast 剔除讨论与文档同步类 Skill
  ↓
[Agent 执行] 受现行授权规则约束：文件清单审批与运行授权不因模式改变
  ↓
[回合边界] turn_end / 消息定稿时校验必要标记；不足时以一次后续请求纠正，且只允许一次
  ↓
交付
```

关键取舍：**分类不在独立一轮里完成**。额外一轮完整模型往返本身就是成本的主要来源之一，因此分类信息由宿主在输入阶段补齐，模型只在信号不足时才显式输出识别结果。

### 2.2 两种执行模式

| | 快速模式 | 标准模式 |
|---|---|---|
| 适用场景 | 目标明确、单文件、低风险 | 需要讨论、多文件、存在设计决策 |
| Skill 能力集 | 仅技术栈规范（如 `vue-ts-spec`、`python-spec`） | 全部适用 Skill |
| 方案讨论 | 豁免 | 保留 |
| 执行清单审批 | **不豁免** | 不豁免 |
| 运行与测试授权 | **不豁免** | 不豁免 |
| 预期效果 | 减少 Skill 正文加载与讨论轮次 | 维持现状 |

快速模式只豁免「方案讨论」这一环，不豁免逐文件清单审批与运行授权；它是省成本的入口，不是绕过确认的入口。

## 3. 新任务流程

### 3.1 识别触发条件

显式识别只在以下情况发生，其余情况直接按判定结果继续：

- 输入存在多种合理理解，且不同理解导致不同改动面；
- 涉及不可逆或高影响操作；
- 用户提问本身模糊，缺少可执行目标。

识别结果不再使用固定分段模板，而是并入既有交付结构：`结果`（本次要做什么）／`修改`（涉及范围）／`问题清单`（仅列阻塞项）。没有阻塞项时不输出问题段落，避免把「澄清建议」变成例行提问。

### 3.2 模式锁定

用户确认后锁定两件事：可用 Skill 集合、讨论是否豁免。锁定发生在会话创建期，不改动授权规则。用户可以在同一任务内改判模式，改判只影响能力集，不影响已提交的清单与授权状态。

### 3.3 流程执行

- **快速模式**：读取目标上下文 → 执行改动 → 交付。
- **标准模式**：现行讨论阶段流程不变。

两种模式在「改动前是否需要逐文件清单审批」上保持一致，差异只在讨论与规范加载的深度。

## 4. 旧任务延续

### 4.1 关联性信号

按可靠性从高到低使用，得分式加权不采用：

1. **用户显式表述**：「现在做」「接下来」「另外」指向新任务；「再加」「改成」「不对应该」「修复刚才」指向延续。这是成本最低且最可靠的信号。
2. **指代与文件引用**：消息引用了上一任务涉及的文件、模块或改动点。
3. **上一任务的未完成项**：上一任务存在待决问题或未执行清单项，且本次输入指向同一对象。

不采用的方向：以文件重叠度加权语义相似度打分并设阈值。原因是中文正文不以空格分词，按空白与标点切词后绝大多数消息只剩单一词元，相似度退化为 0 或 1，总分实际由「消息里是否出现文件后缀名」单独支配，阈值也无来源。

信号不足时由模型用一句话确认，不建独立判定算法。

### 4.2 增量对齐

延续场景只对齐增量，不重复识别整个需求：

- 前一个任务做了什么（一句话）；
- 本次新增或变更的要求；
- 是否影响已完成成果（影响 / 不影响）。

沿用前一个任务已确认的技术栈决定与假设；不复用其「已完成」标记，避免把未交付内容当成已完成。

## 5. 任务上下文管理

### 5.1 任务对象与生命周期

任务对象描述（不在此阶段固定字段契约）：

- **身份与顺序**：任务标识、起止轮次、与父任务的关系；
- **判定输入**：原始消息、识别后的意图、推断范围、显式假设、关联性结论与置信度；
- **执行状态**：模式、状态（待确认／执行中／完成／失败）、涉及文件；
- **产出**：交付结果与未完成项。

生命周期：输入到达时创建 → 模式确定后进入执行 → 交付后标记完成，并把未完成项传递给后续任务。

**已核实的事实**：会话级文件读写聚合已存在——活动投影从每个工具调用提取文件事实（路径与读/写语义）并汇总为会话级列表，供对话区顶部活动条展示；缺的是轮次维度。因此轮次文件事实按此口径落地：活动聚合按轮归组、只记被修改的文件，展示落在回合头，不建任务对象。它决定延续判定信号 2 是否可用。

### 5.2 上下文隔离规则

- **新任务**：清理上一任务的假设、待决项与未完成讨论；保留项目技术栈配置与全局偏好。
- **延续任务**：保留上一任务的技术栈决定、已确认假设与代码成果；清理「已完成」标记。

边界判定的依据来自会话投影（宿主侧消息与工具调用记录），渲染端 store 只承载展示状态，不作为判定来源。

## 6. 宿主层约束机制

### 6.1 三层约束

| 层 | 作用 | 落点 |
|---|---|---|
| 指令层 | 描述识别触发条件与交付结构 | `AGENTS.md`（全局与项目级，见第 7 节） |
| 宿主钩子层 | 输入阶段补齐上下文、回合边界校验必要标记 | `src/sdk-host/session-runtime.ts` 的扩展工厂 |
| 能力集裁剪层 | 按模式剔除 Skill | `src/sdk-host/product-resources.ts` 的 `skillsOverride` |

现有先例：`resources/agent/extensions/skill-guard` 已在做每轮登记与工具调用前拦截，宿主钩子层不需要另建一套拦截骨架，应复用同形态的扩展注册方式。

### 6.2 输入与回合边界

已核实的钩子能力：

- `input` 事件可改写用户输入文本，也可声明已处理。适合在输入上下文里补入上一任务摘要或「需显式识别」标记，成本最低。
- `message_end` 只能替换已定稿消息，不能拒收，也不能阻止它出现在会话里。因此「校验失败即拒绝输出并要求重试」不成立。
- 需要纠正重试时，`turn_end`（与 `agent_before_settle`）可追加条目并请求一次后续模型请求；必须带一次上限保护，否则会形成循环。

据此，校验点定位为：**输入侧补齐上下文，回合边界做一次轻量检查**，不做输出拦截。

上下文补齐采用的注入点：`before_agent_start` 的系统提示分段（`event.systemPromptOptions.sections`），不改写用户可见的输入文本，也不改 transcript。不选 `input` 改写的理由：改写会改变用户自己看到的消息内容。宿主侧已验证扩展经 `ctx.sessionManager.getBranch()` 能读到分支、并在同进程内可取活动投影的按轮改动事实。

该注入当前**不启用**：历史消息已携带上一轮的工具调用记录，摘要存在相当重复，代价是每轮固定 token 与额外偏置；真实增量仅在于日志被压缩或折叠后仍保留改动面。启用时机与上限按当次事实再定，先以指令层的延续判定规则与回合头的改动展示覆盖需求。

### 6.3 能力集裁剪

模式需由主进程随宿主启动参数下发到 sdk-host；Skill 在 sdk-host 进程内由资源装载器组装（`additionalSkillPaths` + `skillsOverride`），过滤在此处按技能名剔除。

`src/main/sessions/sdk-host-manager.ts` 不参与 Skill 收集，不在改动范围。产品 Skill 来自随包资源，用户级 Skill 来自用户目录，两者都经过同一处组装，过滤逻辑只需一处。

## 7. 阶段规划

### 阶段 1：指令层与识别触发（先做）

- **目标**：把「何时需要显式识别」写成可执行规则，并去掉现有规则中与之重复或冲突的部分。
- **设计关注点**：与最短充分回答、提问是最后手段、讨论阶段确认门的边界；哪些段落是补充，哪些是替换。
- **依赖与风险**：全局规则改动影响所有项目，已在第 7 节单独落地；本阶段仅涉及项目级规则。

### 阶段 2：任务对象与边界投影

- **目标**：建立任务级对象，并把边界判定所需信息投影到宿主侧。
- **设计关注点**：任务对象与回合的对应关系；涉及文件列表的聚合方式（当前缺口）；如何在历史回放中重建任务边界。
- **依赖**：文件聚合设计先于展示层。

### 阶段 3：能力集裁剪

- **目标**：快速模式下按模式收缩 Skill 集合。
- **设计关注点**：模式如何随宿主启动参数下发；被剔除 Skill 被显式要求加载时的行为；裁剪不影响记忆、上下文与其他 SDK 发现能力。
- **依赖**：阶段 1 的模式语义定稿。

### 阶段 4：渲染端展示

- **目标**：让用户看见任务边界与关联性结论，并能一句话纠正。
- **设计关注点**：展示位置是回合级列表（`ChatMessageList.vue` 按 `turns` 渲染，不存在消息级循环）；判定结果来自宿主投影而非渲染端计算。
- **前置判断**：任务流程形态的展示已被移除，不再重做业务流程面板；只在轮次文件事实与延续上下文仍不足以支撑时，才以其它形态立项。
- **依赖**：阶段 2 的投影契约。

### 批次划分与最小可交付

四个阶段按依赖合为三个开发批次：

| 批次 | 包含阶段 | 依赖关系 | 体量判断 |
|---|---|---|---|
| 批次 1 | 阶段 1 + 阶段 3 | 互不依赖，只共享「模式」语义 | 两者都小 |
| 批次 2 | 阶段 2 | 含前置缺口：修改文件聚合当前不存在 | 主体工作量集中在此 |
| 批次 3 | 阶段 4 | 依赖阶段 2 的投影契约 | 小，且可延后 |

约束：

- 阶段 2 与阶段 4 不得合并实施。文件聚合与投影契约未定就做展示，会把错误的展示形态先固化下来。
- 阶段 4 不做也不影响前两批的收益，属可选批次。

**最小可交付**：阶段 3 加项目级规则，不建任务对象即可降低 Skill 正文加载成本。任务边界相关部分（阶段 2、阶段 4）整体后置，作为第二批决策。

**当前进度**：所有阶段已按设计文档完成或暂不立项。具体常Ǻ：
• 批次 1 全部落地：执行模式设置页开关、宿主 Skill 跟模式剔除、项目级与全局 AGENTS.md（执行模式＋延续判定＋显式识别触发三条）、pi-skill-setup Windows 模板同步。

## 8. 已核实的项目事实

1. 技术栈：Electron + Vue 3 + TypeScript + Pinia + Tailwind CSS v4。
2. 扩展注册：`src/sdk-host/session-runtime.ts` 中扩展工厂形状为「名称 + 工厂 + 是否内置 + 是否可替换」，钩子在工厂内注册。
3. 钩子能力：`input` 可改写或接管输入；`message_end` 只能替换定稿消息；`turn_end`／`agent_before_settle` 可追加条目并请求一次后续请求。
4. Skill 组装：`src/sdk-host/product-resources.ts` 通过 `additionalSkillPaths` 与 `skillsOverride` 组装，产品 Skill 来自随包 `resources/agent/skills`，用户 Skill 来自用户目录；`src/main/sessions/sdk-host-manager.ts` 无 Skill 相关逻辑。
5. 渲染结构：消息列表按回合（`turns`）渲染，任务边界标记应挂在回合级。
6. 现状缺口：代码中没有任务级对象，也没有修改文件的聚合，两者都需要新建。
7. 已有强制先例：`resources/agent/extensions/skill-guard` 已实现按轮拦截，可作为宿主钩子层的形态参考。

## 9. 风险

| 风险 | 说明 | 处理方向 |
|---|---|---|
| 边界判定误判 | 显式关键词之外的输入可能把新任务判为延续 | 判定结果始终可被用户一句话推翻，不静默沿用旧假设 |
| 输入钩子影响面 | 输入钩子对所有会话生效，逻辑错误会污染全部对话 | 钩子只做上下文补入，不做拒绝；异常时退回原始输入 |
| 模式被滥用 | 用户用快速模式发起高风险改动 | 检测到跨多文件或不可逆操作时提示切换模式，但审批规则不变 |
| 合规感退化 | 去掉固定识别模板后，看起来「流程变少了」 | 授权门未变；交付结构仍要求列出阻塞项与影响范围 |
