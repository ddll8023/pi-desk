# pi-desk 终端常驻初步设计

本文说明需求、范围、架构方向与关键取舍，不是实现规格。逐字段协议、常量与文件清单在开发阶段按当次事实确定。

## 1. 问题与已确认需求

用户要求：终端常驻，关闭也要继续运行，参考 [orca](https://github.com/stablyai/orca)。

已确认的范围（本轮）：

- 关闭动作覆盖「退出应用」：退出后终端与其中的命令继续运行，重新打开应用自动接回。
- 恢复程度为「进程 + 完整滚动历史」：接回时连同应用退出期间的输出一起回放。
- 本轮只做终端，不含内置对话会话（SDK 宿主）的常驻与重连。

## 2. 现状事实

- 终端 PTY 原本运行在 Electron 主进程内；关闭窗口即退出应用，退出链会终止全部终端进程树，因此重启后终端与历史全部丢失。
- 页面重载已经能接回存活终端，工作区标签能按终端清单自动重建，这部分接回链路可复用。
- 已退出的终端记录保留到页面显式关闭，用于如实展示退出码。

## 3. 目标与非目标

目标：

- 应用退出（含崩溃）后终端继续运行；重新启动按同一批终端接回。
- 接回时还原滚动历史与终端模式（备用屏、光标、颜色等），退出期间的输出不丢。
- 用户始终有明确的「结束终端」入口，常驻不意味着无法清理。

不做（本轮）：

- 不常驻内置对话会话；SDK 宿主仍随应用退出终止。
- 不把「关闭终端标签」改成「保留后台进程」：关标签仍结束该终端。
- 不引入进程内 PTY 回退：守护进程不可用时直接报错，避免出现「一部分终端不常驻」的不确定语义。
- 不做多窗口、多用户共享同一批终端。

## 4. 架构方向

参考 Orca 的做法（独立守护进程持有 PTY、按版本化端点通信、快照式接回），按本项目现状裁剪为三层：

- **终端守护进程**：独立进程，脱离应用运行，持有全部 PTY、画面状态（headless 模拟器）、待下发缓冲与历史文件。
  它自己决定 shell 与环境，只接受「项目路径 + 尺寸 + 终端标识」这类终端语义请求。
- **主进程客户端**：把页面请求转成守护进程请求，保留项目路径校验与页面契约错误文案；应用退出时只断开连接。
- **渲染端**：先取画面快照再收实时输出；快照带「已下发字符数」进度，实时段据此判断是否已被快照覆盖。

守护进程与应用之间的传输是本地流式套接字（Windows 命名管道 / POSIX Unix 套接字），按行分帧，握手校验
协议版本与一次性 token。端点名与 token、pid 文件都带协议版本，使不兼容的两代守护进程互不覆盖。

## 5. 恢复与数据流

- 输出到达时同时更新：历史文件（追加、限量裁剪）、模拟器画面、待下发缓冲。
- 页面接回时先取快照：冻结该终端的新输出 → 排空模拟器写入 → 序列化 → 清空待下发缓冲 → 放行冻结输出。
  这样快照与随后的实时数据既不重复也不丢段。
- 应用退出后没有客户端：输出只进缓冲与历史，超过上限时用 PTY 流控暂停读取，避免内存无界增长。
- 守护进程重启（机器重启、崩溃）后：按落盘的会话元数据与历史重建「已结束但保留历史」的终端，
  用户可以查看与关闭；重新运行命令需要用户自己再开一个终端。

## 6. 关键取舍

- **独立进程而非托盘常驻**：托盘常驻只能覆盖「关窗口」，真正退出应用仍会终止终端，与需求不符；两者不叠加。
- **快照而非纯原始回放**：纯回放长历史慢、且无法表达当前画面；快照体积小、状态准，代价是守护进程常驻内存。
- **同时保留原始历史与快照**：前者跨进程重启可重放，后者只活在内存；两者互补，落盘只做前者。
- **协议版本不向前兼容**：版本不符就连不上，旧守护进程里的终端由用户显式结束，不静默杀掉正在运行的任务。
- **运行中数量上限**：已退出但保留历史的终端不占额度，避免常驻后接回一批旧终端就再也开不了新终端。
- **运行目录延迟到首次使用时解析**：终端管理器在模块顶层构造，早于便携版把 userData 改到程序目录；
  构造时读取会让便携版与开发态共用同一端点、互相接管终端。

## 7. 风险与前提

- 守护进程会持有 PTY 与随包的原生模块，因此在覆盖解压新版本、重装依赖前必须先停止守护进程
  （设置页「终端」→「停止守护进程」，或关掉全部终端后等空闲退出）。否则目标文件被占用，解压或更新会失败。
- Windows 上守护进程能否真正脱离应用进程是方案成立的前提：若宿主把应用放进带 kill-on-close 的作业对象，
  终端会随应用退出。需要在目标机器上实测；失败时需要一个额外的 breakaway 启动器，成本上升。
- 从 Windows Terminal 标签页启动应用时，终端自身的作业对象同样可能限制脱离。
- node-pty 原生模块需在守护进程与新出包路径下正确加载。
- 常驻资源：会话数量 × 回滚行数的模拟器内存，加上每终端限量的历史文件，需要上限与清理策略。
- 本地 IPC 安全：端点按运行目录散列、token 仅当前用户可读；不提供跨用户隔离之外的保护。
- 快照按守护进程侧的行列序列化，接回时若窗口尺寸不同会出现重排差异；全屏程序在尺寸同步后会自行重绘。

## 8. 阶段

1. 守护进程骨架、协议与端点、PTY 迁移、退出不终止、重启接回（内存快照）。
2. 历史与元数据落盘、守护进程重启后的历史恢复、裁剪与清理。
3. 标题与状态展示、全部关闭与旧版本守护进程提示、开发态残留处理。
