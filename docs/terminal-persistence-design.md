# pi-desk 终端常驻初步设计

本文说明需求、范围、架构方向与关键取舍，不是实现规格。逐字段协议、常量与文件清单在开发阶段按当次事实确定。

## 1. 问题与已确认需求

用户要求：终端常驻，关闭也要继续运行，参考 [orca](https://github.com/stablyai/orca)。

已确认的范围（本轮）：

- 关闭动作覆盖「退出应用」：退出后终端与其中的命令继续运行，重新打开应用自动接回。
- 恢复进程与保留窗口内的滚动历史：接回时包含退出应用期间仍在保留范围内的输出，不承诺无限历史。
- 本轮只做终端，不含内置对话会话（SDK 宿主）的常驻与重连。

## 2. 现状事实

- PTY、画面解析和历史落盘由独立守护进程持有；退出应用只断开连接，不结束终端。
- 页面按终端清单重建标签，逐视图读取画面，解析完成后才开启实时投递。
- 已退出的终端保留轻量记录与磁盘画面；查看时恢复，切走释放视图，不为所有历史记录常驻模拟器。
- 显式关闭终端删除其历史；停止守护进程结束进程，但保留恢复资料。

## 3. 目标与非目标

目标：

- 应用退出（含崩溃）后终端继续运行；重新启动按同一批终端接回。
- 接回时还原保留窗口内的滚动历史与终端模式（备用屏、光标、颜色等）；离线输出仍持续消费，不因页面不存在而把命令永久堵住。
- 用户始终有明确的「结束终端」入口，常驻不意味着无法清理。

不做（本轮）：

- 不常驻内置对话会话；SDK 宿主仍随应用退出终止。
- 不把「关闭终端标签」改成「保留后台进程」：关标签仍结束该终端。
- 不引入进程内 PTY 回退：守护进程不可用时直接报错，避免出现「一部分终端不常驻」的不确定语义。
- 不做多窗口、多用户共享同一批终端。

## 4. 架构方向

参考 Orca 的做法（独立守护进程持有 PTY、按版本化端点通信、快照式接回），按本项目现状裁剪为三层：

- **终端守护进程**：独立进程，脱离应用运行，持有 PTY、运行会话的 headless 画面与限量历史；终端协议查询由它统一回答。
  它自己决定 shell 与环境，历史落盘和解析均按批次处理，并向会话管理反馈消费进度。
- **主进程客户端**：转发受限请求，按终端分块取画面，保留项目路径校验与真实错误文案；状态查询不启动守护进程，显式新建终端才允许启动。
- **渲染端**：每次挂载建立独立投递代际；按画面原尺寸解析完毕后确认恢复，再按连续进度接收实时输出，累计确认已消费内容。

守护进程与应用之间的传输是本地流式套接字（Windows 命名管道 / POSIX Unix 套接字），按行分帧，握手校验
协议版本与实例 token。认证成功后才接管连接，响应绑定原 socket；端点、凭据、独占锁与持久化资料按协议版本隔离，不兼容的两代守护进程不共享写入。

## 5. 恢复与数据流

- 输出进入批量历史写入与画面解析；只有处于恢复或实时投递中的视图才需要待下发缓冲。
- 接回时暂停该终端的 PTY 读取，排空解析并建立快照边界；随后恢复读取，画面按块传送。页面排空旧写入、按原尺寸解析快照并确认完成后，才释放边界之后的实时段。
- 同一终端的快照工作串行执行；恢复有期限，失效代际不能重新开启投递。快照及所有待处理队列都有容量约束，不把无限输出转存为 Promise 链。
- 没有页面时不积累页面投递缓冲。历史和模拟器仍消费输出；只有磁盘或解析本身跟不上时才短暂背压，消费回落后自动恢复。
- 实时数据与尾部输出都按剩余预算分片，累计 ACK 只能推进当前代际的已消费进度；旧页面、重复确认不影响新页面额度。
- 退出会话将画面冷存储并释放模拟器。守护进程重启后只恢复轻量记录，查看时按需读取磁盘画面或重放限量原始历史；重新运行命令需新建终端。
- 正常停止先禁止新的元数据调度，再保存画面与记录并收敛进程；与显式关闭终端的删除路径分开。

## 6. 关键取舍

- **独立进程而非托盘常驻**：托盘常驻只能覆盖「关窗口」，真正退出应用仍会终止终端，与需求不符；两者不叠加。
- **快照而非纯原始回放**：纯回放长历史慢、且无法表达当前画面；快照体积小、状态准，代价是守护进程常驻内存。
- **同时保留原始历史与快照**：前者跨进程重启可重放，后者只活在内存；两者互补，落盘只做前者。
- **协议版本不向前兼容**：版本不符就连不上，旧守护进程里的终端由用户显式结束，不静默杀掉正在运行的任务。
- **限制重资源而非历史标签数**：运行中和正在保存画面的模拟器共同受资源额度约束；完成冷存储的退出记录不常驻模拟器，也不占该额度。
- **限量保留而非无限历史**：滚动缓冲、原始历史、恢复长度与快照容量均受代码中定义的限制。过大的快照优先减少回滚部分；活动屏仍超过容量时明确报错，不截断 ANSI 流或反复断线。
- **运行目录延迟到首次使用时解析**：终端管理器在模块顶层构造，早于便携版把 userData 改到程序目录；
  构造时读取会让便携版与开发态共用同一端点、互相接管终端。

## 7. 风险与前提

- 守护进程会持有 PTY 与随包的原生模块，因此在覆盖解压新版本、重装依赖前必须先停止守护进程
  （设置页「终端」→「停止守护进程」，或关闭全部终端并断开应用，等待空闲退出）。否则目标文件被占用，解压或更新会失败。
- Windows 上守护进程能否真正脱离应用进程是方案成立的前提：若宿主把应用放进带 kill-on-close 的作业对象，
  终端会随应用退出。需要在目标机器上实测；失败时需要一个额外的 breakaway 启动器，成本上升。
- 从 Windows Terminal 标签页启动应用时，终端自身的作业对象同样可能限制脱离。
- node-pty 原生模块需在守护进程与新出包路径下正确加载。
- 常驻资源：运行中的模拟器与有界队列仍有成本；慢盘或持续高吞吐会触发背压。历史记录保留到用户显式关闭，其磁盘总量仍随保留记录数量增长。
- 协议升级不自动接管或终止旧实例，也不删除旧版本资料；回退代码不会覆盖新版本独立的持久化目录。
- 本地 IPC 安全：端点按运行目录散列、token 仅当前用户可读；不提供跨用户隔离之外的保护。
- 快照按守护进程侧的行列序列化，接回时若窗口尺寸不同会出现重排差异；全屏程序在尺寸同步后会自行重绘。

## 8. 阶段

1. 守护进程骨架、协议与端点、PTY 迁移、退出不终止、重启接回（内存快照）。
2. 历史与元数据落盘、守护进程重启后的历史恢复、裁剪与清理。
3. 标题与状态展示、全部关闭与旧版本守护进程提示、开发态残留处理。
