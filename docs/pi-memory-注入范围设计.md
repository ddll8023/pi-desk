# pi-memory 注入范围与预算设计

## 1. 文档定位

本文是 pi-desk 记忆背景注入的初步设计：确定本轮要注入哪些内容、各段如何分配额度、哪些能力整体退出，以及独立查看器 memory-manager-web 的同步要求。供后续开发会话接手；逐文件改动、实现常数取值细节与验证安排留到开发阶段按当时事实确定。

涉及两个仓库：本仓库 `pi-desk`（真实注入的装配方）与 `H:\code\memory-manager-web`（只读查看器，复刻同一装配口径供人工预览）。

### 1.1 名词约定

全文只用下列名称，不再使用「召回段」「五段」「两段预算」等同义替换。

| 术语 | 含义 | 代码／配置对应 |
| --- | --- | --- |
| 背景注入 | 每轮模型请求前由扩展装配、只进入本请求的一段记忆文本 | `pi-memory.background.v1`；`MemoryRuntime.background` |
| 适用偏好 | 画像段：按领域取用的全局或领域画像 | `profileSection`；`memory_profiles` |
| 常驻约定 | 近七天、带 `rule_key` 的决定与约束，按族取最新 | `residentSummary` |
| 当前项目近况 | 当前项目近七天非规则类记录的有限条预览 | `projectNotes` |
| 任务召回 | 按用户任务词法检索后注入的日记（本轮退出） | `recall.ts`；`recall-background` |
| 报错召回 | 按工具报错指纹匹配 issue 记录的注入（本轮退出） | `errorBackground`；`error-recall` |
| 注入审计 | 每次装配留下的一条不含正文的元数据条目 | `pi-memory.injection.v1`；`MemoryInjectionSnapshot` |
| 预览复刻 | memory-manager-web 按同一口径重算并展示常驻与近况 | `store.resident` |

## 2. 已确认需求与目标

1. **常驻约定与当前项目近况共用一个 10,000 字符上限**，不再是两段独立预算。
2. **移除任务召回与报错召回两段注入**：不再自动检索日记、不再按报错指纹注入历史。
3. **memory-manager-web 同步**：预览复刻必须与真实注入同口径。

目标是让模型每轮看到的记忆更少、更稳定：约定优先、近况次之，其余一律靠模型主动检索。

## 3. 范围与不做项

做：

- 装配侧的段集合、预算分配与状态报告；
- 注入审计、跨进程快照契约与「记忆注入」卡片的分段；
- 引擎侧只服务这两段的只读入口及其 CLI 说明；
- 两个仓库的文档与界面数字口径；
- 停用判定（用户明确要求不使用记忆时跳过背景）保留。

不做：

- 不删除、不改写任何记忆记录，不改库结构、词表与画像；
- 不改 `memory_search`、`memory_rules`、`memory_read`、`memory_profiles`、`memory_save` 等主动工具；
- 不为旧会话的审计条目做迁移或兼容；
- 不改记忆桥（`server/bridge`）的注入文本结构与格式；
- 不在本设计内安排构建、测试、启动或验证。

## 4. 项目事实

以下为设计依据，均已核对当前代码。

| 事实 | 来源 |
| --- | --- |

| 现状预算：约定 17,000、近况 3,000、总预算 20,000，两段各自独立结算 | 同上，顶部常量 |
| 任务召回依赖独立模块 `recall.ts`，其中只有停用判定被入口复用 | `recall.ts`、`index.ts` |
| 引擎侧有 `recall-background` 与 `error-recall` 两个只读子命令，仅这两段消费 | `engine.ts`、`memory_store.py` |
| 注入审计为五段，跨进程契约与渲染层卡片按五段校验与展示 | `src/shared/runtime/memory.ts`、`MemoryInjectionDialog.vue` |
| memory-manager-web 在 `server/store.mjs` 顶部复刻同一组预算常量，注释明确要求与扩展保持一致；README 与需求文档也写了这些数字 | `server/store.mjs`、`README.md`、`docs/REQUIREMENTS.md` |

事实冲突：memory-manager-web 的 `docs/REQUIREMENTS.md` 中常驻视图需求写的是「预算 20000 字符」，与 pi-desk 代码的总预算一致，但与「约定 17,000 / 近况 3,000」的分段口径不一致。本轮统一为合计 10,000 后，两处都需要改写。

## 5. 设计思路与关键取舍

### 5.1 共享预算池（推荐，已确认）

常驻约定与当前项目近况共用 10,000 字符：先按现有预算顺序给常驻分配（归属 → 约束优先 → 日期），近况再按日期倒序使用剩余额度，放不下就整条跳过并报出被丢弃条数。

理由：约定用于约束本轮产出，近况只是「这个项目最近在做什么」的背景；固定比例切分会让近况额度长期闲置，而规则挤不下时又无法借用。单条上限、索引行行数保持现状，索引行与段尾提示不占预算——这与现有「预算只约束正文块」的口径一致。

备选方向：固定 7,000 / 3,000 切分。不采用，原因是它把「哪一段更需要额度」提前固定，与真实数据分布无关。

### 5.2 整链删除而非只停注入

移除的是整条链路：装配调用、审计段、卡片 tab、引擎只读入口、CLI 说明与两处文档。理由：注入停止后这些入口没有消费方，保留会形成第二套无人使用的路径，与「同一职责只保留一个实现」相冲突。

停用判定不是召回的一部分，它决定「用户明确说不要用记忆时跳过整段背景」，继续保留。

### 5.3 旧审计不兼容

审计条目的段集合改为三段后，旧会话里带五段的条目按无效处理，卡片显示「没有审计」。开发期不写迁移：重新发一轮请求即写入新条目。影响面仅限历史会话的核对视图。

### 5.4 跨仓一致性

真实注入与预览复刻是两份实现，共享同一口径。预算改变后必须同批落地，否则查看器会展示与实际注入不符的结果。字段名不要求相同，语义必须一一对应：合计上限、约定用量、近况用量、剩余额度。

## 6. 职责与数据流

装配顺序：适用偏好 → 常驻约定 → 当前项目近况。预算只在后两段之间共享，画像段维持自己的上限与降级方式。

```
请求 → 装配
  ├─ 适用偏好（领域画像，独立上限）
  ├─ 常驻约定（近七天、族内最新、当前项目+通用）──┐
  └─ 当前项目近况（近七天、当前项目、非规则类）──┴─ 共用 10,000，规则优先
→ 注入审计（三段状态与条目身份，不含正文）
```

审计只记录段状态与条目身份，正文仍按记录 ID 或画像领域另取；`/memory status` 摘要随段集合调整，完整字段仍由 `status json` 输出。

memory-manager-web 侧：`store.resident` 是唯一实现，预览视图与记忆桥共用；桥只读注入块与索引行，不读预算字段，因此预算改动不影响桥的注入文本。

## 7. 影响面（模块级）

逐文件改动在开发阶段按当时事实确定，此处只界定需要动的模块。

| 模块 | 现状 | 目标 |
| --- | --- | --- |
| 扩展装配 | 五段、两段独立预算、召回与报错各带独立超时与缓存 | 三段、共享预算、删除两段及其状态与缓存 |
| 停用判定 | 与召回同模块 | 迁入装配模块，行为不变 |
| 引擎只读入口 | 有 `recall-background`、`error-recall` | 删除；主动检索入口不受影响 |
| 注入审计与契约 | 五段、含请求键 | 三段、去掉只由召回产生的字段 |
| 记忆注入卡片 | 五个 tab | 三个 tab，清理召回专用状态文案 |
| 状态查询 | 摘要含召段状态 | 只报常驻与近况 |
| memory-manager-web 装配复刻 | 两段独立预算常量 | 共享池，返回合计用量与剩余额度 |
| memory-manager-web 视图 | 预算条按约定用量 | 按合计用量 |
| 两仓文档 | 分别记录 17,000 / 3,000 / 20,000 | 统一为合计 10,000 与规则优先 |

## 8. 风险与待定

| 项 | 性质 | 说明 |
| --- | --- | --- |
| 近况可能被规则挤到 0 条 | 已接受的取舍 | 规则优先的直接结果；丢弃条数仍会报出，不静默 |
| 旧会话审计失效 | 已接受的取舍 | 卡片显示「没有审计」，重新发请求即恢复 |
| memory-manager-web 工作区有未提交改动 | 开发时需先确认基线 | `server/store.mjs`、`server/server.mjs`、`server/bridge/tools.mjs`、`tests/store.test.mjs`、`docs/REQUIREMENTS.md` 处于 modified 状态，改动叠加在这些内容之上 |
| 单条正文上限是否随合计预算下调 | 待定（开发阶段确定） | 当前倾向保持 2,000 / 1,200，避免同一条正文被切得更碎 |
| 状态查询字段是否改名 | 待定（开发阶段确定） | 现有字段名含「召回」语义，倾向改为只表示背景段状态 |
| 是否需要同步修改桥的注入文案 | 开发时核对 | 桥按注入块与索引行拼接，预算变化不改变结构；若新增「未展开条数」文案需单独确认 |
