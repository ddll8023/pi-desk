# pi-memory 注入范围与预算设计

## 1. 文档定位

本文是 pi-desk 记忆背景注入的初步设计：确定本轮要注入哪些内容、各段如何分配额度、哪些能力整体退出，以及独立查看器 memory-manager-web 的同步要求。供后续开发会话接手；逐文件改动、实现常数取值细节与验证安排留到开发阶段按当时事实确定。

涉及两个仓库：本仓库 `pi-desk`（真实注入的装配方）与 `/Users/mima1234/Desktop/code/memory-manager-web`（只读查看器，复刻同一装配口径供人工预览）。

## 2. 已确认需求与目标

1. **常驻约定与当前项目近况共用一个 10,000 字符上限**，不再是两段独立预算；两段候选合并为一个按日期倒序的序列结算，近期优先，装不下即停并报出截止日期与被丢弃条数。
2. **移除任务召回与报错召回两段注入**：不再自动检索日记、不再按报错指纹注入历史。
3. **memory-manager-web 同步**：预览复刻必须与真实注入同口径。

目标是让模型每轮看到的记忆更少、更稳定：约定优先、近况次之，其余一律靠模型主动检索。

## 3. 范围与不做项

做：

- 装配侧的段集合、预算分配与状态报告；
- 注入审计、跨进程快照契约与「记忆注入」卡片的分段；
- 引擎侧只服务这两段的只读入口及其 CLI 说明；
- 两个仓库的文档与界面数字口径；
- 停用判定（用户明确要求不使用记忆时跳过背景）保留。

不做：

- 不删除、不改写任何记忆记录，不改库结构、词表与画像；
- 不改 `memory_search`、`memory_rules`、`memory_read`、`memory_profiles`、`memory_save` 等主动工具；
- 不为旧会话的审计条目做迁移或兼容；
- 不改记忆桥（`server/bridge`）的注入文本结构与格式；
- 不在本设计内安排构建、测试、启动或验证。

## 5. 设计思路与关键取舍

### 5.1 共享预算池（推荐，已确认）

常驻约定与当前项目近况共用 10,000 字符，两段候选合并为一个序列按日期统一结算：日期降序 → 同日 `constraint` 先于 `decision` → 规则先于近况 → 记录 ID 降序。装不下就停在该条之前，报出本次覆盖的截止日期与被丢弃条数，不回头补齐更早的条目。

理由：目标是「重点是近期」，不是把近三天的记录全部装入。按日期统一排序后，装不下的部分自然落在最老的一端；若沿用「约定先占满额度、近况吃剩余」，类型会压过日期，近况（恰恰是库里最新的记录）每次都是 0 条，等于按类型把最近的事实清零。

约束：合并结算不放宽任何数量上限——近况仍为当前项目内最多 3 条，作为段内约束，不参与跨段排序；单条上限保持约定 2,000、近况 1,200；索引行行数与段尾提示不占预算，与现有「预算只约束正文块」的口径一致；画像段维持自己的上限与降级方式，不并入共享池。

备选方向：①固定 7,000 / 3,000 切分——不采用，它先把额度按类型分好，而按日期排序已经能保证近期优先，再切一次只会让规则侧更紧；②保留约定绝对优先、近况吃剩余——不采用，理由同上，会让近况段恒为空。

### 5.2 整链删除而非只停注入

移除的是整条链路：装配调用、审计段、卡片 tab、引擎只读入口、CLI 说明与两处文档。理由：注入停止后这些入口没有消费方，保留会形成第二套无人使用的路径，与「同一职责只保留一个实现」相冲突。

停用判定不是召回的一部分，它决定「用户明确说不要用记忆时跳过整段背景」，继续保留。

### 5.3 旧审计不兼容

审计条目的段集合改为三段后，旧会话里带五段的条目按无效处理，卡片显示「没有审计」。开发期不写迁移：重新发一轮请求即写入新条目。影响面仅限历史会话的核对视图。

判据不能只看段集合：现行校验把 `recall`、`resident`、`notes` 列为必需键，`errors`、`profiles` 列为可选键；只删掉 `recall` 的必需性，旧五段条目仍然全部通过校验，与「旧条目按无效处理」相反。因此把审计 `version` 升到 2——扩展只写 2，契约只认 2，新旧由版本区分而不是由键集合推断。只由召回产生的 `requestKey` 同批删除，不再保留一个恒为 null 的必需字段。

### 5.4 跨仓一致性

真实注入与预览复刻是两份实现，共享同一口径。预算改变后必须同批落地，否则查看器会展示与实际注入不符的结果。字段名不要求相同，语义必须一一对应：合计上限、约定用量、近况用量、剩余额度。

### 5.5 结算单元与缓存

合并结算意味着两段不能再各自缓存：现有两段各自保存结果与失败计数，共享额度后会让一段的失败把额度错配给另一段，而错配在本会话内无法自愈。

结算单元固定为一份：两段候选、额度分配、分段落正文、条目身份与用量统计一次算完、一起缓存；任一段读取失败则整份不缓存，下一轮整份重算。单次结算内的重试与超时上限保持现状。缓存失效条件与今天相同：会话内保存、`/memory refresh`、配置版本变化、会话切换。

## 6. 职责与数据流

装配顺序：适用偏好 → 常驻约定与当前项目近况（合并结算）→ 注入审计。画像段维持自己的上限与降级方式，不参与共享池。

```
请求 → 装配
  ├─ 适用偏好（领域画像，独立上限）
  ├─ 候选合并：常驻约定（近七天、族内最新、当前项目+通用）
  │              当前项目近况（近七天、当前项目、非规则类、最多 3 条）
  ├─ 按日期降序统一结算 —— 共用 10,000；同日 constraint 先于 decision，规则先于近况
  │                         装不下即停，报出截止日期与被丢弃条数
  └─ 输出时分段：约定在前、近况在后，各自保留段标题
→ 注入审计（三段状态与条目身份，不含正文）
```

审计只记录段状态与条目身份，正文仍按记录 ID 或画像领域另取；`/memory status` 摘要随段集合调整，完整字段仍由 `status json` 输出。

memory-manager-web 侧：`store.resident` 是唯一实现，预览视图与记忆桥共用；桥读的是装配结果（展开条目、索引行、近况），不直接读预算字段，所以文本结构不变，但展开哪些条目会随口径改变，必须与真实注入同批更新。
