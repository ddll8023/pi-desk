# Pi 桌面客户端生态调研

## 目的与范围

本文为 Pi Desktop（`pi-desk`）后续开发提供生态参考：这些项目都在把同一个 Pi coding agent 装进桌面壳里，它们已经反复验证过的进程边界、权限语义、扩展桥接与分发策略，可以直接决定我们少走哪些弯路。

范围限定为生态内的桌面客户端，共 10 个。不含纯 Web UI、CLI 包装与编辑器插件（例如 Web 端与 VS Code 扩展形态的项目不在本文讨论对象内）。

本文只写定性结论，不写 star 数、版本号、发布日期、下载量等会随发布变动的数值；数据口径与核对方式见末节。

## 项目清单

下列顺序沿用源表的热度排序，仅表示生态内的相对热度梯队，不含具体数值。

### 1. `vastsa/PI-Desktop` — 插件化的桌面工作台

- **许可**：LGPL-3.0
- **技术栈**：Electron + React，外加 Rust 侧 `host-core`（源码构建需 stable Rust 工具链）
- **Pi 集成方式**：库内嵌。直接依赖 `pi-ai` / `pi-agent-core` / `pi-coding-agent`，Pi 提供 Agent 引擎，桌面端自建工作区、会话、权限、插件与编排。
- **值得记录的功能**：插件能力矩阵（命令、面板、浮动小组件、工作台视图、Agent 工具、补全、Skill、主题、MCP Server、Service、插件间 Message Bus），`.piplug` 包与市场分发、开发态插件直载；三种工作模式 Agent / Plan / Goal；Subagents 与 Session Orchestrator 两级委派；项目 → 会话 → Agent → Work 的四级工作模型。
- **可借鉴点**：把"核心保持精简、工作流由扩展组装"当作架构前提而非事后补丁；插件能力矩阵的划分方式；插件之间用 Message Bus 解耦而非互相直接引用。

### 2. `minghinmatthewlam/pi-gui` — 会话驱动的工作台

- **许可**：MIT
- **技术栈**：Electron + React，pnpm monorepo（桌面应用、官网、SDK 驱动包、会话驱动包、目录状态包、扩展 UI 包、示例扩展）
- **Pi 集成方式**：库内嵌，但收在单一的 SDK 适配包里；主进程负责窗口、会话监督、worktree、终端 PTY、计划任务、通知与持久化；渲染进程只能走 typed IPC。会话以 Pi 的 JSONL 文件为唯一真相，不自建副本。

### 3. `ayuayue/PiDeck` — 多项目多会话的运维型工作台

- **许可**：MIT
- **技术栈**：Electron + React + Tailwind + xterm
- **Pi 集成方式**：RPC sidecar。核心设计原则是"一个 Agent 会话 = 一个独立的 `pi --mode rpc` 进程"，只通过 stdio JSON-RPC 与 Pi 通信，项目级 cwd 隔离；另有一个非 Pi 后端以 utilityProcess 内嵌引导，不占端口、不起后台 HTTP。
- **值得记录的功能**：多项目工作区与项目间隔离；两套 Agent 后端并存切换；`@` 文件引用、`/` 命令、`!` shell 在同一输入框；会话导入（外部编码代理的历史会话）与导出为自包含 HTML；把 Pi 的 JSON 配置做成 Provider 卡片 + 模型网格的可视化编辑与连接测试；供应商余额查询与本地用量统计；文件树、Git 面板、绑定 Agent 的终端、内置浏览器；系统托盘、桌面宠物、局域网 Web 访问、消息渠道机器人；计划模式（先生成计划逐条确认）；并行问询会话；桌面端接管 Pi 的信任确认，且不信任的项目仍可打开、有 Agent 运行时禁止删除项目。
- **可借鉴点**：把"会话隔离"落实到进程粒度并从设计上守住；把 Pi 的 JSON 配置当成需要 schema 驱动可视化编辑的对象；桌面端接管信任确认时的取舍（放行打开、卡住删除）。

### 9. `DLYZZT/pi-desktop` — 三进程边界与受管进程

- **许可**：Apache-2.0
- **技术栈**：Electron 三进程模型 + React + Vite
- **Pi 集成方式**：主进程负责窗口、菜单、托盘、通知、更新、自定义协议与 Host 监督；Agent Host 在独立 utilityProcess 中运行 Pi Coding Agent，负责会话、文件、配置与扩展；渲染进程只经受控 preload bridge 与 Host 交互。远程网页与本地项目页只进入主进程创建的沙箱化 WebContentsView，拿不到应用 preload、Node 或主渲染桥。Host 与渲染进程之间是带类型契约的 MessagePort IPC。应用不使用 TCP 端口承载 UI 或控制面。
- **值得记录的功能**：完整 Agent 工作台与会话工具执行历史；用户与 Agent 共享的内置浏览器；可观察、可控制的受管开发进程（dev server、watcher、mock API 之类，带崩溃回收）；用对话控制这些进程；MCP 服务与工具管理；模型与扩展统一管理；虚拟模型与自动路由；图片生成与决策模型；跨平台开发工具管理；消息渠道接入，且全部是出站长轮询或出站 WebSocket，不开 webhook、不监听端口。
- **可借鉴点**：utilityProcess + MessagePort + TypeScript 契约的三层边界，以及"控制面不需要本地端口"这一条；受管后台进程的前置条件写法（平台与架构支持、项目信任、会话 cwd 包含关系、崩溃回收健康、资源上限）并明确它是生命周期控制而非容器或沙箱；更新客户端只认包内固定的公开发布配置，不接受渲染进程提供的更新地址或凭证。

### 10. `heyhuynhgiabuu/openpi` — 边界写进项目规则

- **许可**：MIT
- **技术栈**：Electron + SolidJS + Tailwind + SQLite + CodeMirror + xterm；以 Homebrew cask 作为主要分发渠道
- **Pi 集成方式**：主进程监督一个 sidecar 来托管官方 coding agent 包——宿主的是 SDK，不是分叉出来的运行时。项目把三条边界写成硬规则：渲染进程只渲染，不碰文件系统、shell、Git、SQLite、密钥与 Pi 内部；Electron 主进程掌握桌面权限，IPC 载荷用 schema 校验，负责 sidecar 监督、PTY、Git、SQLite、文件搜索、应用元数据与原生对话框；Pi SDK 拥有 agent 语义，会话树、压缩、队列、工具、扩展、供应商与模型行为都由 Pi 负责。

- **可借鉴点**：把进程边界写成项目硬规则并要求跨边界改动额外谨慎；IPC 载荷 schema 校验；PTY、Git、SQLite 这类特权资源的生命周期一律归主进程；用一个守门扩展兜住跨进程的标识状态——比在 UI 层做防御更可靠。分发侧同样暴露了门槛：未签名、未公证的构建需要用户手动处理隔离标记，这类说明必须提前写进发布说明。

## 横向对比

### 1. Pi 集成方式：三条路线

| 路线 | 代表项目 | 共同特征 | 代价 |
| --- | --- | --- | --- |
| 库内嵌 | 第 1、2、5、6 项 | 直接引官方 SDK，与 CLI 共享本机配置目录，扩展、技能、登录天然互通 | 升级 SDK 即升级运行时，需自己保证与扩展的兼容 |
| RPC sidecar | 第 3、8、9、10 项 | 独立进程跑 Pi，协议通信，进程级隔离，可以驱动外部 Pi 二进制 | 需自建协议层、崩溃恢复、连接与权限握手 |
| 打包 Web 服务 | 第 4、7 项 | 以 Web UI 为基础加桌面壳，服务与运行时随包分发，用户无需自备环境 | 体积与启动成本更高，桌面能力要靠外壳补齐 |

`pi-desk` 已选 RPC sidecar 路线，第 3、9、10 项的做法最直接可对照。

### 2. 进程与 IPC 边界

共识非常一致：渲染进程不给 Node 权限，IPC 要么有类型、要么有 schema 校验，文件、shell、Git、PTY、密钥、更新这类特权操作全部归主进程。差异只在 agent 运行时放哪：放主进程内、放独立 utilityProcess、每会话一个 worker、放外部 RPC 进程或 sidecar，四种都有先例。

另一个共识是**不用本地 TCP 端口承载 UI 或控制面**：第 9 项明确不使用端口，第 3 项的局域网 Web 服务是用户显式开启的独立功能而非内部通道。

### 3. 会话与配置共享

几乎所有项目都把 Pi 的本机配置目录当作唯一真相：会话、认证、模型与设置都留在那里，桌面端不自建会话副本，因此"终端起会话、GUI 接着用"是普遍成立的。少数项目会把桌面端自身状态以自定义节点写回会话文件以换取恢复能力，互通性换来了与会话格式的耦合。

多引擎并存时的通行做法是各写各的会话目录、应用聚合读取并按来源打标。

### 4. 权限与信任

Pi 原生的项目信任确认是起点；桌面端在此之上普遍叠加"模式 + 规则"两级：

- 模式：三档（只读/计划、需要确认、完全信任）到四档不等，差异在于是否把"编辑前询问"与"命令前询问"拆开。
- 规则：以动作 + 工具名 + glob 表达，deny 优先且在所有模式生效，allow 只在受信任的作用域生效，工作区级规则只能收紧本机规则、不能放宽。
- 审批入口统一 UI 化（审批 dock 或弹窗），并支持一次性放行。

值得抄的是作者们的克制：明说规则匹配的是原始字符串、不做路径规范化与命令解析，因此它是护栏而非沙箱。这种表述比声称"安全隔离"更可信，也更容易在后续迭代中收口。

### 5. 扩展机制

- **复用 Pi 扩展 + 声明式适配器**（第 6 项最完整）：扩展源码不动，桌面端把扩展的对话框、工具卡、面板与命令映射成原生控件；适配器可被项目级覆盖。
- **自有插件体系**（第 1 项最完整）：面板、小组件、工作台视图、Agent 工具、服务、主题、MCP 与插件间消息总线，独立打包与市场分发。
- **桌面扩展页签**（第 2 项）：扩展可以注册自己的工作台页签。

三者的共同前提是扩展的启用状态与 Pi 自身的设置保持一致，否则会出现"CLI 里有、GUI 里没有"的割裂。

### 6. 分发与更新

桌面壳统一，打包链也趋同。真正的分歧在更新粒度：一派坚持整包签名替换（禁止单独替换安装包内的 JS 包，避免版本错配），另一派把桌面端自更新与 Pi CLI 的更新检查分开管理。

共同门槛是签名与公证：未签名的构建在首次启动时会被系统拦截、需要用户手动放行；macOS 上未签名构建无法自装更新，只能引导用户去下载页；Windows 上同样有 SmartScreen 提示。这一点对所有项目都是现实约束，不是可以延后的细节。

## 对 `pi-desk` 的借鉴与差异

### 可直接借鉴

- **会话与配置不另存副本**：继续以 Pi 的本机配置目录为唯一真相，桌面端只做投影与状态缓存，保住与 CLI 的接力能力。这点与现有 sidecar 方向一致，只需在文档与代码注释里固化成约束。
- **契约单点定义 + 载荷校验**：我们已有按领域拆分的桥接契约与渲染端服务层，可以再进一步把"契约只在 shared 层定义、主进程入口校验载荷"写成硬规则，并借鉴第 10 项用一个兜底扩展守住跨进程标识状态的做法。
- **错误与重试集中处理**：借鉴第 5 项的对话内错误卡片 + 一键重试 + 自动重试状态行，把桥接失败、进程退出、渲染崩溃三类问题收敛到同一套 UI 语义。
- **扩展 UI 桥的覆盖面清单**：第 7 项的确认/选择/输入/编辑器/通知清单和第 6 项的声明式适配器思路，可以直接作为我们扩展 UI 能力的对照表。
- **信任与权限语义**：沿用"工作区规则只能收紧""deny 优先且各模式生效"的语义，并照抄那种诚实的定位表述——规则是防手滑的护栏，不是沙箱。
- **更新与分发**：采用整包签名替换、更新地址与凭证不接受渲染进程输入；把未签名阶段的系统拦截说明提前写进发布说明，而不是等用户报障。

### 需警惕

- **把桌面端状态写回 Pi 的会话文件**：换来恢复能力，但把桌面端版本绑死在会话格式上，格式变动即数据受损。
- **让渲染进程直接引 SDK 或放开 Node 权限**：所有被调研项目都在刻意回避这条捷径，代价是长期的安全面与可测试性。
- **用本地端口做内部控制面**：先例里没有这么做的；用户显式开启的局域网服务属于单独授权、单独令牌的功能，不能顺手复用成内部通道。
- **贸然引入受管后台进程**：若日后要做 dev server 或 watcher 类能力，必须先有项目信任、工作目录包含关系、崩溃回收与资源上限这几项前置条件，并且明确它不是沙箱。

### 生态同质化功能分布

做差异化前需要知道哪些已是标配：

- **几乎人人都有**：会话浏览与恢复、流式对话与工具卡片、模型与供应商配置切换、文件树与 diff。
- **多数都有**：权限模式与审批、扩展与技能管理、终端、主题、会话 fork 与分支树。
- **部分项目有**：计划任务、用量与成本统计、MCP 管理、子 agent 编排、移动端或局域网伴侣、内置浏览器、多引擎兼容。
- **少数项目有**：自有插件体系与插件市场、多 Agent 议会式规划、语音输入、跨项目的后台任务汇总视图。

结论：基础能力上的差异化空间很小，可区分的方向集中在扩展生态的开放程度、权限语义的精细度、以及"会话之外"的工作台能力。
