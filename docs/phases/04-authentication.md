# 第四阶段：Authentication

[开发总览](../development.md) · [上一阶段：Pi 深度能力](03-pi-capabilities.md) · [下一阶段：Desktop 产品能力](05-desktop-features.md)

## 目标与边界

提供 Provider、认证状态、API Key 和官方 OAuth 的 Desktop 入口，继续复用 Pi 的认证实现与数据管理。

认证不阻塞第一阶段。此处不假定当前 RPC 已有 login / logout；实施时已重新核实固定版本的真实能力，结论与依据见[开发总览第 6.2 节认证与凭据](../development.md#62-主进程管理与-ipc-策略)。

## 依赖

- 已有稳定 Runtime、模型选择与错误呈现。
- 已按固定版本核实官方认证能力（见[开发总览第 6.2 节认证与凭据](../development.md#62-主进程管理与-ipc-策略)），沿用官方凭据归属，避免 Desktop 创建平行认证库。
- 凭据不进入 Vue bundle、可公开环境变量、命令行参数或常规日志；UI 输入通过明确的受限操作传递。

## 任务拆分

### P4-01 认证能力确认

**目标**：依据实际版本确定认证接入边界。

**范围**：核实官方 Provider / Auth API、RPC 能力、凭据存储、API Key 与 OAuth 的生命周期。优先正式能力；RPC 不足时确定复用官方认证入口的执行端（主进程或受管辅助进程）。仅复用认证能力，Agent 主 Runtime 仍为独立 Pi RPC sidecar。

**依赖**：当前项目实际 Pi 版本。已完成，结论与依据见[开发总览第 6.2 节认证与凭据](../development.md#62-主进程管理与-ipc-策略)。

### P4-02 Provider 与认证状态

**目标**：展示可用 Provider 与可行动的认证状态。

**范围**：官方 Provider 信息、已配置 / 未配置 / 本地状态异常等状态、错误提示和模型可用性变化；只暴露必要状态，不把凭据解析结果直接返回到页面。

**依赖**：P4-01 确定的数据来源；复用第二阶段模型入口。

### P4-03 API Key

**目标**：通过 GUI 配置或移除 API Key，并保持 Pi 与 Desktop 行为一致。

**范围**：密钥输入、官方存储与移除、状态同步、已有配置冲突提示。输入新密钥必然短暂存在于渲染进程内存，通过固定 preload 方法交给主进程，再按 P4-01 确定的认证执行端受限传递；校验调用窗口与操作参数，不把密钥送入普通 prompt、聊天历史、Desktop 偏好或常规日志。提交或取消后释放输入状态，不持久化明文副本。

主进程只返回必要认证状态与脱敏错误，不回传已有密钥或认证文件。展示成功以真实存储结果为依据，不建立第二套密钥文件；配置变化后协调活动 Runtime 与模型状态刷新，不能把 UI 状态变化当作 Pi 已使用新凭据。

**依赖**：P4-01、P4-02。

### P4-04 OAuth 与 Login / Logout

**目标**：复用 Pi 官方 OAuth 流程提供登录、取消和退出。

**范围**：通过固定 preload 方法请求主进程启动官方登录流程，衔接系统浏览器与官方回调机制，呈现脱敏进度、取消与失败、Logout 和 Runtime 状态刷新。主进程校验登录来源与外部 URL，不在具有 Desktop 桥接权限的窗口中加载任意认证网页，也不向渲染端返回 token 或完整回调秘密；不能重新实现 OpenAI、Anthropic 或 GitHub OAuth。

认证执行端是 P4-01 确定的受管辅助进程：按固定入口、受限通信、生命周期、取消与秘密输出边界实现，不编译独立 Helper，也不把 SDK 嵌入作为 Agent 主方案。认证完成或退出后，协调官方存储、活动 Agent 操作、模型与 Runtime 状态，不能静默假定驻留进程已经刷新凭据。

认证子流程使用的官方回调机制不等于把 Agent RPC 暴露到网络；回调的来源关联、处理范围与生命周期单独说明，不扩展为通用 localhost Agent 服务。

**依赖**：P4-01、P4-02；复用官方认证入口，不要求 OAuth 与 API Key 共用不合适的抽象。

## 推进顺序

```text
P4-01 → P4-02 → P4-03 → P4-04
```

先确认能力，再实现入口。API Key 与 OAuth 只在实际公开行为相同的部分复用。

## 不做项

- 自研 OAuth、账户系统、云端凭据同步或平行认证库。
- 改用 SDK 嵌入作为 Agent 主方案。
- 提前加入所有 Provider 的专属配置页面。
- 通过日志、版本探测或通用 RPC 返回暴露密钥。

## 已确定事项

事实、通道、错误码与形态定义见[开发总览第 6.2 节认证与凭据](../development.md#62-主进程管理与-ipc-策略)。

- RPC 与 CLI 都没有写入凭据的能力：RPC 命令面没有认证命令，`/login` 与 `/logout` 是交互模式内建命令；CLI 的 `pi auth` 只读。RPC 不足，因此认证执行端是**复用官方认证实现的受管辅助进程**（主进程用 `ELECTRON_RUN_AS_NODE` 启动的 ESM 入口），认证能力来自与 sidecar 同版锁定的官方 SDK。
- 不把 SDK 当作 Agent 主方案，不自研 OAuth，不建立平行凭据文件；凭据仍写在 Pi 自己的 `auth.json`。
- API Key 与 OAuth 复用同一套官方登录流程（提示与通知映射为 Desktop 界面），只在公开行为相同的部分复用，不强行共享不合适的抽象。
- 登录/退出后只重读认证状态；可用模型需要重启式重载 Runtime 才会更新，不把 UI 状态当作 Pi 已使用新凭据。
- 浏览器回调、取消与窗口关闭：授权地址只由主进程校验后交给系统浏览器，回调服务由官方实现自己启动；端口冲突与回调无法回到本机都如实展示失败。
- MCP 服务器 OAuth 登录与退出经既有 RPC 的 `/mcp login|logout <server>` 接入，命令文本由主进程拼出；enable/disable/exposure 变更与需要写配置的命令仍不做。
