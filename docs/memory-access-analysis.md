# 主动读取计数的用途与记忆召回优化分析

## 1. 定位与当前结论

本文记录主动读取统计的事实边界、可支持的判断、外部证据及候选优化方向，供积累真实计数后再次分析。与 [记忆系统调研与方案设计](memory-research-design.md) 配合阅读，不替代其整体架构说明。

**当前选择是先积累真实计数，再讨论是否以及怎样改变召回。计数暂不参与排名，不据此删除、降权或改写权威记忆。** 按任务自动召回仍是候选方向，不是已经确定的下一项开发。

本文不构成部署、重载、数据采集、历史补计、依赖安装、测试或代码修改授权，也不安排这些操作。

依据分为三类：

- **项目事实**：来自产品资源维护源、用户库目录与接续记忆。
- **外部证据**：来自论文、官方说明或成熟实现，只证明其原有条件下的机制与结论。
- **设计推断**：根据前两类依据形成的候选方向，尚无本项目效果数据支持。

## 2. 项目事实与现有数据

### 2.1 已实现的采集边界

维护源已实现每条日记的主动定向读取次数、去重会话数、最近读取时间，以及统计查询、持久去重、故障降级和删除联动。统计默认自动运行，不要求用户配置。

实际采集链路为：扩展 `memory_read` 准备完整原文结果，检查身份、输出与操作状态，然后调用引擎内部 `access-record` 协议。引擎按记录、宿主会话与工具调用身份持久去重。

- 同一会话中的新调用增加读取次数，不增加会话数。
- 同一调用重复提交不增加次数，也不刷新最近读取时间。
- 刷新、压缩与同会话分支切换不重置持久去重。
- 底层 CLI `read`、搜索结果、规则列表、画像、自动背景、历史回放及统计查询不计数。
- 搜索与规则工具也能返回正文。因此，该统计不是全部访问量，更不是实际使用次数。
- 计数记录的是主动读取结果已经准备，不保证模型最终接收、理解、采纳或正确应用。

统计独立存于用户库 `.system/access.json`，不修改权威正文、检索索引或保存审批指纹，不参与当前排序。只保存计数、采集起点、最近时间与必要的哈希去重身份，不保存查询、正文或完整对话；哈希身份仍可关联，并不等于匿名化。

统计失败保留成功原文并报告状态未确认，不自动重试或补计。明确删除记录时联动清理对应统计；规则替代不把旧记录的计数转移给新记录。

### 2.2 本轮实际观察到的数据条件

静态与运行调查发现：

- 产品资源维护源已包含自动统计调用并已注册 `memory_access_stats` 工具；用户 agentDir 下的同源旧副本在扩展执行前被排除，不作为另一套生效来源。
- 默认用户库 `~/.agents/memory-store/.system/` 下截至本轮尚无 `access.json`，`memory_status` 报告 `status: not_collected`。
- 未产生统计记录的核心原因包括两层：
  1. **跨平台换行符导致索引指纹校验失败（运行阻断）**：Mac 端提交的派生索引（`index/search.json`）记录的是 LF 换行符哈希，而在 Windows 下 Git 若开启 `core.autocrlf=true` 会将文本检出为 CRLF，导致 `check_search_sources` 抛出 `INDEX_STALE` 错误，阻断了 `memory_read`、`memory_search` 及统计写入链路。现已通过用户库 `.gitattributes`（`* text eol=lf`）及 `reindex` 彻底解除该阻断。
  2. **检索与规则工具直接返回全文导致调用替代（漏斗归零）**：现有采集口径仅覆盖 `memory_read`（定向读原文）。但在真实会话中，`memory_search` 与 `memory_rules` 曾直接返回记录全文（`content`），模型完成检索后已取得足够事实，在实际会话中极少触发二次定向读取 `memory_read`。现已通过 P0 改动将检索与规则工具调整为默认返回前 200 字摘要并附带 `content_truncated` 标识，漏斗绕过问题已在代码层解除。

因此，本轮仍没有可用于分析的实际访问分布。这表示在所检查的存储位置尚无统计文件，不表示所有记录历史上均为零次，也不能推断其他环境的数据情况。后续分析须重新读取当时的部署与数据事实，不能沿用此处观察来判断届时是否已经生效。

不为补齐分布扫描历史会话或补造事件，也不把维护源能力、工具描述或已有类型检查结果当作运行采集已经生效的证据。

### 2.3 现有召回能力

当前检索核心使用中文双字词元、英文词元与 BM25 词法相关性。排序不使用访问计数，也没有遗忘衰减、随机加权或 FSRS。

扩展请求级背景已接入按当前任务自动召回有效规则与日记，并提供适用画像与项目索引；自动背景不计入主动读取统计。模型主动选择检索工具与程序按任务自动召回是不同入口。

## 3. 三项计数分别能说明什么

| 信号 | 可支持的判断 | 不能推出的结论 |
| --- | --- | --- |
| 主动读取次数 | 采集范围内的定向读取强度；结合会话数观察重复读取集中度 | 实际使用次数、正确性、重要性、解决问题次数 |
| 去重会话数 | 跨宿主会话被主动读取的广度；比总次数少受单会话重复调用影响 | 独立任务数、独立需求数、独立成功使用次数 |
| 最近读取时间 | 最近关注过哪些记录；帮助定位短期状态的复核线索 | 事实更新时间、最后核实时间、当前有效期、内容仍在上下文 |

次数高而会话少，只能说明读取集中在少量会话，可能涉及重复排障、反复确认、压缩后重读或其他原因，不能直接选定某种解释。跨会话读取也可能来自同一未解决问题或人为新开会话。

读取次数除以会话数可以描述每个已观察读取会话的平均调用次数，但不是有用率、命中率或独立使用概率。没有观察到会话时，该比值不应计算。

累计次数还受采集时长、记录存续时间和任务机会影响。新旧记录的原始计数不能直接比较价值；当前只有采集起点和最近读取时间等信息，不能恢复完整的访问时间分布或近期读取趋势。

必须区分：

- **尚未采集**：没有统计文件或记录尚未被该入口观察到。
- **统计不可用或未确认**：统计读取、提交或通信存在缺口，不能当作零次。
- **已确认的采集结果**：只描述既定口径下成功记录的事件，不扩展为全部访问。

## 4. 三类用途及其边界

### 4.1 现在就有用的用途：可观察性与复核线索

“有用”指信号具备这些用途，不代表本轮已经取得对应分布或证明收益。

**定位主动读取热点。** 有数据后，可以识别反复被定向读取的记录与主题，优先调查它们是否难找、表达不清或需要反复确认。计数用于安排调查注意力，不自动决定新增摘要、修改正文或提升排名。

**识别重复读取集中度。** 结合次数与会话数，区分主要集中于少量会话的读取和跨会话反复读取，避免被一次长时间排障制造的高频误导。仅凭这两个数不能确认重复原因。

**发现覆盖调查线索。** 与现有记录的主题清单对照，可以标记哪些主题未观察到主动定向读取。但这不是任务需求覆盖率，更不能据此判断知识缺失：相关内容可能已由搜索或规则工具返回，也可能根本没有出现对应任务。

**安排短期状态复核。** 对进展、未决问题、部署状态这类有时效性的内容，最近读取可以提示哪些状态值得优先核实。读取本身不延长有效期，长期未读也不构成失效依据。

### 4.2 需要额外信号的用途：重排、去重与多样性

**候选重排。** 计数缺少当前任务相关性与候选曝光背景。将来若有充分依据考虑使用，应限定在已经相关、适用性相当的候选内部，将跨会话读取作为有上限的弱线索，而不是让热门记录越过相关性。当前没有依据启用这种加权。

**去重。** 需要记录身份、来源版本与内容重叠关系。计数不能判断两条记忆是否重复；同主题记录也可能分别提供决定、原因、反证和历史变化。不能因为词面相似就合并不同适用条件或不同版本。

**多样性。** 需要识别候选是否提供不同的相关信息，而不是用冷门程度代替信息增量。应避免强行按项目或主题平均分配名额，挤掉真正相关的内容。

**重复注入抑制。** 需要知道本次模型请求是否已经完整包含该记录的有效内容。最近读过、同会话读过都不够：压缩、分支变化、内容截断与来源更新均会改变条件。

### 4.3 不应采用的用途

- 将高频直接当作正确、重要或有用；将低频、陈旧直接当作应降权或删除。
- 用读取次数除以记忆总量、返回条数或会话数，宣称得到真实命中率或有用率。
- 把未点击、未继续调用 `memory_read` 当作负反馈；搜索结果可能已经足够。
- 把自动注入继续计入主动读取，再根据增长的计数提高排名。
- 按固定遗忘比例统一衰减所有内容，特别是仍然有效的规则。
- 在明确查历史时，默认偏爱新记录或隐藏被替代版本。
- 为增加探索而直接引入随机排序，或用访问次数代替 FSRS 所需的记住／遗忘反馈。

## 5. 需要警惕的偏差

**入口偏差。** 只统计 `memory_read`，无法与通过搜索、规则或自动背景取得正文的访问直接比较。

**曝光与选择偏差。** 排在前面的内容更容易进入上下文或被继续读取。被选中更多不等于更有用；缺少曝光背景时，不能分清没有被看见与被看见后没有选择。

**自我强化。** 如果读取会增加计数、计数又提高排名，就会形成“被选中—被计数—再次被选中”的循环。自动注入加入相同计数会进一步混淆主动关注与程序选择。

**任务与会话不一致。** 一个会话可以有多个任务，一个任务也可以跨多个会话。现有宿主会话身份不应被重新解释为自然语言任务身份。

**时效与正确性不一致。** 最近被读不等于最近核实；反复读取的内容也可能一直没有解决问题。稳定规则的有效性取决于适用条件与替代关系，而不是年龄或热度。

## 6. 如需补充信号，最小边界是什么

以下均为候选设计，不是新增采集已经获准。

| 补充信息 | 解决的具体问题 | 最小边界 |
| --- | --- | --- |
| 候选返回与选入上下文的状态 | 区分未进入候选、进入但未选、已经提供内容 | 初期只在会话内保留必要的记录身份、候选位置、来源版本和选择原因，不持久保存完整查询 |
| 本请求的内容在场状态 | 避免重复装配仍然完整存在的相同内容 | 依据当前请求与来源版本判断，不用累计计数代替；压缩或分支变化后重新判断 |
| 记录身份、版本及内容重叠关系 | 确定性去重与后续多样性选择 | 优先利用现有身份和来源信息；不默认增加向量服务或模型调用 |
| 明确的用户纠正、确认或可归属结果 | 区分被读取与确实有效 | 仅采用有明确来源的反馈；缺少反馈不是负例，不让模型随意评定价值 |
| 短期状态的时限或来源变化 | 识别需要复核的内容 | 依据内容有效性，不把最后读取时间当作核实时间 |

候选曝光信息只能帮助解释选择过程，仍不足以计算真实有用率。即使正文进入请求，也不证明模型理解或采用。

会话内信息只能服务于当次选择与说明，不能自动支撑长期统计。若确需长期分析，再单独讨论持久化的必要性、保留范围与删除联动，不默认保存完整查询、对话或查询哈希；哈希同样可能产生关联与敏感信息推断。

## 7. 外部证据及可借鉴结论

| 来源 | 原机制与证据范围 | 对本项目的结论 |
| --- | --- | --- |
| Generative Agents | 组合相关性、最近访问与模型评定的重要性，服务于模拟角色的行为连贯性 | 借鉴信号职责分离；不照搬统一时间衰减、重要性打分或权重，不推断工程规则因此更准确 |
| Joachims 等，Unbiased Learning-to-Rank with Biased Feedback | 研究展示位置等因素对人类点击反馈的偏差，并提出相应学习方法 | 借鉴对曝光偏差的警惕；模型读取与人类点击并非同一行为，不直接照搬反事实学习 |
| MMR | 在已检索结果中兼顾查询相关性与非冗余 | 借鉴相关性前提下去冗余；不必直接引入完整算法，也不能删除互补条件、反证或版本差异 |
| FSRS 官方实现 | 依据复习历史、时间以及记住／遗忘的评分安排间隔复习 | 当前访问计数没有对应反馈，不能替代输入；不纳入当前推荐 |
| Sentence Transformers 官方 Retrieve & Re-Rank 说明 | 先召回候选，再对候选评分重排 | 区分候选覆盖与候选排序；仅改善重排无法补回未进入候选集的内容 |

这些来源支持机制判断，不证明本项目已经提高召回效果。参考实现的依赖、默认参数与外部收益数字不作为本项目实施结论。

## 8. 候选的最小下一阶段方向

### 8.1 当前优先级

先利用真实计数观察主动读取行为，不立即开展热度重排。后续结论必须能够指出计数究竟支持了哪种判断，以及仍然缺少什么信息；没有发现明确问题时，不为使用计数而强行修改召回。

数据积累不要求补计历史，也不意味着本轮已经安排部署、重载或采集。产品资源是否已在运行实例中生效，应以届时实际资料为准。

### 8.2 已落实的自动召回闭环

**现已接通“相关性优先的按任务自动召回小闭环”。** 其目标是让相关记忆在模型处理任务前进入上下文，同时避免重复占用预算；访问计数继续作为独立诊断信息，不进入排序权重。

已落实特征：

- 从真实用户任务形成临时查询，复用现有 BM25 检索核心与只读 `recall-background` 协议，不拿自动背景或旧召回内容检索自身。
- 保留来源、适用范围和历史状态，区分有效规则与历史参考，被替代版本不自动注入，无相关候选时保持静默。
- 基于当前请求已包含的工具结果做确定性重复抑制；内存缓存复用时仍严格核对来源集合与文件内容指纹。
- 显式要求读取原文或查看历史，不受自动装配的预算抑制限制。
- 自动召回不计作主动定向读取。

**依据：** 项目已有统一检索核心与请求钩子，但没有按任务自动检索入口。入口问题与热度问题不同，单纯改排名不能替代入口。

**适用条件：** 词法候选能够覆盖当前问题，且需要减少对模型主动选择工具的依赖。对于措辞差异导致的候选缺失，需要另行研究召回覆盖，不能靠计数补救。

**代价：** 增加请求级检索与上下文开销，需要处理任务变化、来源更新、压缩及分支变化后的内容在场判断。现阶段不承诺命中率、成本或任务效果改善。

**不做项：** 热度加权、统一时间衰减、随机探索、FSRS、自动删除、自动提炼、完整查询／对话持久化，以及向量服务引入。合理默认由产品内部承担，不要求用户配置权重或反复调参。

该方向仍需后续讨论确认，不因本文落盘获得实施授权。

## 9. 有真实计数后再次分析的问题

以下是分析问题，不是测试计划或执行要求。

### 数据是否足以解释

- 当时实际启用的采集入口与口径是什么，是否仍只覆盖 `memory_read`？
- 统计是否已经开始采集，覆盖起点在哪里，是否存在不可用或未确认事件？
- 跨平台检出是否已保持 LF 换行符与派生索引指纹一致，是否存在 `INDEX_STALE` 导致的静默读取中断？
- 搜索和规则工具直接返回正文是否形成了完整的调用替代，导致 `memory_read` 漏斗被绕过？
- 记录的新旧、存续时间和任务机会是否明显不同，是否适合直接比较累计次数？
- 是否只有汇总计数，还是另有获准采集的曝光与反馈信息？没有的信息不推算、不补造。

### 读取行为呈现了什么

- 高次数主要集中在少量会话，还是跨会话持续出现？
- 结合可见任务材料，重复读取是否能归因；无法归因时应保留哪些解释？
- 哪些主题只是未观察到定向读取，哪些存在有直接证据的检索或覆盖缺口？
- 最近被读取的短期状态是否需要重新核实，其依据是否独立于访问时间？

### 应当改变哪一层

- 问题是检索没有触发、相关内容未进入候选、候选顺序不合适，还是上下文装配重复？
- 若搜索或规则已经返回正文，较少调用 `memory_read` 是否实际上符合需要？
- 若考虑计数辅助排序，现有证据能否排除重复排障、曝光偏差与采集时长的主要影响？
- 是否确有必要补充信号，能否只保留会话内信息，而不新增持久日志？

后续分析应分别给出已观察事实、仍不能判断的内容及推荐动作。没有充分依据时，维持计数旁路和现有排序；稳定有效规则不能仅因低频或陈旧被降权，明确历史查询不能默认偏爱新记录。
