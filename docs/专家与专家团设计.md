# 专家与专家团设计

本文是 pi-desk「专家与专家团」能力的初步设计：专家身份层的需求、配置存放、加载与校验、会话内生效，以及团队协作层的团队形态、团长与成员边界、双账本与信息调度、派活验收与收敛。本文不描述实现细节，不含字段级定义、文件清单与验证方案；模块现状与文件归属以 [专家与专家团模块](modules/experts.md) 为准，两者不一致时以模块文档为准。

两层是同一条能力线的两个阶段：专家解决「以谁的身份、用什么方法、按什么规范交付」，专家团解决「多位专家如何围绕同一目标分工」。团队模式复用专家的全部机制（身份、能力范围、写入范围、会话绑定），只在装配期追加收窄与一组团队工具。

## 1. 背景与问题

pi-desk 原有两种可复用指令载体：随包与用户级的**技能**，以及四类**子代理**。技能回答「怎么做某件事」，子代理负责「把一段工作挪到隔离进程里做」，但缺少中间一层：**以固定身份、固定方法论、固定输出规范完成单点任务**。缺这一层的结果是，每个会话都从通用助手的状态重新开始，专业方法只能靠用户每次粘贴提示词，或靠 `AGENTS.md` 承担本不属于它的角色描述。

专家层补上了这一层，但一次会话只能有一个专家，真实任务却常常需要多种角色分工——调研、实现、审查各由擅长它的人来做。现有委派（`delegate_subagent`）也只能承担「把一段工作挪到隔离进程里做」：一次工具调用对应一个子进程，任务说明不注入父会话历史，子进程不落盘会话、没有跨调用归属，因此不能续派、不能形成协作，只能单层外包。

团队层要补的是更上面这一层：多位专家围绕同一目标分工推进，由一个负责人拆解与调度，结果汇总到用户面前。多智能体实践与企业管理在这里有一致结论：**负责人不生产，只做拆解、分配、验收与整合**，执行交给成员，所有通信经负责人汇聚。本文的团队部分按这一形态设计。

## 2. 名词约定

全文只用以下名称，不混用近义词。

### 2.1 专家

| 术语 | 含义 | 代码/配置对应 |
| --- | --- | --- |
| 专家 | 一份人工编写的角色定义：身份、方法论、输出规范，外加对能力的引用 | 定义由 `src/shared-process/expert-definitions.ts` 解析，角色段由 `src/sdk-host/expert-role.ts` 装配 |
| 专家定义 | 专家在磁盘上的一份 Markdown 文件（声明段 + 正文） | `expert.md`，声明段取名称、简介、技能范围、MCP 范围、工具范围与写入范围 |
| 专家目录 | 存放专家定义的目录，一个专家一个子目录，目录名即 id | 内置 `resources/agent/experts/`，自定义 `<agentDir>/experts/` |
| 内置专家 | 随产品构建分发、随包目录只读的专家；可写同标识覆盖定义修改 | `resources/agent/experts/<id>/expert.md`，经 `bundle.json` 的 `experts` 段声明 |
| 自定义专家 | 用户在产品 agent 目录下创建或编辑的专家 | `<agentDir>/experts/<id>/expert.md`，可增删改 |
| 覆盖内置 | 自定义目录里与内置同标识的定义：生效的是自定义这一份，随包文件不动；删除即恢复默认 | `<agentDir>/experts/<id>/expert.md` 与内置同 id，清单里 `overridesBuiltin` 为真 |
| 新建 | 从空白开始创建一份自定义专家，与派生同为自定义专家的两条起点 | `<agentDir>/experts/<id>/expert.md`，不写 `derivedFrom` |
| 派生 | 从内置专家复制出一份自定义专家，之后两份独立演进 | `<agentDir>/experts/<id>-copy/expert.md`，定义里写入 `derivedFrom` |
| 召唤 | 在会话中选用某个专家，使其角色定义进入本次会话的系统提示 | 新建会话时选择，绑定随会话持久保存，首轮后锁定 |
| 角色段 | 注入系统提示的专家正文分段 | `expert-role` 分段，与门禁段同一分段机制 |
| 能力范围 | 召唤该专家的会话里可用的技能、MCP 服务器与工具集合 | 由专家定义与默认能力基线合成，装配期生效（`src/sdk-host/expert-capability.ts`）；只有随包工具清单登记过的工具可被收窄，内建控制工具（如提问）与 MCP 管理工具不在范围内，受保护工具另含记忆组与语气风格组 |
| 写入范围 | 召唤该专家的会话里 `write`/`edit` 允许写入的目录或文件 | 专家的 `writeScope` 声明，装配期由宿主守卫执行（`src/sdk-host/expert-write-guard.ts`）；不写声明不限制、空只读 |
| 默认能力基线 | 所有继承型专家共享的默认范围，设置页一处可改 | `<agentDir>/capability-defaults.json`，三个维度都用 `null` 表示不限制 |
| 技能可见集 | 某次会话里模型可用的技能清单 | 技能装配结果（`additionalSkillPaths` 与用户技能合并后按许可集过滤） |
| 子代理 | 由 `delegate_subagent` 派出的独立子进程 | `src/sdk-host/sub-agent/` |

### 2.2 团队

| 术语 | 含义 |
| --- | --- |
| 团队 | 一份团队定义：团长与成员名单 |
| 团长 | 团队负责人，同时是根会话绑定的专家；负责拆解、派活、验收、整合 |
| 成员 | 团队中被派活的专家 |
| 成员会话 | 绑定某成员专家、归属根会话、不占标签的独立会话 |
| 开团 | 在新建会话时选定团队，将会话专家绑定为该团团长并开启团队模式 |
| 任务账本 | 目标、事实、计划与任务条目构成的共享记录，随根会话持久化 |
| 进度账本 | 团长每轮自省「是否满足、是否打转、是否有进展、下一个该谁、该给什么指令」的结论，不单独落盘 |
| 任务条目 | 一项可派给某成员的工作：标题、说明、验收项、依赖、状态、结果引用 |
| 验收项 | 任务完成时必须成立的、团长可核实的条件 |
| 打回 | 团长依据证据把已交付的任务退回同一成员重做 |

## 3. 需求

### 3.1 专家已确认需求

1. **人工配置**：专家由人编写或编辑，设置页只提供字段与正文的文本编辑，不代写、不提供 AI 自动生成、不从历史会话自动沉淀。
2. **双来源**：除内置专家外支持自定义专家，两者在同一界面上并列可选。
3. **可修改内置**：内置专家在设置页可直接编辑，改动写成自定义目录里同标识的覆盖定义；随包文件仍只读，界面上标出「覆盖内置」，删除覆盖即恢复默认。另保留从内置派生独立副本的路径（新标识、独立演进）。
4. **单点任务定位**：专家在单个会话内以固定身份执行任务，不扩展为多角色协作。
5. **可运行子代理**：召唤专家的会话可以调用 `delegate_subagent`，并把委派能力作为可收窄的工具项；子代理仍不认识专家，下级子进程不加载专家正文。
6. **可在设置页创建与编辑**：能从空白新建自定义专家，并在设置页内修改其身份、能力范围、写入范围与正文；编辑范围不外扩到调用方式。
7. **能力范围可配置**：专家能收窄本会话可用的技能、MCP 服务器与工具；先在默认能力基线上继承，再按专家做增减，不必每次从零勾选。范围只减不增，不引入会话原本没有的技能、服务器或工具；受保护工具（技能门禁、待办清单与记忆组）不在可排除之列。

### 3.2 团队已确认需求

1. **团长中心**：团队由团长管理，团长负责拆解、分配、验收与整合；成员不自主认领任务。
2. **团长不生产**：团长不改文件、不跑命令、不产出交付物；保留只读检查用于验收。
3. **成员为独立会话**：每个成员拥有自己的会话、上下文、用量与专家绑定，可被同一团长多次派活。
4. **共享账本**：任务与进度对团长可见并可持久保存，跨轮与上下文压缩后仍然成立。
5. **可验收**：派活必须带验收项，团长据可核实证据决定接受、改派或打回。
6. **可收敛**：根会话中断或关闭时，全部在途成员轮次一并终止。
7. **默认关闭**：团队只在根会话开启，且只在新建会话时选择。

### 3.3 不做项及原因

| 不做 | 原因 |
| --- | --- |
| AI 自动生成专家、从会话记录自动提炼专家 | 与「人工配置」的明确要求冲突 |
| 并入 `desktop-config.json` | 方法论正文会退化为 JSON 字符串，手改、diff、审阅全部劣化 |
| 单独的 `experts.json` 集中清单 | 一份文件装所有正文，无法按专家单独分享与移动 |
| 项目级专家目录 | 项目级已由 `AGENTS.md` 与项目技能承担，再加一层优先级收益低、冲突面大 |
| 按专家收窄主会话工具集以外的权限 | 工具白名单只决定「哪些工具可调用」，不改变文件与命令权限，也不构成审批流 |
| 专家内部嵌套子代理 | 子代理子进程没有委派工具，也不加载专家定义，只能单层委派 |
| 一次会话并存多个专家 | 多段角色指令互相稀释，主提示失焦 |
| 专家市场、版本、导入外部专家包 | 需要来源标记与信任边界，与本期「本地预设」定位不同 |
| 设置页内嵌 AI 生成或改写专家正文 | 与「人工配置」冲突，且要把模型调用嵌进设置页，成本与质量都不可控；需要帮写时用内置的「专家与专家团设计专家」在会话内产出草案，落盘仍由人在设置页完成 |
| 专家分享链接与专家市场 | 分享需要云端账号、托管与新的信任面；跨机复用靠搬运数据目录 |
| 专家头像与其他附加素材 | 列表用名称、简介与来源标签已够识别；引入图片要新增格式校验与体积上限 |
| 同一会话内多角色交叉发言 | 与「一次会话一个专家」冲突，需要房间状态、路由与上下文压缩三套机制；外部只有群聊形态这么做 |
| 成员自主认领任务 | 认领要求任务板事件能唤醒成员会话，多出一条被动驱动入口；且与「团长分配」的定位冲突 |
| 成员之间直接发消息、广播 | 需要消息总线、被动唤醒与权限收敛三套新机制，收益低于成本；通信只经任务板与团长 |
| 嵌套团队 | 团队里再开团会让归属、中断收敛与成本三层叠加；外部成熟方案同样不支持 |
| 团队跨重启恢复在途轮次 | 进程已不在，恢复等于重放执行；只恢复账本结构，在途轮次标为已中断 |
| 用户向成员会话输入 | 会出现「团长与用户同时驱动一个成员」的第二驱动方，责任与角色都会混乱 |
| 团队层计划审批 | 审批属于委派与执行确认的既有边界，团队层再来一层会形成两套确认 |
| 团队市场、团队分享、团队版本 | 需要云端托管与信任边界，与本地预设定位不同 |
| 用户直接在团队面板上停止成员轮 | 需要渲染层 → 主进程 → SDK 宿主的新中断通道；在通道建立前只保留团长通过 `team_stop` 停止，避免一条只走一半的打断路径 |

## 4. 项目事实与外部参考

### 4.1 项目事实

| 事实 | 出处 | 对设计的作用 |
| --- | --- | --- |
| 产品有自有的 agent 目录（便携态在 `data/` 下），共享目录只读且产品不写入 | `src/main/shared/pi-paths.ts` | 自定义专家与团队有唯一可写落点，且随便携数据目录同步 |
| 随包资源由清单声明（扩展、技能、`subAgentOnly` 标记、必需工具、专家与团队段），构建期打包只读 | `resources/agent/bundle.json` | 内置专家与内置团队沿用同一分发形态，不需要新机制 |
| 技能装配为「随包非 `subAgentOnly` 技能 + 共享目录技能」，与用户技能同名时保留随包、剔除用户 | `src/sdk-host/product-resources.ts` | 同名冲突的处理方式可与之对齐，避免两套冲突语义 |
| 配置中心是单个带版本号的 JSON，可选字段缺省回退、临时文件加改名原子写入 | `src/main/config/desktop-config-store.ts` | 该范式适合开关与列表，不适合承载长文本正文 |
| 子代理只认固定任务类型，边界由进程参数强制，不递归、不注入父会话历史 | [子代理](modules/sub-agent.md) | 专家与成员都不能复用子进程通道传角色或上下文 |
| 系统提示支持分段装配 | [门禁](modules/skill-guard.md)所述 `systemPromptOptions.sections` | 角色段、团队段与账本摘要段可加在同层，不需要新运行时 |
| 设置页把专家与专家团放在同一分节：专家有列表、加载诊断、派生副本、覆盖内置后的「恢复默认」、新建与编辑；专家团有列表、加载诊断、新建、编辑与删除 | `src/renderer/src/experts/components/ExpertSettingsSection.vue`、`src/main/sessions/expert-files.ts`、`src/main/sessions/team-files.ts` | 两者都在页面内闭环管理，不必手改目录；团队不声明能力范围，能力取自成员各自的专家定义 |
| 专家与团队标识与目录名同形，且已按该规则固定校验 | `src/shared-process/expert-definitions.ts` 的 `EXPERT_ID`、`src/shared-process/team-definitions.ts` | 标识即目录名，创建时确定后不可改；显示名称与标识是两个字段 |
| 技能装配入口是「随包非子代理专用技能 + 共享目录技能」的全量覆盖点 | `src/sdk-host/product-resources.ts` 的 `skillsOverride` | 技能收窄就在这里过滤；可见集同时是斜杠补全与 Skill 门禁的来源，三处不会漂移 |
| MCP 由内置扩展在会话启动时读 `mcp.json` 并连接，扩展接受 `loadConfig` 钩子 | `@earendil-works/pi-coding-agent` 的 `McpExtensionOptions`，经 `src/sdk-host/session-runtime.ts` 注册 | 会话级收窄可以在钩子里完成，不必改动用户配置文件 |
| 产品 agent 目录是主进程与 SDK 宿主都能读的共享位置 | `src/main/shared/pi-paths.ts`、`src/sdk-host/product-resources.ts` | 默认能力基线、专家与团队目录放这里，不需要新增 IPC 到宿主的传递链 |
| 会话与专家的绑定在打开链落盘，首轮后锁定 | [会话与聊天](modules/sessions-chat.md) | 开团即绑定团长，不需要第二套身份机制 |
| 同一项目可并行运行多个独立会话（对话标签可显式发起并行任务） | [工作区标签](modules/workspace-tabs.md) | 成员会话不需要新建执行模型，只需归属与列表过滤 |
| 会话记录可承载自定义记录条目 | `@earendil-works/pi-coding-agent` 的 `appendEntry` 能力 | 任务账本与成员轮次记录随根会话走，不新建独立存储 |

### 4.2 外部参考

角色化能力的跨产品对照明细见[会话角色与多角色协作机制](开源项目参考/expert-role-mechanisms.md)（覆盖 WorkBuddy、EvoFlow、DeepSeek Harness、dsh-superagent、Cline、Ekko Studio、OpenBitFun、TencentDB Agent Memory 与 ZCode，核实于 2026-11-18）。跨产品结论只影响下面这张摘要表；单点采纳结论仍以 WorkBuddy 为准。

| 议题 | 外部常见做法 | 本项目的选择 | 结论 |
| --- | --- | --- | --- |
| 角色载体 | 一份定义文件或一份组合配置（WorkBuddy `agents/*.md`、DSH Profile、dsh-superagent preset） | `expert.md`：声明段 + 正文 | 印证 |
| 能力范围声明位置 | 作者声明能力，或平台按类型统一分配（WorkBuddy 的工具权限即由系统按专家类型分配） | 作者声明三维范围，受保护工具不可排除 | 不同：本项目粒度更细，代价是要维护随包工具目录与受保护集合 |
| 绑定粒度 | 会话级、工单级、团队级三档，团队级内部仍是「根 + 下级会话」 | 会话级，首轮后锁定 | 印证：外部没有同会话多身份的先例，多角色都靠独立会话 |
| 多角色协作 | 同会话多角色必须引入持久共享状态（房间、任务板、邮箱）；引入不了的产品把成员放进独立会话 | 已实现：成员会话 + 双账本（§8–§12） | 已选「成员会话 + 双账本」一支：同会话多角色要房间、路由与上下文压缩三套机制，本项目按「一次会话一个专家」不做 |
| 团队限制 | 成本约 3–5 倍、不支持嵌套、无会话恢复、成员权限在生成时确定 | 已采纳为设计约束 | 印证：这些限制被直接写进团队设计的成本与不做项，不重复论证 |
| 提示段治理 | 只有 dsh-superagent 做到不可变版本与上游默认升级差异 | 正文可编辑、派生副本不自动合并 | 部分借鉴：差异展示与自动合并是两件事，本项目只保留人工判断这一层 |

WorkBuddy 是闭源商业产品，这里只对照官方文档描述的公开行为，不涉及任何实现。核实于 2026-11-12，来源见 [WorkBuddy](开源项目参考/workbuddy.md)。

| 对方做法 | 采纳结论 | 本项目的处理 |
| --- | --- | --- |
| 我的专家作为独立入口，创建、修改、分享、删除集中一处 | 借鉴 | 并入设置页，与专家团合为同一分节「专家与专家团」（类型筛选 + 共用诊断），不新开独立页面 |
| 对话式创建：进入创建对话，由内置专家管理工具引导配置，可逐步确认 AI 的分析结果 | 不借鉴 | 与 §3.1「人工配置」冲突；设置页只提供字段与正文编辑，需要帮写时由内置「专家与专家团设计专家」在会话内产出草案，用户自己在设置页落盘 |
| 配置项为头像与显示名称、人设身份、擅长领域、提示词 | 借鉴字段语义 | 落到已有的五类信息：身份、技能范围、MCP 范围、工具范围、正文（§5.4） |
| 创建前须确定名称，创建后不可修改，改名称需重建 | 部分借鉴 | 标识创建后不可改（它同时是目录名与会话绑定键）；显示名称可改，因为本项目标识与展示名已分离 |
| 分享生成链接，被分享方拿到副本 | 不借鉴 | 需要云端托管与分享面；跨机复用仍靠搬运数据目录（§5.5） |
| 删除后不可恢复 | 借鉴 | 已有确认对话框；只删定义文件，目录里还有其他文件时整体拒绝 |

结论：借鉴「自定义专家在设置页内闭环管理」的产品形态与字段语义；不借鉴依赖云端账号的分享，以及在设置页内由模型代写正文的创建方式——会话内产出草案不改变「人审核并落盘」这条边界。草案在会话内以卡片形式提交并由人工点击保存，机制见[会话与聊天](modules/sessions-chat.md)的会话内卡片部分。

## 5. 专家：存放与定义

### 5.1 布局

两类来源各一处目录，互不写入：

- **内置专家**：`resources/agent/experts/<id>/expert.md`，随构建暂存产出、只读、随版本升级；修改它以同标识覆盖的方式落到自定义目录。
- **自定义专家**：`<agentDir>/experts/<id>/expert.md`，可写，随便携数据目录一起迁移。

两者结构一致：一个专家一个子目录，目录名即专家 id，目录内放专家定义文件。目录结构留出附加资源的位置（头像等），本期不引入其他文件类型。

标识与目录名同形、按固定字符规则校验，因此**标识在创建时确定，之后不可改**；显示名称、简介、能力范围、写入范围与正文都可以改。改标识等同于换一份专家，会让既有会话绑定失效，所以不提供重命名。

### 5.2 来源与优先级

- 两个来源合并成一份专家列表，每项标注来源，界面上可追溯。
- 随包目录只读：内置专家的文件在运行期不被修改、不被删除。
- 自定义目录可写。同标识的自定义定义**覆盖**同名内置条目，列表里原位替换并标「覆盖内置」；界面始终能看出当前生效的是覆盖后的那份。
- 优先级是固定的：自定义 > 内置。删除覆盖定义即回到内置版本，不需要另一套「恢复」通道——删掉的就是那份覆盖文件。
- 两个自定义定义之间不会同标识：标识即自定义目录的子目录名，文件系统本身保证唯一。

### 5.3 冲突、覆盖、派生与新建

- 内置专家改动的唯一落地方式是覆盖：随包目录通常不可写（打包后位于安装目录内），因此编辑内置时读随包定义回填，保存写 `<agentDir>/experts/<同标识>/expert.md`，随包文件全程不动。
- 覆盖不跟随内置升级：产品升级后内置正文更新，覆盖项仍按用户改过的版本生效；用户可删除覆盖回到新版内置。这是选择「可改」付出的代价，界面上以「覆盖内置」徽标与「恢复默认」动作显式承担。
- 覆盖定义损坏时（缺声明段、正文为空、标识与目录不一致）不接管：内置条目保留在列表里，另报一条 `definition-invalid` 诊断指向自定义目录的那份文件。坏掉的只是一次改动，不该连带把内置也弄没。
- 识别冲突只剩一种：随包清单里两个条目同标识。同标识的自定义定义不再算冲突，按覆盖处理。
- 自定义专家有两条起点：**覆盖**改的是内置那一份（同标识），**派生**复制出一份独立副本（新标识），**新建**从空白定义起步。三者落到同一个目录、同一种文件形态。
- 新建时标识由主进程分配 `expert-<序号>`（顺延到未占用的编号），落盘前确认不与内置或其他自定义专家重名：中文显示名称无法转成合法标识，而标识创建后不可改，让用户手填只会填错。
- 派生流程：从内置专家复制正文到自定义目录，标识自动顺延为 `<内置 id>-copy`（占用时 `-copy-2`…），并在声明段写入 `derivedFrom` 指回来源。派生副本同样不跟随内置升级；它与覆盖的区别是「新标识、可与原内置并存」。

### 5.4 文件形态

一个专家定义包含五类信息，不在此锁定具体字段：

1. **身份**：显示名称与一句话简介，用于列表与召唤时展示。
2. **技能**：本专家要使用的技能 id 列表，以及它相对默认基线的加减。
3. **MCP 范围**：本专家可连接的 MCP 服务器范围，同样继承默认基线并做加减。
4. **工具范围**：本专家会话里可激活的工具，同样继承基线并做增减；受保护工具（技能门禁、待办清单与记忆组）不可排除。
5. **正文**：方法论、工作流程、输出规范——即真正注入系统提示的部分。

正文为空、或只有能力清单而没有正文的专家，视为无效定义（只带能力清单的专家退化为一个开关，失去引入这一层的意义）。

### 5.5 便携与同步

自定义专家位于产品 agent 目录内，随 `data/`（便携态）或用户数据目录一起迁移，不需要额外的同步通道。跨机器复用依赖用户自己搬运数据目录；不提供导出/导入。默认能力基线同在 `agentDir` 根下，跟着一起搬运，不单独同步。

### 5.6 默认能力基线与增量

两层：**默认能力基线**（全局一份，设置页可改）与**专家定义**（继承基线并做增减）。

- 基线每个维度只有两种形态：不限制（`null`，等于全部），或一份子集。没写过这份文件时三个维度都是不限制，行为与引入基线之前一致。
- 专家每个维度也有两种口径：**继承**（默认）与**仅用选中**。继承时只记录相对基线的 `Add` 与 `Remove`；仅用选中时列表本身就是完整白名单，与外层基线无关。
- 生效集 = 仅在选中模式下取白名单；否则 `基线 ∪ Add − Remove`。三者都为空时不限制，不把当时的清单固化成白名单，新装的技能、服务器与工具仍能被继承。
- 生效集每次会话装配时重算：产品升级新增的技能、服务器与工具随下一次新建会话进入，磁盘上只保存基线与加减集，不保存算出来的集合。
- 基线只在召唤了专家时参与计算：没选专家的会话不读基线、不裁剪任何技能、服务器或工具。
- 专家编辑界面每项只呈现勾选状态，行尾标出它是「基线默认」「额外启用」「已排除」「当前不可用」还是「必需」；勾选差异由页面自己翻译成 Add 或 Remove，用户不需要理解两套写法。默认能力基线不区分继承与白名单：只有一份勾选集合，勾满即等于不限制，保存时归一成 `null`。

| 议题 | 选择 | 代价 |
| --- | --- | --- |
| 基线放哪里 | 产品 agent 目录下的小 JSON | 不进桌面配置中心，需要自己保证原子写与容错读取 |
| 默认口径 | 继承（不限制） | 用户要“管住”专家时必须显式收窄；换来的是不改变任何现有会话 |
| 收窄维度 | 技能、MCP 与工具三个维度 | 工具白名单把权限面引到专家定义，需要一份随包工具目录清单与受保护集合来兜底 |
| 能不能加回基线之外 | 能，以 `Add` 表达 | 需要同时处理加减与“仅用选中”两种口径的展示 |

## 6. 专家：加载与校验

加载发生在会话装配前，产出「可用专家列表 + 诊断」。诊断沿用资源装配现有的方式：在界面上可见、按严重程度分级，不以一句「加载失败」掩盖原因。

需要覆盖的问题类型（不列具体校验实现）：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 结构类 | 目录名与声明 id 不一致、定义文件缺失、正文为空 | 该专家不可用，报诊断 |
| 引用类 | 引用的技能不存在、引用了子代理专用技能 | 专家保留，标记该引用失效 |
| 引用类 | 白名单里引用的 MCP 服务器在全局配置里不存在 | 专家保留，报诊断；项目级服务器因项目而异，不在这里判 |
| 冲突类 | 随包清单里两个条目同标识 | 后者不进入列表，报诊断并给出来源；同标识的自定义定义不算冲突，按覆盖处理 |
| 覆盖类 | 覆盖定义的声明损坏（缺分隔行、正文为空、标识与目录不一致） | 内置条目保留在列表里并报诊断；删除覆盖文件即恢复默认 |

核对原则：**能保留的保留，能标出来的标出来**。引用失效不应让整个专家消失，否则用户改不了、也看不到哪里错了。

一处必须显式拦截的引用：四类子代理专用技能只对子进程可见，不得被专家引用；引用时应报诊断而不是悄悄加载后又失效。

保存期校验与加载期诊断是两套口径，不合并：

- **保存时拒绝**：正文为空、标识写法不合法、新建时与另一个自定义标识重复（与内置同标识是覆盖，不拒）、引用了子代理专用技能、技能白名单为空、把受保护工具排除出范围、写入范围超出上限或含非法项。这些在写入前就能判定，直接不让落盘，并说明是哪一项不满足。
- **保存时提示但不拦**：引用了当前不可见的技能、MCP 服务器与工具，正文超过注入上限。用户可能先写引用、后补能力，拦下来会让编辑无法保存。
- **保存后重读**：写回成功即重读清单，新定义立刻出现在设置页；已打开的会话在新建时才重新装配，即下一次装配才读到新正文与新范围。

写回只动这一份 `expert.md`，声明段里本设计不认识的字段原样保留，避免把用户自己加的说明洗掉。

## 7. 专家：会话内生效

### 7.1 召唤

- 一个会话同时只使用一个专家（团队模式除外，见 §9：此时专家即团长），切换专家等同换一个角色上下文。
- 召唤后把专家正文作为独立的角色段注入系统提示，与既有的其他提示分段并列，不改写用户级与项目级指令。
- 召唤在会话开始前完成，首轮后锁定：绑定随会话持久保存，重新打开或重启应用后仍然带着同一个专家；换专家需要新会话。绑定在打开成功时由主进程落盘（会话身份那一刻才确定），页面只读打开回包，不自行回写。
- 选择入口在输入坞的 ＋ 菜单里：菜单是双级结构，左列是分类行（添加图片、模型、执行模式、专家 / 团队、技能、常用消息），右列是当前分类的二级面板。专家与团队共用一个二级面板，团队在上、专家在下，「不使用专家」为首项；选中团队即把会话专家改成团长。一级列不随候选数量变高，也把「已选哪个」与「有哪些可选」分开。选中后坞内只有一个身份徽标，会话进行中也看得出当前角色；绑定失效时转警示色，后果由坞内的失效说明行承担。
- 绑定的定义被删除或改名后，界面如实标出「已失效」并提示本会话不再注入角色，但不自动清除绑定——重建同名专家即可恢复，自动清理会把误删变成不可恢复。判定只在清单成功读到后进行，避免一次加载失败被误报成失效。
- 覆盖内置的定义被删除不会让绑定失效：标识没变，下一次装配按内置正文生效；这也意味着删除覆盖是**可逆**的恢复动作，界面用「恢复默认」而不是「删除」来表达它。
- 专家只在主会话生效，不写入会话历史，也不随会话记录转移到子进程或成员会话。
- 在设置页改完正文、技能、MCP、工具或写入范围后，从下一次会话装配起生效（都是创建期装配，已打开的会话要重开）：新建会话就按新范围装配，不打断当前轮；标识不可改，因此编辑不会让既有绑定失效。绑定失效只可能来自定义文件被删除，或目录被手工改名。

### 7.2 能力范围

技能、MCP 服务器与工具都受能力范围控制。

- 技能：范围由默认能力基线与专家定义合成。范围外的技能不进会话可见集，斜杠补全、Skill 门禁与提示里的技能清单同时跟着变，不会出现“界面能选、模型看不到”。
- MCP：范围外的服务器在会话启动时标记为停用，不连接、不起子进程、不读凭据；它们在 `/mcp` 里仍列出来，让人看得出是被当前专家排掉的，而不是配置丢了。
- 只减不增：专家引用会话环境里没有的技能或服务器时只产生诊断，不会凭空装配出新能力，也不构成新的信任面。
- 收窄是装配期决定：改完要新建会话才生效；已打开的会话按打开时的范围继续运行。角色段会说明本次的实际范围，避免模型把没加载的能力当成可用。

### 7.3 写入范围

工具范围决定会话有没有写工具，写入范围决定能写到哪里，两者正交。

- 声明三态：`writeScope` 不写行是不限制、写 `[]` 是只读、写列表是白名单（相对项目根的目录以 `/` 结尾，其余按完整文件）。两种“空”不能合并——否则一份只写了一半的定义会静默放大写入面。
- 执行点：宿主在会话装配期挂上守卫，只拦 `write` 与 `edit` 的 `path`，按真实路径与目录边界比较；越界拒绝并给出专家名与允许范围。没有专家的会话不装任何拦截。
- 已知边界：`bash` 的重定向不经过工具参数，不受这层约束；子代理的写入由自己的 `write_scope` 管，两套规则不合并。
- 写错的范围项被忽略并产生 `write-scope-invalid` 诊断，合法项照常生效。

### 7.4 不改变的边界

- **工具集按范围裁剪**：范围外的工具在会话开始装配时从激活集合移除；技能门禁、待办清单、记忆组与语气风格组属受保护项，始终保留（后两组同属记忆组件，整组由记忆配置与快速模式决定）。只有随包工具清单登记过的工具可被裁剪，内建控制工具（如 `ask_user_question`）与 MCP 管理工具既表达不了也勾不到，装配时一律保留。团队工具（账本、派活、停止）由装配期单独保留，不因专家工具范围被移出。装配时与快速模式的记忆工具剔除合并为一次 setActiveTools，各自调用会互相覆盖。
- **不产生嵌套委派**：子代理子进程没有委派工具，也不加载专家正文；专家可以派子代理，但子代理不认识专家，仍是一层。
- **不改变权限与信任**：专家正文与用户自己写的技能同源，不构成新的信任面，也不绕过任何既有确认。

### 7.5 上下文影响

角色段会占用系统提示空间。单专家不叠加，是控制这一成本的主要手段；正文超过注入上限时在前段截断并在尾行说明，定义文件本身不被改写，也不因此报诊断——规则收紧不能让已在用的定义突然失效。上限量与截断判断只有一个来源，主进程视图与宿主角色段共用同一口径；设置页列表与输入坞选择器都标出「已截断」，用户能看出后面那段没进去。

## 8. 团队：定义与存放

团队与专家同构：一份 Markdown 文件放在以团队标识命名的目录里，声明段写结构，正文写这个团队的协作约定。

- **两类来源**：内置团队随包只读，自定义团队在产品 agent 目录下可增删改，随便携数据目录一起迁移。
- **声明段内容**：名称、一句话简介、团长（专家标识）、成员（专家标识列表）。这几项就是团队的全部结构，不另设权限、模型或预算字段——能力由成员自己的专家定义决定。
- **团长必须是专家**：空白助手无法拆出有方法论支撑的任务；团长也不是「根会话当时恰好绑定的专家」，而是团队定义里的那一份。
- **引用一致性**：团长与成员的专家引用失效时只标诊断，不整体作废；一个团队里至少要有团长与一个可用成员才算可开团。
- **标识稳定**：团队标识即目录名，创建后不可改；显示名称可改，与专家的处理一致。
- **管理入口**：团队与专家合并在设置页「插件」分节下的「专家与专家团」插件详情，同页按类型筛选；团队行给出团长与成员的显示名、可开团状态，内置只读，自定义可新建、编辑与删除。保存时标识由主进程分配 `team-<序号>`，界面不提供标识输入。
- **团长不进成员**：解析与保存都会把成员名单里的团长剔除并记一条诊断。派活只校验「在成员名单里」，团长留在成员里会让团长以成员身份被开出一个可写会话，绕过「团长不生产」。
- **不提供派生副本**：当前随包 `teams` 段为空，派生只会得到一份没有来源的副本；等有内置团队时再按专家那套派生规则补。

## 9. 团队：开团与团长边界

### 9.1 开团与团长身份

- 开团入口与「选专家」在同一个面板：新建会话时在输入坞的「专家 / 团队」面板里选择团队，即把会话专家绑定为该团团长，并开启团队模式；坞内身份徽标只渲染一个，团队优先。
- 会话已开始第一轮后不可开团、不可换团，与「换专家需新会话」同一条规则。
- 团队模式是随会话持久保存的状态，重开应用后仍是同一个团。
- 修改团队定义（增删成员、换团长）不改变已开团的会话，下一次装配才生效；这与专家改正文的生效口径一致。
- 团长身份只有一个来源：团队定义决定绑定，会话绑定决定实际装配，两者在开团那一刻对齐，不存在第二个权威。

### 9.2 团长只做四件事

1. **定计划**：把目标拆成任务条目，写明分工、依赖与验收项。
2. **派活**：把条目派给成员，处理依赖顺序，必要时改派。
3. **验收**：依据可核实证据判断任务是否成立，决定接受、改派或打回。
4. **整合交付**：汇总成员结果，向用户交付最终产物并说明未解决项。

### 9.3 工具边界

| 能力 | 团长 | 说明 |
| --- | --- | --- |
| 任务账本读写 | 有 | 分配权与账本的唯一入口 |
| 派活、停止、打回 | 有 | 唯一能驱动成员的角色 |
| 只读检查（读文件、检索、列目录） | 有 | 验收需要证据；这是与「只能听汇报」的关键差别 |
| 向用户确认、交付卡片 | 有 | 用户只与团长对话 |
| 写文件、编辑、执行命令 | 禁用 | 团长不产出交付物 |
| 委派子代理 | 禁用 | 团队内执行一律走成员，避免「团长的子代理」这条绕过成员的旁路 |

- 团队语义优先于专家的工具范围：即使团长专家的定义里包含写与执行，团队模式下也会在装配期移除。否则一个团队会因团长专家配得宽松而退化成单专家。
- 团长被移出的工具固定为四个：`write`、`edit`、`bash`、`delegate_subagent`。其余工具按团长专家的范围保留，不额外裁剪：验收需要看文件与产物，因此 `read`、检索与列目录类工具留在团长手里；是否还要更多检索能力由验收需要决定，而不是默认加上。
- 只读工具保留的是「能验证」而不是「能生产」：它能看产物、看文件是否存在、看改动是否符合验收项，但不能修改任何东西。
- 团长的写入范围在装配期被置为只读，与其专家声明的三态无关。

### 9.4 团队分段

团队模式下向根会话注入两段系统提示：

团队段（`team-role`）固定为三块：

1. 团长身份与四条职责，明确禁止自行执行。
2. 成员名册：标识、显示名、简介、显式能力范围。
3. 派活与验收规则：任务说明必须含验收项；依赖未满足不得派发；打回须附证据与未满足的验收项；打回只有一次机会。

账本摘要单独一段（`team-board`）：只给目标与各状态计数，不逐轮贴整份账本；目标超过上限截断成一句，条目状态、依赖与验收项以最近一次 `team_board` 提交为准。两段分属不同扩展，**不要**把摘要写回团队段：写同一分段时会互相覆盖。

两段都随每轮重写。成员结论与待决项不预先注入团长上下文，而是随 `team_assign` 的回执在派活当下送达。

## 10. 团队：成员会话与双账本

### 10.1 成员会话

- 一个成员对应一个会话，绑定该成员专家，拥有独立上下文与用量，并带归属标记指向根会话。
- 成员会话 id 由根会话与成员标识确定性推出，目录位于 `<agentDir>/team-sessions/<根会话 id>/`，因此不在项目会话列表、不占标签、不能被其它团队复用，也不能再开团。
- **派活＝向成员会话发一条任务消息并跑完一轮**；同一成员再次派活复用同一会话，因此保留它自己的上下文——这是与委派子进程最本质的差别。
- 成员只收到团长给的那条任务说明，看不到任务账本全貌，也读不到其他成员的结论；独立路径可以避免互相模仿与路径依赖。
- 成员遇到需要拍板的事写进结论的待决项，由团长下一轮读到后决定继续、改派或向用户确认；成员不能主动联系团长。
- 成员的能力范围与写入范围仍由它自己的专家定义决定，团队层不再收窄，也不放宽。
- 成员会话对用户只读可看：时间线、用量、结论与写入文件，不提供输入入口。

### 10.2 任务账本

任务账本随根会话持久化，包含四部分：

- **目标**：用户要什么，以及明确的边界与不做项。
- **事实**：已确认的事实与来源，供成员复用而不必各自重查。
- **计划**：任务条目及依赖关系。
- **条目状态**：待分配（`pending`）→ 已分配（`assigned`）→ 执行中（`running`）→ 待验收（`review`）→ 已完成（`done`）；失败走 `failed` 并在备注里写一句原因。条目带依赖、指派人、验收项与备注，但不带结论正文。

条目不保存产物正文。产物留在工作区文件里，账本只存路径与摘要——避免把长文搬进团长上下文，也避免多轮复制导致内容失真。

账本存在 `team_board` 工具结果的 `details` 里，随会话分支落盘；rewind 或 fork 后自然回到当时那份。

### 10.3 进度账本

每轮派活结束后，团长按固定五问自省：是否已满足用户目标、是否在原地打转、这一轮是否有实质进展、下一个该由谁行动、要给它什么指令。结论决定续派、改派、打回或收尾。

进度账本是团长的推理规则，不单独落盘；它的结论以任务条目状态与派活决定的形式留痕。

### 10.4 信息调度

- 团长每轮看到的是：账本摘要、各条目状态、未读的成员结论摘要与待决项。
- 成员轮次的结论摘要、写入文件、待决项与用量由宿主写入根会话记录（`team-member-run.v1`），读侧合并为团队轮次；它们与账本并列，不会被团长的自述改写。
- 用户每轮看到的是：团长的说明与交付，而不是成员之间的往来。
- 成员之间没有通道；需要共享的结论由团长写进账本事实区，下一轮派活时随任务说明下发。
- 账本摘要只在每次开工时给目标与状态计数；完整条目只在两处出现：`context` 钩子按工具结果计数节流回述，以及 `team_board` 提交后的工具回执。
- 这条规则让「开会」只发生在团长与成员之间，避免成员互相干扰与上下文互相污染。

## 11. 团队：派活、验收与打回

- **派活必填**：目标、产出形式、验收项、边界（不许改动什么）。缺验收项的派发直接拒绝——没有验收项的任务无法判断是否完成，也无法打回。
- **依赖校验**：条目的依赖未全部完成时拒绝派发，并说明还差哪几条；顺序由团长决定，宿主不替团长排程。
- **成员校验**：负责成员必须在团队名单内，且团长不能以成员身份被派活。
- **终态回写**：成员一轮结束时，由宿主按执行快照把终态、结论摘要、产物引用与待决项写成一条根会话记录，读侧合并为团队轮次事实；账本条目状态仍只由团长提交——两份事实分属两个写入方，谁都不能替对方写。
- **验收强制**：验收项没有全部勾选的条目不允许置 `done`，提交时会被退回 `review` 并说明缺哪几项；「完成」因此由验收项与宿主记录共同决定，不由团长一句话决定。
- **验收与打回**：团长依据只读证据核对验收项。打回必须附上未满足的验收项与证据位置，不允许「再完善一下」这类无验收项的返工。
- **打回上限**：同一任务默认只给一次打回机会：失败与中断都计入失败轮数，超过上限后宿主直接拒绝再派，只能改派或上报用户。依据是 §4.2 的配对实验：无法核实的反复返工会降低结果质量并增加模糊措辞。
- **改派**：打回机会用尽、成员能力不足或成员会话不可用时，团长可把条目改派给另一成员，任务说明由团长重写。

## 12. 团队：收敛、面板与成本

### 12.1 收敛与生命周期

- 根会话中断、关闭或应用退出时，全部在途成员轮次终止，走与单轮中断相同的收敛路径（先请求结束，超时后强制结束）。
- 团队结束不删除成员会话记录与账本；账本随根会话记录走，不新建独立存储、不引入新的保留策略。
- 不按时间过期：成员会话是否清掉只看根会话还在不在。删除根会话时成员目录立即移系统废纸篓；应用启动后低频核对一次，根会话在所有已添加项目里都找不到的成员目录连同登记与团队绑定一并清理。
- 重开根会话时账本结构可重建，但在途轮次一律标为已中断，不自动续跑。
- 停止成员轮只能由团长通过 `team_stop` 发起；用户直接在面板上停止需要渲染层到 SDK 宿主的中断通道，目前未做（见 §3.3）。这是人工干预之外的唯一停轮路径，不构成第三个驱动方；用户仍不能向成员会话输入内容。

### 12.2 面板与可观察性

- 团队面板嵌在根会话里，不新增顶层页面、不新增标签：任务列表（状态、负责成员、依赖、写区重叠提示）、成员入口。
- 位置与待办清单一致：贴在输入坞上方，标题行即折叠开关；非团队会话整块不渲染，也不读取成员清单。
- 面板只读：它展示账本、成员状态、写区重叠与成本，不提供派活、改状态、停止或输入入口——这些只能由团长的工具完成。
- 点开成员进入只读对话查看：时间线、用量、结论、写入文件、未解决事项。
- 写区重叠只做提示：成员之间按各自专家的写入声明两两比较（`null` 视为不限制，与任何声明算重叠），重叠时在面板标出；执行期仍由成员自己的写入守卫硬拒越界，不形成第二套判定。
- 成本提示：面板标题行给出成员数与该团队的累计成员轮次用量。
- 跨会话用量统计同样含成员会话：它们不在项目会话目录里，统计会单独扫 `<agentDir>/team-sessions/` 并按根会话归组为「团队用量分布」；会话列表里带「团队」标记，可下钻到该团队的成员会话明细。

### 12.3 成本、适用与风险

1. **成本显著更高**。每个成员是完整会话装配加独立上下文与用量；外部数据显示多智能体约为普通对话的 15 倍 token。因此团队默认关闭，并在入口说明适用场景。
2. **适用面窄于单专家**。适合可并行、可验证、信息量超过单会话承载的任务（调研、审查、多文件独立改造）；不适合强依赖、需要所有角色共享同一上下文的单点调试与反复试错。成员之间不共享上下文，跨成员的中间结论只能靠任务账本与产物传递，与用户对「开会式协作」的直觉有差距。
3. **团长无法核实时会变差**。只读验收是缓解手段，但团长仍可能只看产物不看过程；因此验收项必须可判定，而非「质量要好」。
4. **逐轮同步是瓶颈**。一个成员跑得慢会拖住整轮，团长也无法在成员执行中途改指令；这是当前形态的已知限制，异步派活不在本期范围。
5. **成员能力固定**。成员权限与写入范围在开团时由其专家定义决定，团队不因任务临时放宽；需要更宽能力时改专家定义后新建会话。
6. **账本增长**。任务条目与结论摘要累积会挤占团长上下文，因此按上限收敛：条目、事实与验收项各有上限，成员轮次记录只保留最近若干条（数值以定义处为准）；摘要段只给目标与各状态计数，不逐轮贴整份账本。
7. **与委派的关系需持续守界**。团队用成员会话，轻量只读任务仍用 `delegate_subagent`；两者并存的前提是职责清楚：一次性隔离任务走委派，需要续派与协作走成员。

## 13. 与相邻能力的分界

| 能力 | 回答的问题 | 执行位置 | 与专家／专家团的关系 |
| --- | --- | --- | --- |
| 技能 | 怎么做某件事 | 主会话与各成员会话（子代理专用技能除外） | 专家可引用技能，但不能内联技能正文 |
| 子代理 | 把一段工作挪到隔离进程里做 | 独立子进程，一次调用一个 | 专家可经 `delegate_subagent` 使用，受工具范围控制；团队内禁用团长的委派；子代理不认识专家 |
| 专家 | 以谁的身份、用什么方法、按什么规范交付 | 单个会话 | 专家层对象；团长与成员都是专家 |
| 专家团 | 多角色如何分工协作 | 根会话（团长）+ 多个成员会话 + 共享任务账本 | 团队层对象；成员是绑定各自专家的独立会话，不受同一会话里的多个角色支配，也不在子代理层 |

## 14. 关键取舍

| 议题 | 选择 | 代价 |
| --- | --- | --- |
| 存放形态（专家） | 文件化专家目录，两类来源各一处 | 需要新增资源类型与加载校验，不能复用配置中心的字段回退 |
| 同名处理（专家） | 自定义同标识覆盖内置，另保留派生副本 | 覆盖项与派生副本都不自动跟随内置升级，回到新版内置要靠「恢复默认」 |
| 作用域（专家） | 只做全局（内置 + 用户级） | 无法为单个项目定制专家，需靠项目指令与技能补 |
| 生效方式（专家） | 系统提示注入 + 技能、MCP、工具与写入范围 | 工具白名单需要随包工具目录与受保护集合维护，预算仍不变 |
| 范围配置（专家） | 默认基线 + 专家增量 | 改基线会同时改掉所有继承型专家，需要界面明说影响面 |
| 与委派的关系（专家） | 可授予、可收回 | 需要并行或上下文隔离的任务可以把委派工具收进或移出专家范围；子代理本身仍单层、不认识专家 |
| 创建方式（专家） | 表单式填写，不由模型代写正文 | 用户要自己写方法论；换来的是与「人工配置」一致、无模型调用成本 |
| 编辑形态（专家） | 设置页内按文本编辑，不复用外部编辑器 | 写回要自己保证格式与未知字段保留；换来的是新用户不必找目录 |
| 标识稳定性（专家与团队） | 标识创建后不可改，显示名称可改 | 名称与标识可能不一致，界面要同时展示；换来的是会话绑定不被编辑打断 |
| 可见性（专家） | 一次会话一个专家 | 无法在一次对话里让多个角色交叉发言；多角色靠团队 |
| 执行单元（团队） | 成员为独立会话 | 每成员一次装配、独立上下文与用量；扩展现有委派做不到续派与跨轮归属 |
| 团长能力（团队） | 只读 + 调度，禁写与执行 | 团长不能边做边拆，必须先派活看清；纯协调（无文件访问）会让验收只能听汇报 |
| 团长来源（团队） | 团队定义的团长，开团时绑定会话 | 换团长要换团队或新建会话；沿用会话当前专家会让团队定义与会话绑定形成两个来源 |
| 协作载体（团队） | 任务账本随根会话持久化 | 无法跨团队共享、无独立查询接口；独立任务板存储要多一套保留与访问边界 |
| 通信拓扑（团队） | 全部经团长汇聚 | 成员之间不能直接对齐口径；成员互发消息要消息总线、被动唤醒与权限收敛 |
| 打回（团队） | 有上限且必须附验收项 | 团长不能反复要求打磨；无上限返工会让清晰度随每次返工下降 |
| 成员可见性（团队） | 成员对用户只读 | 用户不能直接纠正成员；可输入会引入第二个驱动方 |

## 15. 风险与可行性限制

### 15.1 专家层

1. **执行层没有「角色」概念**。系统提示装配可以承载分段，但「选中的专家是谁」需要在会话生命周期里被记录与传递；这一条不落地，召唤只是把一段文字塞进提示，界面上无法回显。
2. **专家能力仍偏弱**。工具范围只能收窄既有工具，不能凭空增加能力；专家多用于改善方法与人设，不直接缩短长任务或隔离噪声。
3. **覆盖项与派生副本都会漂移**。见 §5.3：内置升级后覆盖项不自动合并，用户看到的仍是自己改过的版本；派生副本同理。区别是覆盖保留原标识（会话绑定不受影响），派生换了标识（绑定要重选）。
4. **快速模式的交互未定**。现有执行模式会在新建会话时剔除部分技能与能力；被剔除的专家引用技能已在角色段尾说明，仍待定的是「快速模式下专家是否可选」（§17）。
5. **正文质量不可控**。人工编写意味着质量方差大；不做评分、推荐位与质量校验。
6. **页面内写回会碰用户的手工格式**。用户可能手写过声明段里的其他字段或特殊排版，页面保存必须保留未识别字段、只改它能识别的那部分，否则一次保存就洗掉手工内容。
7. **显示名称与标识分离带来理解成本**。两个名字并存时，用户容易以为改显示名称就能换掉绑定；界面需要同时给出标识并说明标识不可改。
8. **基线是共享的**。改默认能力会同时影响所有继承型专家，用户可能只想调一个专家却动了全局；界面必须在基线与专家两处分别说明影响面。
9. **MCP 合并逻辑是本地复刻的**。SDK 没有导出它自己的配置合并函数，收窄只能在 `loadConfig` 钩子里交回一份同形状的结果；Pi 调整覆盖语义时本仓库需跟着核对。

### 15.2 团队层

10. **成本与适用面**：见 §12.3 的前两条，默认关闭并在入口说明适用场景。
11. **团长无法核实即失效**：只读验收是唯一兜底，验收项必须可判定。
12. **逐轮同步是瓶颈**：成员跑得慢拖住整轮，中途改不了指令。
13. **成员能力固定**：临时放宽能力只能改专家定义后新建会话。
14. **账本增长挤占上下文**：靠条目上限与摘要段收敛，数值以定义处为准。
15. **两套工具并存需守界**：成员会话与 `delegate_subagent` 的职责划分要持续在界面与文案上区分。
16. **用户侧不能停轮**：中断通道未做，用户只能通过团长下达停止。

## 17. 待定项

以下不影响当前设计方向，留到后续按当时事实确定：

- 快速模式下专家是否可选。
- 被能力范围排除的 MCP 服务器在 `/mcp` 里如何呈现：当前按「列出但停用」处理，文案与是否提供“临时启用”入口待定。
- 默认能力基线是否提供项目级覆盖：当前只做全局一份，项目级服务器仍按项目配置装配。
- 团队账本摘要的注入长度与折叠方式，以及条目上限等数值。
- 团队面板的成员用量排序与导出未做：目前只在面板标题行与设置页「团队用量分布」给出汇总结论。
- 成员会话与 `delegate_subagent` 的分工需要在入口文案上说清：一次性隔离任务走委派，需要续派与多角色协作走成员会话。
