# 会话内卡片工具设计（present-card）

本文是 pi-desk「会话内卡片」能力的初步设计：要解决的问题、已确认需求与不做项、项目事实、外部参考、大致设计方案、职责边界、关键取舍、风险、阶段划分与后续候选场景。本文不描述字段级协议、渲染细节、文件清单与验证方案；模块现状以 `docs/modules/` 为准，两者不一致时以模块文档为准。

## 1. 背景与问题

pi-desk 目前的交互产物分成三类，各自有明确来源：

1. **工具结果卡片**：模型调用工具，工具在结果里交付结构化快照，渲染层按工具名用固定组件展示（委派子代理即此形态）。
2. **命令触发的固定对话框**：由输入坞识别命令后打开（如 `/memory status` 打开记忆注入卡片）。
3. **扩展发起的原生弹窗**：扩展要求选择、确认或输入文本。

缺口在于：模型产出一份**需要用户点一下才落地**的成果时（专家定义草案、配置草案、待保存的清单），只能输出普通文本，用户要自己复制、找入口、逐字段重填。专家定义尤其明显——草案在会话里，落盘入口在设置页，两边没有连接。

产品曾在 2026-11 移除过一整族「生成式界面（genui）」：由模型描述任意界面、渲染器尽力解释。因此本设计必须先回答一个边界问题：**引入卡片不是把 genui 加回来**（见 5.4）。

本期要解决的是：给「模型产出、用户点按钮落地」这类交互一条统一通道，让上层场景只提供数据与动作名，而不是每来一个场景就重做一遍渲染与写入。

## 2. 已确认需求

### 2.1 需求

1. **一个通用载体，而非单场景组件**：后续场景（记忆候选、技能草案、配置草案等）复用同一套外壳与动作机制，不重新设计交互。
2. **卡片上直接落地**：用户点卡片按钮即完成写入，不需要跳到设置页重填；写入复用产品已有通道与校验，卡片不自建第二套写盘路径。
3. **模型只提供数据，不提供界面结构**：卡片类型与动作都是宿主枚举，模型在其中选；枚举外一律不成立。
4. **可降级**：卡片渲染不出来或不支持时，信息仍以文本形式可用。
5. **首个落地场景是专家定义草案**：内置「专家设计专家」产出草案后经卡片保存为自定义专家。

### 2.2 不做项

| 不做 | 原因 |
| --- | --- |
| 模型描述任意界面（布局、样式、组件树） | 即已移除的 genui 路线；安全问题优先于表达力 |
| 卡片内嵌第三方 HTML/JS 或沙箱 iframe | 等于在客户端跑外部代码；当前无沙箱与 CSP 治理能力 |
| 第三方扩展注册自定义卡片类型 | 卡片类型保持随包枚举，避免把 UI 注入面重新打开 |
| 卡片内编辑字段并二次保存 | 编辑仍归设置页；卡片只做一次性落地 |
| 高影响动作（写 MCP 配置、写技能目录、批量应用补丁） | 需要单独的确认与风险分级，不在首期 |
| 按专家收窄工具集以实现「只有某专家能看到卡片工具」 | 与现有边界冲突：专家只收窄技能与 MCP，不收窄工具 |

## 3. 项目事实与依据

| 事实 | 出处 | 对设计的作用 |
| --- | --- | --- |
| 工具结果的结构化数据可直达渲染层，并由跨进程契约校验后才使用 | `src/sdk-host/projection/tool-projection.ts`（子任务快照解析）、`src/shared/runtime/projection.ts`（工具执行项字段）、`src/shared/sub-agent-view.ts`（契约与解析器） | 卡片数据沿用同一形态，不引入第二条下发链路 |
| 渲染层已具备「按工具名渲染专用组件」的位置 | `src/renderer/src/sessions/components/ChatMessageItem.vue` 的工具块分支 | 卡片组件挂在这里，不新增消息类型 |
| 宿主可注入产品内置扩展并注册工具 | `src/sdk-host/session-runtime.ts` 的 `extensionFactories`（委派工具即此方式） | 卡片工具作为产品内置扩展注册，不改 `resources/agent` 扩展清单 |
| 专家保存通道已存在且已暴露到渲染层 | `desktop:expert-save`（`src/shared/experts-api.ts`）、preload 的 `saveExpert` | 卡片动作直接复用，不新增 IPC |
| 写入校验集中在主进程 | `src/main/sessions/expert-files.ts`：标识由主进程分配、保存期强校验、原子写 | 卡片动作不复制校验，只呈现结果 |
| 专家清单有两个刷新入口 | `src/renderer/src/sessions/stores/session.ts` 的专家清单加载（输入坞 ＋ 菜单）、`src/renderer/src/experts/stores/expert.ts` 的 `load()`（设置页） | 保存成功后要让 ＋ 菜单与设置页看到新专家 |
| 专家只收窄技能与 MCP，不收窄工具集 | `docs/experts-design.md` §3.2、§7.3 | 卡片工具对所有会话可见，不做按专家装配 |
| 生成式界面已整族移除，不保留关闭态代码 | 2026-11-13 决定记录（`ui.genui-removed`） | 本方案必须显式界定与 genui 的区别 |

## 4. 外部参考与调研结论

外部调研于 2026-11 完成（来源为官方文档与开源仓库；A2UI 的 1.0 规范上游标注 candidate、部分开源实现标注 experimental，此处作设计参照，不作为运行时依赖）。

| 路线 | 代表实现 | 模型生成粒度 | 采纳结论 |
| --- | --- | --- | --- |
| 受限组件目录 + 动作白名单 | A2UI 的 catalog 注册表、Vercel `json-render` 的 `defineCatalog`、assistant-ui 的组件 allowlist | 组件名 + 属性 + 子节点的 JSON 树，名字必须命中宿主注册表，未命中硬失败 | 直接采用为核心约束 |
| 工具 → 组件注册表 | Vercel AI SDK 的生成式 UI、CopilotKit「组件即工具」、MCP Apps 的工具与视图绑定 | 工具结果按工具名映射到客户端组件 | 直接采用为载体（pi-desk 的委派卡片已是此形态） |
| 服务器提供 HTML（沙箱 iframe） | MCP Apps（MCP 官方扩展）、OpenAI Apps SDK | 任意 HTML + JS | 仅作对照：表现力最强，但等于运行第三方代码，公开安全研究记录了这类宿主上的越权与跨会话读取问题 |
| 自由 UI 描述 | 早期 genui、Figma Make Designs 下线、Claude Artifacts 安全研究 | 任意结构 | 不采用 |

可直接借鉴的三条工程做法：

1. **数据与控制分离**：工具结果里给模型的是简短结论，给界面的富数据单独承载，避免同一份正文在上下文里重复出现。
2. **动作名是枚举**：动作由宿主声明并绑定到既有通道，模型只能选名字，不能定义新动作；高风险动作另行要求确认。
3. **状态机最小化**：卡片只需「待提交／提交中／已提交／失败」四态，已提交即终态，不做可撤销的双向状态。

结论：业界已收敛到「模型只产出数据、组件与动作均为宿主枚举」这一形态，且自由生成 UI 路线有明确的安全与维护失败记录。本项目的实现取其组合——**工具通道承载数据，枚举约束类型与动作**。

## 5. 设计方案

### 5.1 形态：工具通道 + 宿主枚举

- 一个产品内置工具承载所有卡片，模型提交「卡片类型 + 内容字段 + 动作名」，不提交任何布局、样式或组件树。
- 卡片类型与动作名都是随包常量：类型不在枚举内、动作不在白名单内，工具直接报错，不产出半成品卡片；渲染层对未知值同样失败并降级为文本。
- 外壳由产品提供且各场景共用：标题、副标题、字段行、正文、主次按钮、状态区。场景只换内容与动作，不换外壳，因此视觉与无障碍质量不随场景波动。
- 卡片数据随工具结果的结构化字段下发，模型看到的是简短结论；正文等富内容不进模型上下文。

### 5.2 数据流

模型产出草案 → 调用卡片工具提交（类型 + 字段 + 动作）→ 宿主校验枚举与字段后写入工具结果的结构化字段 → 投影层解析并随工具执行项下发，渲染层按契约校验 → 卡片组件展示 → 用户点按钮 → 渲染层调用该动作绑定的**既有**业务通道 → 主进程按自身规则校验并落盘 → 卡片显示终态并刷新受影响的清单。

关键约束：动作只做转发，不做判断；写入是否成立仍由主进程判定。渲染层不直接写文件，也不读模型未提交的内容。

### 5.3 组件类型与动作

首期只落一个类型与两个动作，其余在架构上留位：

- **类型：专家定义草案（expert.draft）**——一份可落盘的专家定义，含标题（显示名称）、副标题（一句话简介）、若干字段行、正文、能力范围与主动作。类型即场景契约：带能力段的草案不叫通用 `draft`；旧卡片没有能力段时按「继承默认基线」处理。
- **能力段**：与专家定义的声明同构——技能与 MCP 各带口径（`inherit`／`only`）与名单，语义沿用「继承＝基线加减、仅用选中＝白名单、皆空＝不限制」。模型只能给建议名单，卡片列出现有候选供用户勾改；候选与默认基线来自能力候选通道，不在模型侧拼装。
- **动作 `expert.save`**——把草案连同当前勾选的能力范围保存为自定义专家，复用专家保存通道（标识由主进程分配）；成功后卡片进入终态并刷新专家清单。
- **动作 `copy.text`**——把正文复制到剪贴板，纯只读，作为无法保存时的兜底。

动作与类型的增补遵循同一原则：先有明确场景与唯一落点，再进枚举；不在未确定落点时预留占位动作。

### 5.4 与生成式界面（genui）的边界

| 维度 | 已移除的 genui | 本方案 |
| --- | --- | --- |
| 模型产出 | 任意界面结构，渲染器尽力解释 | 只在宿主枚举里选类型与动作，其余一律失败 |
| 组件与样式 | 由描述决定 | 全部随包提供，各场景共用同一外壳 |
| 动作语义 | 模型自定义 | 白名单 ID，绑定到既有业务通道 |
| 失败形态 | 渲染出半成品或无内容 | 硬失败并降级为文本 |

结论：本方案不是 genui 的复活，但它确实改变了「模型完全不参与界面产出」这一绝对表述。这条边界需要与 genui 的移除决定并行成立，并作为该能力后续扩展的判据——任何让模型描述结构、样式或可执行内容的提案都超出本设计范围。

## 6. 职责边界与不改变的约束

| 层 | 职责 |
| --- | --- |
| 宿主工具 | 校验枚举与字段形状，产出结构化结果与简短文本；不写盘、不改清单 |
| 共享契约 | 卡片视图的形状与跨进程校验；宿主与渲染层共用同一份判定 |
| 投影层 | 从工具结果提取卡片数据，形状不符时按「没有卡片」处理，不猜造字段 |
| 渲染层 | 外壳展示、动作转发、终态与错误文案；不自行拼装写入参数以外的内容 |
| 业务通道 | 校验与落盘（专家保存走既有通道，标识分配与原子写不变） |

不改变的约束：

- 不新增第二套写盘路径，不在渲染层复制业务校验；
- 不改变工具集与权限模型：卡片工具常驻，不按专家收窄，也不构成新的信任面；
- 不改变既有三类交互产物（工具卡片、命令对话框、扩展弹窗）的形态与职责；
- 卡片数据只进界面，不进系统提示。

## 7. 关键取舍

| 议题 | 选择 | 代价 |
| --- | --- | --- |
| 载体 | 复用工具通道，不新增独立 UI 描述协议 | 卡片数据受工具结果通道的形状与体积约束 |
| 通用方式 | 一个工具 + 类型判别 + 统一外壳 | 判别需要严格校验，否则退化成任意 JSON |
| 枚举位置 | 随包常量，不开放第三方注册 | 新场景要跟随版本；换来 UI 注入面不扩大 |
| 首期动作范围 | 仅保存专家与复制正文 | 通用架构先就位，短期覆盖场景少 |
| 工具可见性 | 所有会话常驻 | 模型工具清单多一项；换取不改专家能力范围的定义 |
| 状态管理 | 渲染层内存态，已提交即终态 | 应用重启后卡片回到「待提交」外观，需靠内容本身判断是否已保存 |

## 8. 风险与可行性限制

1. **枚举挡不住字段值**：类型与动作可控，但字段内容是模型产出的文本，渲染时必须按纯文本处理，禁止进入富文本或链接注入路径。
2. **能力名单只能建议**：卡片上的勾选才是最终范围，模型给的名单可能超出候选或引用子代理专用技能；不可用引用由主进程保存时回报，卡片必须就地展示而不是静默丢弃。
2. **动作看起来比实际更强**：按钮存在会被理解为「一定能保存」，但主进程校验仍可能拒绝（重名、引用不可用技能等）。失败原因必须就地显示，不能只让按钮回到可点状态。
3. **上下文与实际体积**：卡片正文不进模型上下文，但工具参数本身在上下文里；长正文会推高单轮成本，需靠既有长度约束与提示引导控制。
4. **两处清单刷新**：保存后若只刷新一处，输入坞菜单与设置页会短暂不一致，容易被当成保存失败。
5. **字段膨胀**：通用外壳容易演变成「什么都能塞」，需要按场景评审字段，而不是把卡片做成自由表单。
6. **术语漂移**：文档与界面若不区分「卡片」与「生成式界面」，后续容易被理解为 genui 回归，判据见 5.4。

## 9. 开发阶段

| 阶段 | 目标 | 设计关注点 | 依赖 |
| --- | --- | --- | --- |
| 一、契约与工具 | 一个卡片工具 + 类型与动作枚举 + 硬失败降级 | 枚举校验位置、字段上限的归属、工具结果只带结论 | 无 |
| 二、下发链路 | 卡片数据经投影层与跨进程契约到达渲染层 | 形状不符时的降级、历史记录的兼容（旧数据没有卡片字段） | 阶段一 |
| 三、外壳与动作 | 统一外壳组件、动作转发、终态与失败文案、清单刷新 | 动作语义边界、无障碍、两处清单刷新的一致性 | 阶段二 |
| 四、首个场景与文档 | 专家定义草案落地，内置专家的交付方式改为提交卡片 | 草案与保存结果的口径一致、正文长度约束 | 阶段三 |

各阶段的具体实现方式在进入该阶段时按当时事实讨论确定。

## 10. 候选场景（后续，不在首期）

以下场景在「有唯一动作落点」时才进入枚举；按落点是否已存在排序。

| 场景 | 卡片内容 | 动作与落点 | 前置条件 | 风险 |
| --- | --- | --- | --- | --- |
| 记忆候选 | 本轮值得记的若干条，可勾选 | 写入记忆库（复用记忆保存通道） | 需要确定勾选粒度与「不选即不写」的默认 | 低 |
| 会话交付汇总 | 本轮改动、删除项与受影响文件 | 复制文本、在文件管理器中定位 | 无（纯只读） | 低 |
| 技能草案 | 技能名称、描述与正文 | 写入产品目录或共享目录 | 需先确定写入位置选择与同名冲突策略 | 中 |
| MCP 服务器配置草案 | 服务器名、启动命令与参数 | 写入 MCP 配置 | 引入外部进程与凭据，需二次确认与显式展示参数 | 高 |
| 自动化/定时任务草案 | 频率、范围与脚本 | 保存为任务 | 产品尚无任务持久化面 | 高 |

最后两项即使将来实现，也应绑定单独的确认流程，不复用首期「点一下即保存」的强度。

## 11. 待定项

- 卡片是否需要在工具结果里附带「已保存」的持久标识，以支持重启后的终态回显（首期按不附加处理）。
- 多动作卡片（主次按钮之外的第三动作）是否纳入枚举：首期只有主次两槽。
- 卡片正文的折叠默认状态与展示长度，留到界面阶段按实际内容确定。
- 动作失败时的重试策略：首期由用户再次点击，不做自动重试。
